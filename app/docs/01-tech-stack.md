# APP 设计文档 01：技术栈

> **文档状态**：正式设计稿 v2.1（iOS 分发口径修订），待评审。基于 `analysis/` 的 19 份报告与 `temp/go-music-dl` 的本地服务范式。
> **范围**：本文只定义 v1 客户端技术栈。FastAPI 后端、用户观测上报、服务端种子分发均为
> **v2 之后的议题**，本文不涉及，也不为其预留代码或目录。
> **已定**：平台 = Android + iOS；UI = Flutter + Dart；数据引擎 = 内嵌 Go 服务；
> 首版数据 = 内置种子（基线）+ 详情页进入即抓（增量更新）；架构 = 前后端分离但同处一个 App 进程。
> 搜索 = 本地索引 + 官方双接口三层合并，命中即收录（§4.5）。
> **分发**：iOS 由用户自签安装，**不上架 App Store**；Android 走常规 APK。
> 因此 App Store 审核口径不构成约束，但 iOS 沙盒（禁 fork/exec 外部二进制、回环 HTTP 的 ATS 例外）
> 自签后依旧成立——两者不可混为一谈。
> **口径依据**：数据来自 `analysis/out/novels.csv`（245,779 行 × 15 列，剔除正版日轻后），
> 内容上界 **2026-05-03**（原始 jsonl 的 `max(last_update)`，即扫描起点，非统一读取时刻）；
> 上架年由 nid 定年（104 锚点，LOO P99 = 50 天）；对在架书覆盖率约 68.9%。
> 凡引用早期档案或 go-music-dl 的数字，均标注来源与口径，不作为当前实测结论。

## 1. 架构：前后端分离，同处一个进程

借鉴 `temp/go-music-dl` 的成熟范式，但按 Flutter 技术栈调整进程形态。

```
App 进程
├── Flutter UI（Dart）
│   ├── Riverpod 状态 / go_router / CustomPainter
│   └── 只通过 HTTP 调 localhost 引擎，不直接碰 SQLite
│
└── 内嵌 Go 引擎（in-process）
    ├── Gin HTTP 服务：127.0.0.1:<port>
    ├── 爬虫层：限速、重试、UA、Cookie、解析器（纯函数）
    ├── 存储层：SQLite（种子导入 + 爬虫写入 + 榜单查询）
    └── 启动期：就绪握手，UI 轮询 /healthz 后再进入主界面
```

### 1.1 为什么是 in-process 而不是独立子进程

go-music-dl 用 Gio 把**整个 App 编译成 Go 程序**，Go 运行时就是主进程，
因此它可以直接 `go web.StartDesktop()` 起 HTTP 服务。
我们的 UI 是 Flutter，主进程是 Dart——**iOS 禁止 App fork/exec 外部二进制**，
无法在 iOS 上起一个独立的 Go 子进程。

因此 Go 引擎以**库形式嵌入同一进程**：

- 编译为 C archive（iOS）或 C shared library（Android），Dart 经 `dart:ffi` 调用启动函数
- HTTP 服务在 Go 运行时的 goroutine 内运行，监听回环地址
- Android 虽可起独立进程，但为两端一致，**统一走 in-process**
- 代价：Go 与 Dart 共享内存与生命周期，崩溃会互相影响；收益：无跨进程数据拷贝，
  符合 iOS 沙盒对可执行文件的限制（自签不改变这一限制），双端架构一致

> 需验证：`dart:ffi` 调 Go C-archive 在 iOS 真机的可用性与包体增量。这是 v1 的第一技术风险。
> 因不上架，若 spike 失败可退到「Go/Gio 主进程 + WebView UI」完整复刻 go-music-dl，
> 无需承担上架审核成本——这是自签带来的额外回退空间，但不改变 FFI 本身仍需验证。

### 1.2 启动握手（沿用 appshell 模式）

go-music-dl 的 `internal/appshell/server.go` 给出可直接照搬的协议：

1. UI 触发 Go 引擎启动（FFI 调用），引擎在 goroutine 中监听回环端口
2. UI 以 200ms 间隔轮询 `/healthz`，**15 秒超时**
3. 就绪后进入主界面；失败时展示带诊断信息与重试的页面，**不无限重载**
4. 端口：优先动态分配（`127.0.0.1:0`，引擎回报实际端口），固定端口作降级

## 3. 端上爬虫：数据新鲜度的主通路

**种子必然落后于实际值**——它是构建期快照（内容上界 2026-05-03），发布那一刻就开始过期。
因此 v1 不把种子当「当前状态」，只当**基线**：用户每次进入详情页，引擎就抓取该书详情并写回本地库。
用得越多，这台设备上的数据越准。这不是补全功能，而是 v1 唯一的增量更新机制。

| 维度 | v1 规则 |
| --- | --- |
| 触发方式 | **进入详情页即触发**（唯一主通路）；从搜索、榜单、书架点进同一条路径。不做后台批量定时 |
| 请求速率 | 全局限速器在 Go 侧统一实施（每设备每秒上限 + 单日上限）；同书并发请求合并 |
| 去重 | 同一本书在短窗口（初值 30 秒）内重复进入只发一次请求，窗口内二次进入读本地值 |
| 目标 | 用户实际打开的每一本；未收录书首次进入即抓取补全，不从头扫全库 |
| 写入 | Go 侧单事务：更新该书最新值 + 追加一条观测记录；UI 不直接写库 |
| 解析 | 纯函数 parser，配套 golden test；接口变更时先改测试 |
| 失败 | 结构化错误；**UI 回落本地已有值并标注数据时间**，不显示空白或「不存在」 |
| 数据时间 | 种子值与本地抓取值**分别标记来源与 `observed_at`**，UI 可区分 |

> 限速器排队时**详情页请求优先**，队列设上限（超出直接丢弃而非积压）——
> 用户快速翻书时宁可少刷几本，也不让请求无声堆积。

### 3.1 种子只读随包，用户数据独立成库

**种子是随安装包分发的只读副本**——覆盖安装（升级）会整包替换它，写入会在下一次安装时消失。
这不是靠「小心不要覆盖」能规避的实现细节，而是分发方式决定的硬约束。因此本地是**两份物理库**，
不是一份库里的两张表：

| 文件 | 位置 | 权限 | 覆盖安装 |
| --- | --- | --- | --- |
| `seed.db.gz` | App bundle / assets（压缩包） | **只读** | 被整包替换 |
| `seed.db` | 数据目录 `seed/seed-<version>.db`（解压副本） | **只读打开** | 按版本比对替换 |
| `user.db` | 应用数据目录（iOS `Application Support`、Android `filesDir`） | 读写 | **保留** |

- `seed.db`：**扁平单表 `books`（20 列）+ 反范式 `book_tags`**（报告 18 实测定案）；
  索引 4 个（`idx_favs` / `idx_year` / `idx_author` / `idx_bt`）；
  **不建** `tags`/`authors`/`contests` 维度表（低基数枚举，拆表只增 JOIN 与体积）；
  `rank_snapshots` / `banner` 作为独立资产随包分发而非建表。构建期产出，运行时只 SELECT
- `user.db`：`observations`（只追加）、书架、标注、搜索历史，**永不随安装替换**
- 查询：`ATTACH DATABASE ... AS seed` 跨库 join；同一字段取 `observed_at` 较新者

**跨库关联只能用 `nid`（书的稳定 id），不能用 rowid**——种子重发后 rowid 会重排，
而观测必须跨种子版本继续挂在同一本书上。

两个附带结论：种子裁剪掉某本书时，它的观测仍在 `user.db`，用户打开过的书不会凭空消失；
观测与基线不混一列，UI 才敢标注「种子快照 / 本地刷新于 X」而不撒谎。

**但删书不是需要设计的场景**。种子源头本身是从第三方抓取、已缺失大量数据的集合
（对在架书覆盖率约 68.9%，遗漏偏短、新、更新中），再按「用户高概率需要」筛选一遍，
实际演化只会增补与刷新数值，几乎不会移除。因此 v1 不为「种子删书」写迁移逻辑——
观测保留只是上述结构自然产生的结果，不是需要额外维护的特性。

这还带来一个种子给不了的能力：**同一本书的本地时间序列**。分析结论是累计指标跨书、
跨世代不可比（报告 02、08），但同一本书的纵向对比是有效的——`observations` 表让
「这本书最近 30 天收藏涨了多少」成为可回答问题。

### 3.2 能力边界（必须写清，不做过度承诺）

- 冷门书只在被打开时刷新；没人打开的书停留在种子基线，不会自动变新。
- 单设备准度取决于使用路径，不是「全库实时」。
- 详情页只给该书自身的当前值；榜单排名与同期对照仍来自种子。
- 请求量随用户数线性增长——**限速在引擎层强制**，不靠调用方自觉。这是生存约束，不是性能优化。

## 4. 逐层选型论证

### 4.1 UI：Flutter 3.x / Dart 3

- UI 表现力与双端一致：原生 widget、动画、CustomPainter 分位带。
- 状态用 Riverpod：localhost API 的异步结果、种子就绪状态、用户标注三路汇入。
- 只做呈现与交互，**不持有数据、不直接访问 SQLite**——数据所有权归 Go 引擎。
- 详情页必须呈现**数据来源与时间**（种子快照 / 本地刷新于 X 分钟前），这是数据可信度的一部分，不是装饰。

### 4.2 引擎：内嵌 Go 服务

- 爬虫生态成熟：net/http、超时控制、Cookie、限速、重试、并发队列都有现成做法。
- 解析器是纯函数，Go 侧 `go test` 可直接覆盖；这是数据可信度的基础。
- 参照 go-music-dl 的分层：`core/`（业务与解析）、`internal/web/`（HTTP 路由）、
  自研 `appshell` 对应层（启动与就绪握手）。
- **许可证已兼容**：本项目与 go-music-dl 同为 AGPL-3.0，工具层代码（限速器、重试、
  启动握手、数据目录解析）可直接移植，须保留原作者版权声明并以 AGPL-3.0 分发。
  仍**不复制其音乐业务逻辑**——域不同（音乐检索 vs 书目分析），无可复用价值。

### 4.3 通信：localhost HTTP

- UI 与引擎的唯一边界；所有数据访问走 HTTP API，接口可独立测试。
- 仅监听 `127.0.0.1`，不对外暴露；接口不提供配置/鉴权等敏感能力给 UI 之外的调用方。
- 沿用统一 RoutePrefix（如 `/strata`），便于未来加代理或测试。
- 错误RESPONSE结构化，UI 按错误码渲染。

### 4.4 存储：Go 侧 SQLite

- **两份物理库**（见 §3.1）：`seed.db` 随包只读、`user.db` 在应用数据目录可写。
  Go 侧同时持有两个连接，`ATTACH` 做跨库查询；种子升级只替换前者的文件。
- **种子落地方式**：`seed.db.gz` 随包（iOS bundle / Android assets）。SQLite 无法直接打开 Android
  assets 内的文件，故首次启动或版本变更时解压到数据目录 `seed/seed-<version>.db`，
  以包内 `manifest.json` 的版本号与库内 `seed_meta.version` 比对决定是否替换，成功后删除旧文件。
  **替换是整文件换名，不做增量 UPDATE**——这是「种子只读」的落地形态；
  解压副本不会随覆盖安装自动刷新，版本比对是唯一保险。
- schema 从 §2 的九条约束反推，至少包含 `books`（含 `est_year` 与分位）、
  `tags`（含词表版本）、`banner`（含下注/奖励类型）、`rank_snapshots`、`seed_meta`（含上界与生成时间）。
- **`observations` 表**（在 `user.db`）：`nid + observed_at` 为键，存详情页抓回的 clicks/favs/praises/words/status。
  写入只追加，种子升级不触碰；查询时与 `books` 按 `observed_at` 取新。
  索引按 `(nid, observed_at DESC)`，保证详情页读取是单次索引查找。
  主键用 `nid` 而非自增 rowid，理由同 §3.1：要能跨种子版本续挂。
- **`discovered` 表**（在 `user.db`）：搜索命中但种子未收录的书，见 §4.5。
  只承载目录字段（标题/作者/分类/评分/简介/封面/`source`/`observed_at`），`est_year` 与分位为空，
  **不参与任何统计查询**——它与 `books` 是「目录条目」与「统计样本」的区别。
- **不做 FTS5**：种子规模小，内存索引（标题/作者/拼音首字母）足够；
  FTS5 对中文两字词的 trigram MATCH 有已知失效（早期实测）。
- 用户数据（书架/标注/搜索历史）全部在 `user.db`，与种子升级完全隔离；
  覆盖安装不会丢，卸载才会。

### 4.5 搜索：三层复合，命中即收录

本地只有种子 + 用户打开过的书，必然搜不全；官方搜索是唯一能覆盖全库的入口。
所以搜索不是「本地或官方」二选一，而是三路合并：

| 层 | 来源 | 延迟 | 作用 |
| --- | --- | --- | --- |
| L0 联想 | 本地前缀索引（0ms）→ 官方 `op=searchreffer`（~150ms） | 即时 | 输入过程中补全书名 |
| L1 本地 | `seed.db` + `user.db`，标题/作者/拼音首字母内存索引 | 0ms | 有统计与分位的书 |
| L2 官方 | HTML 全量 + JSON 评分，按 `NovelID` 合并 | 200–500ms | 本地没有的书 |

**两个官方接口字段互补，缺一不可**（2026-11-16 复核，实测关键词「英雄」）：

| 接口 | 返回 | 条数 | 独有字段 |
| --- | --- | --- | --- |
| `GET s.sfacg.com/?Key=&SS=0&S=1` | HTML | **全量**（实测 29 条） | 简介、`last_update`、封面 |
| `GET m.sfacg.com/API/HTML5.ashx?op=search&keyword=` | JSON | **固定 12 条，无分页**（`page`/`pi`/`p`/`PageIndex` 均无效） | `Point` 评分、`TypeName`、`Tags` |
| `POST m.sfacg.com/API/Book.ashx?op=searchreffer` | JSON | 15 条 | `keywords[]` 完整书名 |

只取 JSON 会漏掉一半结果且没有简介；只取 HTML 会没有评分——这正是必须合并的原因。
另需注意 HTML 页是 ASP.NET WebForms（带 `__VIEWSTATE`），字段靠解析而非契约，
因此解析器要按 §3「纯函数 + golden test」维护，接口改版先改测试。

> 接口清单来自 `temp/sfacg_tools/sfacglib/search.py`；`docs/search.md` 存有 2026-11-15 的完整实测记录
> （仅其接口边界仍有效，其中的书目数字属旧口径，不复用）。

**命中即收录**：L2 返回而本地没有的书，写入 `user.db` 的 `discovered` 表
（`nid`/标题/作者/分类/评分/简介/封面/`source`/`observed_at`），下次本地即可搜到。

> **收录 ≠ 进入统计**。这些条目没有定年、没有历史指标、没有分位（`est_year` 为空），
> **不参与榜单排序与世代统计**，UI 单独标注「官方目录，无统计数据」。
> 理由与分析口径一致：累计指标必须同世代/同期比较（报告 02、08），
> 把搜索结果直接并进 `books` 会让分位被无基线样本污染。

合并规则：A 组（本地有）按用户当前维度排序，B 组（仅官方）按相关度附后；
两者按 `NovelID` 去重（官方两个接口自身也会返回重复）。本地与官方都无结果时，
明说「官方也未收录」并给近似建议，不假装存在。

### 4.6 图表与测试

- 核心可视化是分位带、世代对比、时间轴断点，CustomPainter 定制；常规图用 fl_chart。
- 配色沿用 `analysis/charts.py` 的分期色板，保证报告与 App 视觉一致。
- 测试分两层：Go 侧解析/服务 `go test`；Dart 侧 UI widget test + 集成测试。

| 早期稿 / go-music-dl | v1 方案 | 原因 |
| --- | --- | --- |

## 6. v1 明确不做

- **不做服务端**、不做用户观测上报、不做服务端种子分发（v2 之后另行设计）
- **不做后台批量爬虫**，不做全库 7 天轮转；爬虫只在前台按用户触发
- **不内置全库**，不做本地全库离线搜索
- **不做 FTS5**、不做同义词标签合并、不做跨世代绝对数排名
- **不做用户系统**、登录、书架云同步
- **不上传搜索词**：搜索只在本地与官方接口之间发生；未命中记录只留本地（v2 若做观测也只报书 id，不报关键词）
- **不做 App Store 上架适配**：iOS 走用户自签，不为审核裁剪本地 HTTP 服务与爬虫能力
- **不复制 go-music-dl 的音乐业务代码**（域不同，无可复用价值）；其工具层可在 AGPL-3.0 下直接移植

## 8. 待决问题

1. **FFI 可行性**（最高优先级）：`dart:ffi` 调 Go C-archive 在 Android/iOS 真机的可用性、
   包体增量、调试方式——需先做 spike 验证，失败则回退到 MethodChannel + 平台原生库。
2. **种子书单口径**：榜位闭包 top200 / 标签闭包 / banner 全集并集，需按新数据重算本数与体积。
   原则是「用户高概率需要」而非覆盖全库——种子既非全量，也不追求全量；删书按低概率事件处理，不做迁移设计。
3. **分位计算时机**：构建期预计算写入种子，还是 Go 侧查询时实时算——影响 schema 与性能。
4. **爬虫接口清单**：详情页抓取的端点、字段映射（clicks/favs/praises/words/status/last_update）、
   限速阈值——单独一篇设计文档。
5. **观测历史保留策略**：`observations` 永久保留、按季度聚合裁剪，还是只留最新 N 条——
   直接决定库体积增速（进入详情页即抓，写入频率与使用强度同阶）。
6. ~~iOS 分发合规~~ **已关闭**：iOS 由用户自签、不上架，App Store 审核口径不再适用。
   但 `NSAllowsLocalNetworking` 仍须在 Info.plist 开启——这是回环明文 HTTP 的**运行时 ATS 要求**，
   与审核无关，真机验证仍列入集成测试。
7. **`discovered` 条目治理**：何时刷新（暂定仅在该书再次被搜索命中时更新）、容量上限、
   长期未命中的条目是否降级或清理——只增不减会拖慢索引构建。

## 附录 A：从 go-music-dl 借鉴什么

参考实现：`temp/go-music-dl`（AGPL-3.0，与本项目同许可）。**工具层可移植，业务层不复制**：
限速器、启动握手、动态端口、数据目录解析等基础设施可直接搬用，
须在其文件保留原始版权声明、并在本项目 `LICENSE`（AGPL-3.0）下分发；
音乐检索相关的业务与解析代码与本产品域不同，不复用。下表逐组件说明取舍。

| 组件（源文件） | 处理 | 说明 |
| --- | --- | --- |
| 启动握手 `internal/appshell/server.go` | **可移植** | 200ms 轮询 `/healthz`、15s 超时、就绪后导航、失败诊断页不无限重载 |
| 动态端口 `cmd/music-dl/search_server.go` | **可移植** | `net.Listen("127.0.0.1:0")` 取实际端口回报 UI；固定端口作降级 |
| 数据目录 `desktop_go/data_paths.go` | **可移植** | 固定到用户配置目录、绝对路径环境变量、绕开 cwd 只读 |
| 限速与 Cookie `core/service.go` | **可移植** | 集中式限速器与并发安全 Cookie 管理可直接搬；目标端点与解析按我们的需求写 |
| 纯函数解析 + 大量 `*_test.go` | **照搬纪律** | 解析器可独立单测，接口变更先改测试；golden test 覆盖 |
| Gin + 统一 RoutePrefix | **可移植** | 单一路由前缀，接口可独立测试，不散落 |
| iOS ATS 配置 `package_ios.sh` | **借鉴约束** | `NSAllowsLocalNetworking` 必开（自签也需要的运行时 ATS 例外）；`NSAllowsArbitraryLoadsInWebContent` 我们不用 WebView，按需评估 |
| 前后端分离理念 | **借鉴模式** | 数据所有权在后端，前端只消费 API——本项目的核心理由 |
| Gio / WebView 壳 `desktop_app/` | **不用** | UI 已定 Flutter；原生桥换成 `dart:ffi` |
| WebView 桥接、AI 播放器控制 | **不用** | 与本项目无关 |
| Rust/Tao/Wry 桌面壳 `desktop/` | **不用** | v1 只做 Android + iOS |
| 音乐搜索/下载/播放/歌词业务 | **不用** | 从头实现 SFACG 书目爬虫与解析器 |
| 多客户端 `client_id` 定向 | **不用** | 单机单客户端，无并发多端控制需求 |

> 一句话：拿它的**骨架**（内嵌服务、就绪握手、集中限速、固定数据目录、测试纪律），
> 不拿它的**血肉**（音乐业务、WebView 壳、播放器控制）。
