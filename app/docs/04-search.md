## 0. 结论

**一句话**：搜索的骨架不变（本地 + 官方三层合并），但**「官方搜索能覆盖全库」这个前提是错的**——
它硬截断在 30 条，因此本地种子从「方便」升级为「不可替代」，自动收录的收益从「主要来源」
降级为「边际补充」。

| 结论 | 依据 |
| --- | --- |
| 1. 官方搜索是 **≤30 条截断检索**，且声明的命中数也是截断值 | 实测搜单字「的」声明 28 条，库内标题含「的」有 98,793 本（§2.1） |
| 2. **官方搜索不能枚举、不能翻页**，六种分页参数全部无效 | `Page`/`page`/`pi`/`PageIndex`/`PageSize` 返回与基准完全相同的结果集（§2.1） |
| 3. 但**官方目录可以枚举**——`op=novelbytype` 支持深翻页 | 九类 42,568 页 = **255,408 个目录槽位**，实际返回 221,354（13% 槽位被跳过，§7.1） |
| 4. 宽泛词检索**必须靠本地**：种子覆盖「少女」2,338 本，官方只给 29 本 | 官方可见比例 0.03%–2.25%（§2.2） |
| 5. 精确书名**官方 12/12 命中**，是「找已知书」的可靠通路 | 12 个随机书名逐个实测（§2.3） |
| 6. 自动收录的真实收益是**每条官方结果中约 9.2% 在库外** | 8 个关键词 217 条结果，库外 20 条（§5） |
| 7. HTML 搜索有**静默限流**：HTTP 200 + 「请输入关键字」+ 0 结果 | 连打 17–18 次触发，>3 分钟未恢复（§8） |

**四条不可协商的规则**：

1. **不得向用户承诺「搜遍全站」**。官方只给 30 条，本地只有种子。UI 文案只能是
   「找到 N 本」而不是「共 N 本」，**任何地方都不出现「总共/全部」字样**。
2. **本地优先于官方**，但不是因为快，而是因为**本地更全**——宽泛词下本地命中比官方多 80 倍。
3. **官方结果不进统计**。`discovered` 条目无定年、无分位，不参与任何榜单（03 §1.2、02 §3.2）。
4. **静默限流必须显式识别**。用「结果为空」判断成功会把限流当成「没有这本书」，这是最坏的失败。

## 1. 口径声明

### 1.1 三个官方接口的能力边界（实测于 2026-11-16）

| 接口 | 条数 | 分页 | nid | 简介 | 评分 | 分类 | 更新时间 | 限流 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| HTML `s.sfacg.com` | **≤30** | ✗ | ✓ | **✓** | ✗ | ✗ | ✓ | **有（静默）** |
| JSON `op=search` | 6–15 | ✗ | ✓ | ✗ | **✓** | ✓ | ✗ | 未触发 |
| 联想 `op=searchreffer` | 15 | ✗ | **✗** | ✗ | ✗ | ✗ | ✗ | 未触发 |

**三者不可替代**：简介只在 HTML，评分与分类只在 JSON，联想词只给书名不给 nid。
完整字段表与选择器见 [`sfacg-endpoints.md`](../../analysis/references/sfacg-endpoints.md) §2、§4。

### 1.2 候选池口径

| 层 | 候选池 | 规模 | 时间基准 |
| --- | --- | --- | --- |
| L1 本地 | 种子 + `discovered` + 书架 | 30,794 本（29,396 + 短篇 1,398，见 §2.2 注）+ 用户累积 | 内容上界 2026-05-03 |
| L2 官方 | 官方相关度排序的前 30 | ≤30 | 实时 |

**L2 的候选池是全站，但每次只返回 30 条**——这是「全站」与「可检索全站」的区别，
也是本文所有设计约束的根源。

### 1.3 与 01 §4.5 的差异

01 §4.5 写的「HTML 全量（实测 29 条）」是**误判**：29 条不是「这次刚好命中 29 条」，
而是「上限 30，本次返回 29 条」。同表另写「JSON 固定 12 条」也不准确（实测 6–15 条）。
两处均已由 2026-11-16 实测更正，**以本文与 `sfacg-endpoints.md` 为准**。

## 2. 核心命题：官方搜索不是全库检索

这不是接口缺陷，是站方产品选择——搜索面向「我知道要找什么」的用户，
不面向「我要看这类书」的用户。后一种需求站方用分类页与榜单承接。

### 2.1 上限是硬的

| 关键词 | 官方声明 | 官方返回 | 库内标题命中 | 官方可见比例 |
| --- | --- | --- | --- | --- |
| 魔法 | 28 | 28 | 4,210 | **0.66%** |
| 重生 | 30 | 30 | 4,357 | **0.69%** |
| 少女 | 29 | 29 | 10,813 | **0.27%** |
| 转生 | 30 | 30 | 4,593 | **0.65%** |
| 英雄 | 29 | 29 | 1,270 | **2.28%** |
| 的 | 28 | 28 | 98,793 | **0.03%** |

**「共搜索到 N 个结果」的 N 是被截断的数**——搜「的」时它说 28 条，
而站内标题含「的」的书近 10 万本。**因此无法得知任何关键词的真实命中总量**，
也就不能写「共找到 4,210 本，显示前 28 本」这类文案（那个 4,210 只有我们有，官方没有）。

**六种分页参数全部无效**（关键词「重生」，基准首条 nid `506050`）：
`Page=2`、`page=2`、`pi=2`、`PageIndex=2`、`PageSize=50` —— 返回条数 30、首条 `506050`、
结果集与基准**完全相同**。

### 2.2 所以宽泛词必须靠本地

种子池（29,396 + 短篇补入 1,398 = **30,794** 本）对宽泛关键词的覆盖
（现算，`est_year ∈ 2007–2025`，统计基数 241,758 行）：

| 关键词 | 种子内命中 | 全库命中 | 种子覆盖 | 官方最多 | **本地/官方** |
| --- | --- | --- | --- | --- | --- |
| 魔法 | 749 | 4,210 | 17.8% | 28 | **26.8×** |
| 重生 | 868 | 4,357 | 19.9% | 30 | **28.9×** |
| 少女 | 2,338 | 10,813 | 21.6% | 29 | **80.6×** |
| 转生 | 980 | 4,593 | 21.3% | 30 | **32.7×** |
| 英雄 | 137 | 1,270 | 10.8% | 29 | **4.7×** |
| 剑 | 494 | 3,641 | 13.6% | 30 | **16.5×** |

> 本表口径：种子 = 报告 18 的 29,396（`NEW_CUTOFF=2025-05-04`、`ACTIVE=2026-02-03`）
> ∪ 报告 19 的短篇补入 1,398。**02 文档记的 30,831 与本表的 30,794 差 37 本**——
> 差额来自报告 19 内部复刻种子时用的边界（`2025-05-03`/`2026-02-02`）比报告 18 早一天。
> 37 本对覆盖率的量级无影响（<0.1 pp），但**种子构建器必须只取一个边界**（02 §5.1）。

**这是本文最重要的一张表**。它说明：用户搜「少女」时，本地能给 2,338 本带分位的书，
官方只给 29 本不带任何成绩的书。**把官方结果排在前面是产品错误**。

同时也给出诚实的边界：种子对宽泛词只覆盖全库的 10.8%–21.6%，
**所以「找全」这个承诺无论如何都给不出**——只能给「找到这些」。

### 2.3 精确书名是官方的主场

12 个随机书名（长度 6–14 字）逐个实测：**12/12 命中，且全部排在第 1 位**。

| 书名 | 官方返回 | 自命中 | 排位 |
| --- | --- | --- | --- |
| 金龙璃月：我乃创世之主 | 1 | ✓ | 1 |
| 恶劣的百合花 | 1 | ✓ | 1 |
| 有我在，你放心 | 1 | ✓ | 1 |
| 新世纪的嘲弄 | 1 | ✓ | 1 |
| （另 8 个同类） | 1 | ✓ | 1 |

所以官方的真实能力是：**「我知道书名，帮我找到它」——这一件事它做得比本地好**
（本地只覆盖种子；官方覆盖全站）。这也是 L2 存在的唯一理由。

> 注意这与早期档案的「官方库也有遗漏」不矛盾：那次遗漏的是**老书**
> （`53831` 退役英雄的我现在正带着孩子，2017 年上架）。本次 12/12 是**书名精确匹配**场景，
> 命中的都是书名完整、无特殊标点的条目。含全角标点的长书名命中率低，需在回归测试里覆盖。

### 2.4 对产品命题的改写

| 原命题（01 §4.5） | 修正后 |
| --- | --- |
| 「官方搜索是唯一能覆盖全库的入口」 | 「官方搜索是唯一能触及库外书的入口，但每次只给 30 条」 |
| 「11,442 本种子 + 官方搜索 = 全库搜索体验」 | 「种子 + 官方 = **两类不同检索**的并集，不是全库」 |
| 搜索定位 | 从「全库检索」改为「**已知书名找书 + 库内宽泛检索**」 |

**「发现新书」不靠搜索**，靠榜单与标签浏览（03 的 A/B 类榜）。
搜索是**收敛**工具，不是**发散**工具——这个定位必须在 UI 上体现（§9.3）。

## 3. 三层架构

```
用户输入
  │
  ├─ L0 联想（本地 0ms → 官方 ~293ms，二选一而非并集）
  │   本地：种子标题前缀 + 拼音首字母
  │   官方：op=searchreffer → 15 个完整书名（无 nid，仅用于补全输入）
  │
  ├─ L1 本地（<5ms，同步渲染）
  │   seed.db + user.db(discovered/shelf) 内存索引
  │   → 带分位、带成绩、带世代，可直接进榜单视图
  │
  └─ L2 官方（212–314ms，异步追加）
      HTML（简介+更新时间） ∪ JSON（评分+分类），按 nid 合并
      → 库内书：用官方值刷新本地缓存，不改变排序
      → 库外书：追加为「官方目录」分组，并写 discovered
```

### 3.1 L0 联想：本地与官方二选一

**不合并**。理由是两者回答不同问题：本地联想答「我搜的词在库里能搜到什么」，
官方联想答「站内存在哪些含这个词的书名」。合并会让用户看到一堆点不进去的书名。

| 输入状态 | 用哪个 | 原因 |
| --- | --- | --- |
| 本地命中 ≥3 条 | **只用本地** | 0ms，且结果可点进详情 |
| 本地命中 0–2 条 | 本地结果 + 官方联想（标注「站内有」） | 补全用户可能记错的词 |
| 用户已停止输入 400ms 且本地 0 命中 | **只发官方联想** | 省一次请求 |

官方联想词**必须去重**：实测「英雄」15 条中，「英雄再临(英雄？我早就不当了)」与
全角括号版本、「拜托请不要再找我当超级英雄了」与自身完全重复——
规范化全/半角后按书名去重，15 条剩 13 条。

### 3.2 L1 本地：内存索引

沿用 02 §4.3 的实测结论，不重复论证：建索引 17.7 ms、精确查 0.07 µs、
前缀扫描 3.89 ms（v1 已知性能债，v2 换有序数组二分）。

**新增一条口径**：索引必须同时覆盖 `seed.db.books` 与 `user.db.discovered` + `shelf`，
但**两者的排序键不同**——见 §4。

### 3.3 L2 官方：两个接口必须合并

| 场景 | HTML 贡献 | JSON 贡献 |
| --- | --- | --- |
| 库内书 | 刷新 `last_update`、补简介 | 补 `Point` 评分、校正 `TypeName` |
| 库外书 | **唯一能给出简介的来源** | 唯一能给出评分的来源 |

**只用 JSON 会丢 17/29 条结果**（实测「英雄」HTML 29 条、JSON 12 条，JSON 全部包含在 HTML 中）。
**只用 HTML 会完全没有评分**。

**合并键是 `NovelID`**，且**不能假设 JSON 是 HTML 的前 12 条**——
实测 JSON 的 12 条在 HTML 中的位置是 `0,1,2,…,10,13`，第 12 条（索引 13 的 `124218`）
跳过了 HTML 第 12 位。两接口排序规则不完全一致，必须按 nid 做集合运算，不能按位置切片。

### 3.4 并发与超时

| 项 | 规则 |
| --- | --- |
| 发射时机 | L1 渲染完成后立即发（不阻塞首屏） |
| 并发 | HTML 与 JSON **串行**，间隔 ≥800ms |
| 超时 | 单请求 8s；两接口合计预算 12s |
| 失败降级 | HTML 失败 → 只用 JSON（12 条、无简介）；两者皆失败 → 保留 L1 + 提示网络问题 |

**为什么串行**：两个接口在同一域名族下，并发会加速触发静默限流（§8）。
串行的代价是首屏结果慢约 250ms，但 L1 已经在屏幕上，用户感知不到。

## 4. 合并与排序

### 4.1 三个分组，不能混排

| 组 | 条件 | 排序键 | 展示 |
| --- | --- | --- | --- |
| **A 已收录** | 命中 `seed.db.books` | 用户当前维度（分位/收藏/字数…） | 全字段 + 分位带 + 世代标签，可进榜单视图 |
| **B 本机新增** | 命中 `user.db.discovered` 或 `shelf` | `observed_at` 倒序 | 全字段但**无分位**，标注「本机收录」 |
| **C 官方目录** | 仅在官方结果中 | 官方相关度（跟随接口顺序） | 书名/作者/评分/简介/封面，标注「站内，无统计」 |

**A 与 B 可合并排序，C 必须单独成组**。理由：A/B 都有成绩与分位（同参照系），
C 什么都没有。把 C 插进 A 的排序里，等于让「无数据的书」占据「按成绩排序」的位置。

### 4.2 默认排序：A+B 按维度，C 附后

默认视图 = A+B 按用户当前维度降序，C 组折叠为「站内还有 N 本相关」的**可展开条目**，
不默认展开。展开后 C 内部按官方相关度排序（不重排——我们没有 C 组的任何可比值）。

**提供一键切换「按相关度」**：此时 C 组提前，A/B/C 按官方顺序混排，
用于「我记得书名大概是什么」的场景。切换开关的状态**不持久化**——
每次新搜索回到「按成绩」，因为这是本产品的默认命题。

### 4.3 与 03 榜单排序的一致性

03 §9 要求本文回答这一点。答案：

| 场景 | 排序依据 | 与榜单是否一致 |
| --- | --- | --- |
| A 组按收藏 | `fav_pctl`（世代内分位） | **一致**——与「同世代收藏分位榜」同一字段、同一参照系 |
| A 组按字数 | `words` 绝对值 | 一致，但**须标注「非成绩」**（03 §5.2） |
| A 组按赞藏比 | `pr` 预计算列 | 一致，但须 `favs ≥ 10` 才显示（03 §4.2） |
| 短篇筛选 | `words ≤ 50,000 且 status='已完结'` | **一致**——必须走部分索引 `idx_shortfav`（02 §2.3） |
| B/C 组 | 无分位 | **不参与任何榜单** |

**「搜索结果里按收藏排序」与「收藏榜首屏」是同一口径**，不会出现「搜索里排第一、榜上排第 300」的
矛盾——因为两者都用 `fav_pctl` 而非 `favs` 绝对值。这是 03 §1.2「分位以全库为参照系」
在搜索侧的直接兑现。

> **一处必须显式标注的不可比**：A 组按 `fav_pctl` 排序时，2010 世代的书会与 2020 世代的书
> 相邻出现，而两者绝对值可能差 20 倍（03 §2）。搜索结果**必须显示世代标签**，
> 否则用户会以为「分位 0.98 的 2010 书」和「分位 0.98 的 2022 书」是同等热门。

## 5. 自动收录

### 5.1 真实收益：9.2% 在库外

8 个关键词、217 条官方结果，与 245,779 行全库比对：

| 关键词 | 官方返回 | 在库 | 库外 | 库外率 |
| --- | --- | --- | --- | --- |
| 英雄 | 29 | 27 | 2 | 7% |
| 魔法 | 28 | 25 | 3 | 11% |
| 少女 | 29 | 28 | 1 | 3% |
| 转生 | 30 | 30 | 0 | 0% |
| 重生 | 30 | 30 | 0 | 0% |
| 修仙 | 29 | 28 | 1 | 3% |
| 学院 | 29 | 22 | 7 | **24%** |
| 悬疑 | 13 | 7 | 6 | **46%** |
| **合计** | **217** | **197** | **20** | **9.2%** |

**这说明两件事**：

1. **收录是有真实增量的**：约每 10 条官方结果就有 1 本是数据集没有的。
   但这 20 本里同样混着快照后上架的新书（§7.1 的拆分表明「库外 ≠ 漏抓」），
   所以**它是「补新」通路，不是「补漏」通路**——真正的存量缺口按 0.47% 算只有千本量级。
2. **但收录的绝对量很小**：每次搜索最多 30 条结果，期望新增 ≈ 2.8 本。
   按 02 §3.2 的 `discovered` 单行体积，一年累积对数据库体积无实质影响。

**所以「搜索即采集」的定位要降级**：它不是数据增长的主要通路（那是详情页抓取，归 05），
而是**补上「用户明确表达过兴趣、但我们恰好没有」的书**——这些书的收录优先级最高，
因为它们已经被真实需求验证过。

### 5.2 写入规则

| 项 | 规则 |
| --- | --- |
| 触发 | 仅当官方结果中的 nid **不在** `books` 且**不在** `discovered` 时写入 |
| 字段 | 只写接口实际返回的：`nid/title/author/genre/summary/cover_url/source/observed_at` |
| `words`/`favs`/`praises` | **留 NULL**，不猜。HTML 搜索不返回成绩，JSON 也不返回 |
| `source` | `html` / `json` / `both`（两接口都命中同一 nid 时写 `both`） |
| 更新 | 同一 nid 再次被搜到：**只更新 `observed_at` 与仍为空的可选字段**，不覆盖已有值 |
| 容量 | 无硬上限。但 `discovered` 行数超过 **5,000** 时，按 `observed_at` 最旧优先清理从未被打开过的条目（`shelf` 与 `observations` 里出现过的永不清） |

### 5.3 收录 ≠ 进入统计（重申 02 §3.2）

`discovered` 的条目**没有 `est_year`、没有分位、没有历史指标**，
因此：

- **不进入任何榜单**（03 §4.1–4.8）；
- **不参与分位分母**（分位在全库固定集合上算，加进来会改分母，02 §5.1 规则 1）；
- 搜索结果里作为 B 组展示，**但排序键是 `observed_at` 而非任何成绩**；
- 详情页可进入（触发 05 的抓取），抓到的成绩写入 `observations`，
  **但仍不进 `books`**——`books` 是种子内容，运行时不可写（01 §3.1）。

**一个例外必须写清**：若用户在设置里「重建索引」，`discovered` 条目不参与重建，
否则每次重建都会产生不同的搜索结果集。

## 6. 官方结果的质量边界

用户看到 C 组时，会默认「官方返回的书是相关的」。实测这条不成立：

- **官方不按成绩排序**。搜「英雄」时第 6 条（`651053`，614 万点击）排在第 5 条
  （`111608`，429 万点击）之后——前 4 条严格递减，之后打乱。是**相关度**排序。
- **官方结果含「非本类」内容**。搜「悬疑」只返回 13 条，其中 6 条在库外；
  搜「学院」29 条里 7 条库外——说明官方对分类词的处理是「标题里出现该字样」，
  不是「该分类下的书」。

**产品含义**：C 组不能展示成「这些是你要找的书」，只能展示成「**站内还有这些**」。
UI 用中性措辞，不给相关度背书。

## 7. 全库枚举：构建期工具，不是端上功能

实测发现 `op=novelbytype` 支持深翻页（详见 `sfacg-endpoints.md` §3）：

| 项 | 实测 |
| --- | --- |
| 每页 | 6 条，1.5 KB；**实测平均填充 5.20 条**（180 页抽样，SD 0.90） |
| 九类总页数 | 42,568 页 = **255,408 个目录槽位**（PC 列表页同为 14,9xx 页），实际返回 **221,354 条（±5,578）** |
| 稳定性 | 同页重复请求结果一致；相邻页无重叠；类内偶有空洞页（悬疑第 915 页） |
| 排序 | **不按 nid**（首页混有 78 万与 77 万的新书，第 5000 页混有 56 万的书） |
| 限流 | 连打 30 次 @0.5s 全部成功；0.3s 间隔连扫 929 页零失败 |
| 全量耗时 | 约 **16 小时** / **62 MB** 流量（实测 ~1.4 s/页） |

**结论：这是种子构建期与 v2 维护期的工具，不是端上功能。**

- **端上不用**：16 小时、62 MB 不可接受；且它只给 nid + 书名 + 作者 + 评分 + 分类，
  **没有收藏、点击、字数、状态**——枚举到了也无法进榜单。
- **构建期可用**：作为「官方目录」与「我们的数据集」的差集来源。悬疑整类普查给出确切分解：
  目录中库外的 187 本里 **165 本是快照后新建**（nid > 774,850，属时间差），
  **同范围内真遗漏仅 22 本（0.47%）**→ 全站约 **1k 本**；
  反方向 **10.1% 的库内书不在分类目录**（523/5,170）。所以它能给出一份
  「已知的在架缺失清单」，但清单只有千本量级，且**必须先扣掉快照后的新书**（§7.1）。
- **v2 维护期的风险**：排序不按 nid、无「最新」参数，**新书发现必须整类重扫**。
  除非 §12 #2 的「首页是否等价于最近更新」被证实（若是，可用 9 页/天做增量）。

### 7.1 三个必须先分清的量

| 量 | 数值 | 含义 |
| --- | --- | --- |
| 目录槽位容量 | **255,408**（42,568 页 × 6） | 目录能装多少书；PC 列表页页数同为 14,9xx，两端口径一致 |
| 实际返回 | **221,354 ± 5,578** | 枚举真正给到的条目 |
| 缺口 | 约 13% | 槽位被跳过：条目移出目录，但**书本身未必消失** |

**「目录装不下」不等于「站上没有」。** 悬疑整类普查把两者拆开了：目录 5,556 槽位只返回 4,836，
而库内 5,170 本悬疑里有 **523 本（10.1%）查不到分类目录**——页面正常、分类标签仍是悬疑，
只是不在列表里。所以目录是「可发现集」，不是「存在集」。

**这条修正了一个我先前写错的推论。** 我曾用「255,408 是上界」去否定报告 10 的
356,696 本（1.45 倍），那是把目录容量当成了活书上界——**该推论已撤回**：
既然存在大量目录外仍可访问的书，活书总数就可能超过目录容量。

**但报告 10 的数字同样不能照用**，它的前提有三处不成立：

1. **只测「页面能否打开」**，未排除非小说页（漫画与小说共享 nid 空间）；
2. **状态码完全不可信**——无效 nid 也返回 HTTP 200，PC 页 1,643 B 写着「小说不存在」，
   移动页 3,738 B 写着「出错啦」。判活必须匹配文案（`sfacg-endpoints.md` §4.4）；
3. **把「nid 空洞」整体当成抓取遗漏**。空洞里混着三态：**死亡**（「小说不存在」/「出错啦」页，
   HTTP 仍 200）、**僵尸**（有详情页但无 `点击阅读` 入口，或数字字段非法；13–15 KB，
   与存活页体积中位只差 35 B）、**存活**。构建 CSV 时已按 `status_missing` 剔除
   **2,287 本僵尸**，这 2,451 本剔除书在原始 jsonl 里**都已抓到**，不是抓取遗漏。
   报告 10 的「>5KB 且含书名」会把僵尸全算成存活。下架原因（版权/违规/抄袭/AI 等）
   **不进判据**——多数僵尸页的简介不写下架声明。所以遗漏也**不是「近均匀于世代」**。
   详见 `sfacg-endpoints.md` §5.2、§11.5。

**68.9% 偏低的确切机制**：复测 C 组那 63 本后确认它们**全是真活书**
（63/63 有阅读入口、19/25 官方搜索能命中自身），所以偏差**不在个体判活**，
而在**分母**——526,415 个「缺失槽位」里混进了已剔除的 2,451 本（原始 jsonl 早抓到）
和真死亡页，两者都不是「漏抓」却被算进「站上有、我们没有」的分母。
即：**不是把死书判成活书，而是把「本地已有 / 已下架」算进了「漏抓」**。
详见 `sfacg-endpoints.md` §11.5「对报告 10 重写与补爬估算的直接影响」小节。

**因此本文不引用「覆盖率 68.9%」这一数字**；要定量，需要的是「同一批 nid 同时测
可访问、在目录、有阅读入口」的**联合抽样**，而不是任何一侧的单独外推
（`sfacg-endpoints.md` §5.1/§5.2、§12 #7）。

**v1 明确不实现**。本文记录它，是因为它推翻了一个长期前提（「官方不可枚举」），
后续文档与路线图不能继续基于旧前提推演。

## 8. 限流与降级

### 8.1 静默限流是本文最危险的失败模式

| 项 | 实测 |
| --- | --- |
| 触发 | 连续 17–18 次 HTML 搜索（间隔 0.5s） |
| 表现 | **HTTP 200**，5.8 KB 正常页面，标题变「请输入关键字」，声明「共搜索到 0 个结果」 |
| 持续 | **>3 分钟**（20/45/90/180 秒均仍被限） |
| 影响面 | **仅 `s.sfacg.com`**；同期 JSON 搜索、联想词、详情页、`novelbytype` 全部正常 |

**任何「结果为空 = 没搜到」的逻辑都会把它误判成「这本书不存在」**——
这是最坏的一种错误，因为用户会得出「这个 App 连官方都搜不到」的结论。

### 8.2 识别与降级

```
HTML 响应到达
  ├─ 含「请输入关键字」→ 判定为限流，不是空结果
  │    → 丢弃该响应，不写任何缓存，不写 discovered
  │    → 立即切 JSON 搜索（12 条，无简介）
  │    → 启动指数退避：60s → 180s → 600s，上限 600s
  │    → UI 提示「官方检索暂时受限，已显示本地结果」
  └─ 不含 → 正常解析
```

**必须在解析器里做这一条**，而不是在调用方——上游 `sfacg_tools` 的
`_parse_html_results` 没有这个检查，被限时静默返回空列表（`sfacg-endpoints.md` §10 #1）。

### 8.3 客户端配额

| 项 | 值 | 理由 |
| --- | --- | --- |
| 防抖 | 停止输入 **400ms** 后发 | 避免逐字符请求 |
| 同词缓存 | 24h（结果集整体缓存） | 早期已验证的量级；且能大幅降低触发限流的概率 |
| 单次搜索请求数 | 2（HTML + JSON） | 固定 |
| 日上限 | **200 次搜索**（≈400 请求） | 远超正常用户（重度使用者日均 <20） |
| 超限后 | 纯本地搜索，UI 注明「今日官方检索已达上限」 | 不静默降级 |

**不做「为补数据而构造搜索词」**。只记录用户真实搜索——
否则既违反限流预算，也违背「收录反映真实需求」这个前提（§5.1）。

## 9. 空结果与展示规范

### 9.1 三档兜底

| 档 | 触发 | 展示 |
| --- | --- | --- |
| 1 | 官方联想词有命中 | 「你是不是想找：〈3 个书名〉」。实测「英雄」联想词含 `英雄我早就不当了`（《英雄再临》的别名），能纠正记错书名 |
| 2 | 无联想，但输入是分类词（九类之一） | 「该分类的书」→ 跳分类浏览（本地 `genre` 筛选），不是搜索 |
| 3 | 都没有 | 「换个词试试」+ 三条引导（按标签 / 按世代 / 看榜单），**不给推荐列表** |

**第 3 档不给推荐**的理由：把「搜不到」变成「随便给你看点什么」，会让用户以为
「这个 App 搜什么都出来一堆不相干的书」。沉默比噪音好。

### 9.2 文案红线

| 禁止 | 理由 |
| --- | --- |
| 「共找到 N 本」 | 本地 N 不是全站 N |
| 「全站」「全部」「完整收录」 | 种子只覆盖库内 245,779 本；官方每次只给 30 条，**没有任何入口能给出全站计数** |
| 「未收录 = 不存在」 | 未收录可能只是我们没有（01 §2 约束 7） |
| C 组标「推荐」或「相关」 | 我们没有 C 组的任何可比数据（§6） |

### 9.3 搜索的角色定位（UI 层面）

搜索框的占位文案建议为「搜书名或作者」，**不是「搜书」**。
前者与官方 12/12 的精确匹配能力对齐；后者暗示「你可以用它找任何书」，
而这一点我们做不到（§2.2）。

**发现类需求走别的入口**：首页给榜单（03 的 A 类）、分类浏览、标签共现（报告 09）。
搜索是收敛工具，不是发现工具。

## 10. 明确不做

| 项 | 理由 |
| --- | --- |
| 官方结果翻页 | 六种分页参数实测全部无效（§2.1） |
| 标签同义词扩展（搜「百合」带出「橘味」） | 现算：「百合」**根本不是标签**，只是标题词（303 本）；站方对应标签是「橘味」（6,183 本），两者**交集 1 本**。同理「末世」8,808 本与「末日」464 本**交集为 0**。硬拼等于编造关系（旧档 `docs/search.md` §5.5 的判断成立，数字已按当前数据更正） |
| 搜索历史云端同步 | 无服务端（01 §0）；且搜索词是偏好数据 |
| 拼音全拼搜索 | 仅做首字母（`yxlz` → 英雄再临）。全拼需要完整拼音表，v1 不做 |
| 模糊纠错（编辑距离） | 用官方联想词兜（§9.1 第 1 档），不自建纠错表 |
| 端上全库枚举 | 16 小时 / 62 MB（§7） |
| 把官方结果并入 `books` | 会让分位分母被无基线样本污染（02 §3.2） |
