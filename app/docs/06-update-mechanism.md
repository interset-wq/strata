# APP 设计文档 06：更新机制

> **定案 v1.0**。上游契约：01 §1.2/§6、02 §2.4/§6（版本与校验）、03 §4.6（在线榜缓存）、
> 04 §5.2/§8.3（清理与配额）、05 §6（限速）、07 §5（U5 订阅爬取）。

## 0. 结论

"更新"是五件互不相同的事，没有一件是"后台定时刷新全库"：

| # | 名称 | 触发 | 对象 | 定义于 |
| --- | --- | --- | --- | --- |
| U1 | 发版更新 | 用户升级 | 随包种子整文件替换 | 本文 §2 |
| U2 | schema 迁移 | 启动版本比对 | `user.db` | 本文 §3 |
| U3 | 数据刷新 | 打开详情页 | 单本当前值 → `observations` | 05 |
| U4 | 缓存/保留期清理 | 启动或阈值 | 观测/收录/缓存 | 本文 §4 |
| U5 | 订阅观测爬取 | 用户在 `watchlist` 显式开启 | ≤100 本，间隔 ≥6h | 07 §5 |

**核心判断：不叠加全库数据更新调度。** 理由：
1. 主通路（U3）已覆盖真正有价值的对象——没打开的书说明此刻无价值；
2. 补爬缺口仅约 1 千本（覆盖率 69.3% 是可访问上界），不值得一套调度器；
3. 全库调度让请求量与用户行为脱钩，与限速器"请求量=兴趣量"前提冲突；
4. 累计指标跨时点不可比，刷了也不能横比——新值只用于同书纵向对比。

U5 是有边界的例外（用户显式订阅、最低优先级、溢出丢弃），保留"请求量=兴趣量"前提；
四条分界（发起方/对象/量级/兴趣关系）任一被突破即退化为被禁的全库调度。

推论：分位/世代/定年是构建期刻度，App 生命周期内不变；端上刷新"当前值"不刷新"刻度"
（U5 也不写 `books`）。

## 1. U1：种子发版更新

三层版本独立，不可合并：`schema_version`（表结构变更 → 整包替换 + 迁移）、
`seed_version`（内容更新 → 只换文件）、`content_end`（数据时点 → UI 显示，不触发逻辑）。
包内 `manifest.json` 作启动比对源，不打开库即可决定是否换包。

升级路径：

```
启动（引擎握手前）
 ├─ 比对 manifest.seed_version 与数据目录 seed-<version>.db
 │    不存在 → 解压落盘；一致 → 直接用；不同 → 删旧解压新
 ├─ 比对 schema_version → 一致直接用；不一致 → 事务内迁移
 └─ 引擎就绪 → /healthz 通过 → 主界面
```

**种子替换发生在引擎就绪之前**，UI 不会看到半新半旧状态。

原子替换：解压到 `.tmp` → 校验完整 → 原子 rename；失败删临时文件下次重试；
旧版本文件在新版就绪后才删。**不做增量 UPDATE**（种子只读随包、无网络分发，
增量机制换不来收益）。

换包必须保住：`user.db` 完全不动；观测靠 `nid` 挂住（rowid 重排）；
`content_end` 从新 `seed_meta` 读不硬编码。**跨版本分位不可比**（参照系随种子变），
UI 不显示"分位比上版涨了"。

## 2. U2：用户库迁移

原则：迁移脚本在事务内（失败整体回滚）；只动 `user.db` 永不碰 `seed.db`；
迁移前备份 `.bak` 成功后删；向前兼容一个版本。

v1 无历史库，但**迁移框架必须落地**（否则 v2 无处挂载）。可预见的 v2 迁移：
`observations` 加评论两列、新建 `watchlist`/`novel_chapters`（均 `ALTER/CREATE` 默认 NULL，低风险）；
`clicks` 列 v1 保留、07 恢复写入，**无需 ALTER**——这正是 v1 保留该列的价值。

失败处置：引擎不就绪，UI 显示诊断与重试页；不无限重试；`.bak` 保留供手动恢复。

## 3. U4：缓存与保留期清理

三类清理周期互不统一，**不做统一清理任务**：

| 对象 | 周期 | 规则 |
| --- | --- | --- |
| `observations` | 启动检查 + 按月 | 保留 180 天，按月批量 DELETE，**不做 VACUUM**；被裁观测引用的 `fav_delta_30d` 保持 NULL 不回填 |
| `discovered` | 写入后检测 | 超 5,000 条按 `observed_at` 最旧清"从未被打开"的；`shelf`/`observations`/`watchlist` 中出现过的永不清（单事务内 LEFT JOIN 判定） |
| 搜索结果 / 在线榜缓存 | 24h | 内存或临时缓存，不进持久表；在线榜与 A 类分区，标注"官方实时（缓存于 X）" |

## 4. 启动时序

```
App 启动
 ├─ [U4-a] 按月裁剪 observations（失败不阻断——清理是可重试维护操作）
 ├─ [U1] 比对 seed_version → 解压+校验+原子替换（失败保旧库，下次重试）
 ├─ [U2] 比对 schema_version → 迁移（失败回滚、不就绪、UI 提示重试）
 ├─ [U4-b] discovered 超额清理
 └─ 引擎就绪 → /healthz → 主界面
      ├─ [U3] 详情页抓取（05）
      ├─ [U5] watchlist 到期书串行爬取（07；前台活跃期每 30 分钟检查，前台抓取中暂停）
      └─ [U4-c] 24h 缓存（惰性）
```

U4-a 失败不阻断；U1/U2 失败必须阻断（带不匹配版本进主界面会产生错误数据）。

## 5. 不做

全库后台批量/轮转（U5 除外）；服务端推送/观测上报；增量 UPDATE 种子；
写 `books` 或重算分位；rowid 关联；统一清理任务；迁移失败无限重试；
UI 硬编码 `content_end`。

## 6. 待决

180 天保留期初值（存储宽裕可放宽 365）；在线榜缓存落内存（建议 map+时间戳）；
种子换包失败降级为"保旧库 + UI 标注版本未更新"。无阻塞实现的悬置问题。

> 实现里程碑：最小闭环 = 启动握手 → 种子只读打开 → 详情页抓取 → 观测写入 →
> 涨幅榜显示；U1/U2/U4 可后补，**U3 不能延后**（产品承诺的立足点）。
