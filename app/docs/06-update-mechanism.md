## 0. 结论

**一句话**：这个项目里"更新"指的是四类互不相同的东西——**换包**（种子整文件替换）、
**迁移**（用户库 schema 升级）、**刷新**（前台/订阅抓取单本当前值）、**清理**（观测与收录的保留期）——
**没有一件是"后台定时刷新全库数据"**。2026-11-17 修订：新增 07 作者工作台后，
前三类之外补入第五类 **U5（用户订阅的后台观测爬取）**——它作用于 `watchlist` 的小集合，
与"全库轮转"有本质区别（07 §5.1）。

| 结论 | 依据 |
| --- | --- |
| 1. **种子更新 = 换静态包**，不是增量 UPDATE；版本比对走 `manifest.json.seed_version` 与 `seed_meta` | 02 §6.2：整文件换名，只读副本按版本替换 |
| 2. **用户库更新 = schema 迁移**，事务内、先备份、`user.db.bak` 成功后删；**永不碰 `seed.db`** | 02 §6.3 三条原则 |
| 3. **不叠加全库数据调度**：无全库后台批量、无 7 天轮转、无定时刷新 | 01 §6；覆盖率 69.3% 的补爬对象仅约 1 千本，不值得一套调度器 |
| 4. **但允许 U5：用户订阅的后台观测爬取**，仅作用于 `watchlist`（≤100 本，实际常 1–3） | 07 §5：用户显式开启、可随时关闭、日请求 ≤300；与全库轮转不可同日而语 |
| 5. **三类自动清理有不同保留期**：观测 180 天按月裁、`discovered` 超 5,000 条按最旧清、搜索结果缓存 24h | 02 §3.1 / 04 §5.2 / 04 §8.3 |
| 6. **在线官方榜缓存 24h**，与 A 类分区，不写任何本地库 | 03 §8 #7；榜单是查询不是数据资产 |
| 7. **升级必须保住用户观测**：`nid` 是跨版本唯一键，rowid 不可靠 | 01 §3.1；扫描重发后 rowid 重排，观测靠 `nid` 挂住 |
| 8. **内容时点永远可见**：`content_end`（2026-05-03）与本机 `observed_at` 分别标注，不混淆 | 02 §2.4、05 §7 |

## 1. 口径声明：五种被混称为"更新"的东西

产品讨论里"更新"一词至少指五件事，它们的触发、对象、频率完全不同。混为一谈会导致
"做个全库后台定时更新"这种既违反 01 §6、又解决不了真实问题的方案。

| # | 名称 | 触发 | 对象 | 频率 | 本篇是否定义 |
| --- | --- | --- | --- | --- | --- |
| U1 | **发版更新** | 用户升级 App | 随包种子 `seed.db.gz` | 随发版（低） | ✅ §3 |
| U2 | **schema 迁移** | 启动检测到版本不符 | 用户库 `user.db` | 极少 | ✅ §4 |
| U3 | **数据刷新** | 用户打开详情页 | 单本书的当前值 → `observations` | 每次打开 | ❌ 归 05，本篇只重申边界（§2） |
| U4 | **缓存/保留期清理** | 启动或阈值触发 | 临时缓存、过期观测、超额收录 | 定期/按阈值 | ✅ §5 |
| U5 | **订阅观测爬取** | 用户在 `watchlist` 显式开启 | 观测列表中的书（≤100） | 用户定间隔，≥6 h | ❌ 归 07 §5，本篇只划边界（§2.4） |

**U3/U5 是仅有的两种改变"数据新鲜度"的机制**，且都已在别篇定义（05 / 07）。本篇的主要工作，
是明确 U1/U2/U4 各自做什么，并论证**为什么仍然不需要"全库数据调度"**——
U5 是有边界的例外，不是那个被否决的东西复活。

## 2. 核心判断：不叠加**全库**数据更新调度

### 2.1 命题

v1 **不叠**任何一层**全库规模**的自动数据更新：

- 不做全库后台批量爬虫、不做全库 7 天轮转（01 §6）；
- 不做定时刷新种子里的所有书、不做"冷门书轮转更新"；
- 不做服务端推送新数据、不做观测上报换取云端更新（01 §6：无服务端）。

**例外 U5**：用户显式订阅的 `watchlist` 后台观测爬取（07 §5）——
对象是自己的一两本书、间隔 ≥6 h、可随时关闭、日请求 ≤300。它不是"全库调度"，
下文四条理由针对的都是后者；U5 的边界见 §2.4。

### 2.2 为什么这个判断是成立且必要的

**第一，主通路已经覆盖了真正有价值的对象。** 用户会打开的书，就是他关心的书——
每打开一次抓一次，这台设备上他关心的书永远是最新的。没人打开的书停在种子基线，
而"没人打开"恰恰说明它此刻对用户没有价值。为一个没人看的书花请求，是把稀缺配额
花在零收益处（05 §2.1）。

**第二，补爬缺口小到不值得一套调度器。** 报告 10 重写后，真正的补爬对象
（在目录 ∩ 有阅读入口 ∩ 不在库）约 **1 千本**，不是旧稿说的 11.1 万；
覆盖率 69.3% 是"可访问上界"，其中混着死亡页、僵尸页、已下架书与"可访问但不可发现"的口径差。
为一千本书建一套后台调度、去重、失败重试、限速治理，复杂度远超收益——
而且这批书里相当一部分是快照后新建的书，本来就该由 U3 在用户打开时自然补全。

**第三，全库调度器会与限速器打架。** 05 §6 的限速器是全局单例、队列有上限、溢出直接丢弃，
设计前提是"请求量 = 真实兴趣量"。一旦加入**全库**后台调度，请求量与用户行为脱钩，
变成"用户数 × 调度频率"，这正是 01 §3.2 列为生存约束的那条线性增长。
两个来源抢同一个限速队列，要么前台请求被后台挤掉（伤害体验），
要么后台被饿死（调度白做）——没有好的结果。

> U5 不触犯这条，恰恰因为它**保留**了"请求量 = 真实兴趣量"的前提：
> 订阅是用户显式表达的兴趣，对象是用户自己的书，上限 ≤100 本、间隔 ≥6 h。
> 它复用同一限速器且优先级最低、队列溢出直接丢弃（07 §5.3），不会挤占前台。

**第四，累计指标跨时点不可比，刷了也不能比。** 报告 02/08 已证 `clicks`/`favs` 受书龄与曝光分母混杂，
跨世代、跨时点不可直接比较；端上抓来的新值意义是"这本书现在的绝对数"，
配合本机 `observations` 做**同一本书的纵向对比**才有效（01 §3.1）。
把这个新值塞回种子去改分位、去和别的书横比，反而破坏了可比性（05 §5.3）。

### 2.3 一个容易被忽略的推论

"不叠加全库调度"还意味着：**种子里的分位、世代、定年字段在整个 App 生命周期内不变**。
它们不是"数据旧了要刷新"的对象，而是构建期固定在全库参照系上的刻度（02 §5.1 规则 1）。
端上要刷新的是书的"当前值"（收藏/赞/字数/状态），不是它的"刻度"。
这条区分是 05 §5.3 "绝不写 `books`" 的更新机制侧表述——**U5 同样不写 `books`**，
只是把当前值写进 `observations`（07 §7）。

### 2.4 U5 的边界（与全库调度的四条分界）

| 维度 | 全库调度（禁止） | U5 订阅观测（允许，07 §5） |
| --- | --- | --- |
| 发起方 | 系统自动、无差别 | 用户显式开启，可随时关闭 |
| 对象 | 全库 24.6 万本 | `watchlist` ≤100 本，实际常 1–3 |
| 日请求量 | 数百万 | ≤300，且优先极最低、溢出丢弃 |
| 与兴趣关系 | 无关 | 完全由用户订阅驱动，仍满足"请求量 = 兴趣量" |

四条分界任一被突破（如"帮用户自动订阅所有书架书""默认全开"），U5 就退化成被禁止的全库调度——
这是实现时必须盯住的滑坡。

## 3. U1：种子发版更新（换静态包）

### 3.1 三层版本，各管一件事

沿用 02 §6.1，三种版本互相独立，**不可合并成一个号**：

| 版本 | 变更频率 | 触发什么 |
| --- | --- | --- |
| `schema_version` | 极少 | 表结构变了：种子整包替换 + 用户库迁移（§4） |
| `seed_version` | 随发版 | 种子内容更新：只换文件，不迁移 |
| `content_end` | 随发版 | 数据内容时点（如 2026-05-03）：UI 显示，不触发任何逻辑 |

`seed_meta` 是随种子包的一个小表（02 §2.4），包内另有一份 `manifest.json`
记录 `seed_version`，作为**启动时的比对源**——不打开数据库就能决定是否要换包。

### 3.2 升级路径（02 §6.2 的落地）

```
启动（01 §1.2 握手之前）
  ├─ 读包内 manifest.json.seed_version
  ├─ 比对数据目录 seed/seed-<version>.db
  │    ├─ 不存在        → 解压 seed.db.gz → 落盘
  │    ├─ 版本一致      → 直接用
  │    └─ 版本不同      → 删旧 → 解压新的
  ├─ 打开 user.db → 比对 schema_version
  │    ├─ 一致 → 直接用
  │    └─ 不一致 → 执行迁移脚本（事务内，§4）
  └─ 引擎就绪 → UI 轮询 /healthz 通过（15s 超时）→ 进主界面
```

**关键点：种子替换发生在引擎就绪之前**。UI 看到的永远是一个已经换好种子、迁移完用户库的
一致状态，不会在启动中途看到"一半旧一半新"的数据。

### 3.3 原子替换

种子是**整文件换名**，不是增量 UPDATE（02 §6.2）：

- 解压到临时路径（如 `seed-<version>.db.tmp`），校验完整性后再原子 rename 到目标名；
- 失败的临时文件删除，下一次启动重试——**绝不在半途的库上打开查询**；
- 旧版本文件在新版本就绪后才删，避免解压失败时无库可用。

**为什么不做增量更新**：种子是只读资产，增量 UPDATE 需要记录每个版本的 diff、
处理中途失败的部分写、还要维护版本链——复杂度全部换来一个"省 6.27 MB 下载"的收益，
而种子本来就是随包分发、没有网络下载这一步（01 §6：无服务端分发）。

### 3.4 版本换包时必须保住的东西

| 资产 | 换包后 | 依据 |
| --- | --- | --- |
| `user.db`（观测/书架/标注/搜索历史） | **完全不动** | 独立文件，不在包内（01 §3.1） |
| 观测与书的关联 | 靠 `nid` 保持，不靠 rowid | 01 §3.1：种子重发后 rowid 重排 |
| 被裁掉的书的观测 | 仍在 `user.db`，UI 不显示但可查 | 02 §5.1 规则 3；不为删书写迁移 |
| `content_end` 显示 | 从新 `seed_meta` 读，**不硬编码** | 02 §2.4、05 §7.1 |

**一个必须写清的边界**：分位字段随种子整体替换而变（因为参照系可能是新一版全库）。
因此跨版本的分位**不可直接比较**——UI 若展示"这本书分位比上版涨了"，是错误叙事。
分位只在当前种子版本内有效。

## 4. U2：用户库 schema 迁移

### 4.1 三条原则（02 §6.3，不可协商）

1. **迁移脚本必须在事务里**，任一步失败即整体回滚，保留原库；
2. **迁移只动 `user.db`，永不触碰 `seed.db`**；
3. **迁移前自动备份** `user.db.bak`，成功后删除。

补充一条从 v1 实际表结构推出的约束：**迁移必须向前兼容一个版本**——
v1 的库能被 v2 打开，反之不必（02 §6.3）。

### 4.2 v1 的迁移清单

v1 是首个版本，**没有历史库要迁移**。迁移框架本身要在 v1 落地（否则 v2 无处挂载），
但 v1 只执行"版本一致 → 直接用"分支。

为 v2 预留的可预见迁移：

| 变更 | 迁移动作 | 风险 |
| --- | --- | --- |
| 新增列（如 §5.4 失败态标记） | `ALTER TABLE ... ADD COLUMN`，默认值 NULL | 低；现有行不受影响 |
| 作者工作台的两列 + `watchlist` 表（07 §4.2、§3.1） | `observations` 加 `short_comments`/`long_comments`；新建 `watchlist` | 低；均默认 NULL/空表 |
| `observations.clicks` 启用 | 列已在 v1 保留，**无需 ALTER**——07 §4.3 已对订阅用户开始写入 | 零 |

> **一处修订说明**：06 原稿把 `observations.clicks` 与 `user_stats.click_delta_30d` 都写成"v1 恒 NULL 死列"。
> 07 作者工作台让 `clicks` 恢复写入（仅订阅用户、只绝对值），
> 因此**只有 `click_delta_30d` 仍是恒 NULL**。保留 `clicks` 列的价值由此兑现——
> 恢复写入不需要迁移表结构，这正是 v1 保留它的原因。
> 但**点击变化量仍不做**（07 §4.3），`click_delta_30d` 保持 NULL。

### 4.3 迁移失败的处置

迁移失败时（事务回滚、原库保留）：

- 引擎**不**进入就绪状态，UI 显示带诊断信息与重试的页面（01 §1.2 的失败路径）；
- 不无限重载、不自动反复重试——反复尝试一个有结构性问题的迁移只会磨损用户耐心；
- `.bak` 保留供用户手动恢复；下次启动可重试。

## 5. U4：缓存与保留期清理

三类清理对象，三个不同周期，**互不统一**（强行一个"统一清理任务"会把 24h 缓存和 180 天观测混在一起）：

### 5.1 `observations`：保留 180 天，按月裁剪

02 §3.1 实测 59 B/行：5,000 行 368 KB、20,000 行 1.4 MB、10 万行 5.8 MB。
全保留可接受，但 90 天前的观测对"近 30 天涨幅"已无用，故保留 180 天。

| 项 | 规则 |
| --- | --- |
| 触发 | 启动时检查一次；此后按月 |
| 动作 | `DELETE FROM observations WHERE observed_at < ?`（阈值 = 现在 − 180 天） |
| 批量 | 按月分批，单批上限防止长事务卡 UI |
| VACUUM | **不做**——碎片由 SQLite 自动复用（02 §3.1） |
| 连带 | `user_stats` 的 `fav_delta_30d` 若引用的旧观测被裁，下次写入时保持 NULL，不回填伪造差值 |

### 5.2 `discovered`：超过 5,000 条按最旧清理

04 §5.2 定的阈值与判别：

| 项 | 规则 |
| --- | --- |
| 触发 | 写入新条目后检测 `COUNT(*) > 5000` |
| 清理对象 | 按 `observed_at` 最旧优先，且**从未被打开过**的条目 |
| 永不清 | 出现在 `shelf`、`observations` 或 **`watchlist`** 里的——订阅是比"打开过"更强的兴趣信号（07 §3.4） |
| 依据 | 搜索期望每次新增 ≈2.8 本（04 §5.1），5,000 条上限远超正常使用；单行体积极小 |

### 5.3 搜索结果缓存：24h

04 §8.3：同一关键词的结果集整体缓存 24h。这是**内存/临时缓存**，不进任何持久表，
与 `discovered`（持久收录）是两回事。

### 5.4 在线官方榜缓存：24h

03 §8 #7 定的策略：

| 项 | 规则 |
| --- | --- |
| 对象 | B 类在线官方榜（月票榜、热销榜、对话月票榜，03 §4.6） |
| 缓存 | 24h，内存或临时文件，**不写 `books`/`user.db`** |
| 展示 | 与 A 类分区，标注"官方实时（缓存于 X）"，不提供跨区排序 |
| 理由 | 榜单是**查询结果**不是数据资产；与本机观测、种子统计三不可比（03 §1.3） |

## 6. 更新机制时序总览

把 U1/U2/U4 放进一条启动时间线，避免实现时各自为政：

```
App 启动
  │
  ├─ [U4-a] 读 user.db，按月批量裁剪 observations（180 天）
  │          └─ 失败不阻断启动：清理是可重试的维护操作
  │
  ├─ [U1] 比对 manifest.seed_version
  │    └─ 版本不同 → 解压 + 校验 + 原子替换 seed-<version>.db
  │          └─ 失败：删临时文件，保留旧库，下次重试
  │
  ├─ [U2] 比对 schema_version
  │    └─ 不一致 → 备份 .bak → 事务内迁移 → 成功删 .bak
  │          └─ 失败：回滚、保留原库、不就绪、UI 提示重试
  │
  ├─ [U4-b] 检查 discovered 超 5,000 → 清理未被打开的最旧条目
  │
  └─ 引擎就绪 → UI /healthz 轮询通过 → 主界面
       │
       ├─ [U3] 用户打开详情页 → 抓取 + 写 observations（归 05）
       ├─ [U5] 检查 watchlist 中 poll_enabled 且到期的书 → 串行爬取（归 07 §5）
       │        └─ 前台活跃时每 30 分钟检查一次；前台抓取中则暂停
       └─ [U4-c] 在线榜 24h 缓存 / 搜索结果 24h 缓存（按需，惰性）
```

**U4-a 放在最前、且失败不阻断**：清理是维护操作，不该因为一次 DELETE 失败就让用户进不了 App。
U1/U2 失败则必须阻断——带着不匹配的版本进入主界面会产生错误数据。
**U5 排在引擎就绪之后**：它依赖 `watchlist` 与限速器，且优先级低于前台——
App 未运行时不爬取，下次启动补一次（07 §5.2）。

## 7. 明确不做

| 不做 | 原因 |
| --- | --- |
| 全库后台批量爬虫 / 全库 7 天轮转 | 01 §6；补爬缺口仅约 1 千本，不值得一套调度器（§2.2）。**观测列表订阅式爬取 U5 除外**（07 §5） |
| 服务端推送更新 / 观测上报换更新 | 无服务端（01 §6）；请求量与用户行为脱钩是生存约束 |
| 增量 UPDATE 种子 | 种子只读随包、无网络分发；整文件替换更简单可靠（§3.3） |
| 把端上抓取值写回 `books` 或重算分位 | 分位参照系固定、跨版本不可比（§2.3、05 §5.3） |
| 用 rowid 关联观测与书 | 种子重发后 rowid 重排；唯一键是 `nid`（§3.4） |
| 统一清理任务（把 24h 缓存与 180 天观测一起清） | 周期、对象、失败后果都不同（§5） |
| 迁移失败后自动无限重试 | 01 §1.2；结构性错误重试无意义 |
| 硬编码 `content_end` 在 UI | 从 `seed_meta` 读，随版本更新（§3.4） |
