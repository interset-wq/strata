## 0. 结论

**一句话**：官方 App 只给作者看收藏的动态变化，而作者真正关心的是**更新量（直接关系全勤 RMB 奖励）、
点赞、收藏、评论、长评、点击**这一整组数字，以及和同期作品的对照——
把它做成"用户主动订阅的书 × 时间"的可视化，是本产品对作者用户的核心竞争力。

| 结论 | 依据 / 说明 |
| --- | --- |
| 1. **观测列表是独立实体 `watchlist`**，不是书架 | 书架语义是"想读"（02 §3.3）；作者追踪自己的作品不等于想读它。三者可重叠但语义不同（§3） |
| 2. **后台定期爬取只作用于观测列表**，与"全库 7 天轮转"有本质区别 | 用户显式订阅、对象是自己的书（个位数）、请求量可控；01 §6 禁的是后者，不连带禁前者（§5.1） |
| 3. **点击按通路分档**：PC 版 ±500 量化不可做变化；**App API 的 `viewTimes` 精确整数可做单书曲线** | 精度是**通路的属性**，不是平台的属性（§4.3）。跨书变化榜仍不做——理由换成"累计量需曝光分母" |
| 4. **评论/长评可做变化观测**：`op=getcomment` 返回精确整数，比点击更适合追踪 | 实测 82,291 / 452；此前"不抓评论"的前提（无写回目标、逐本查）在观测场景中消失（§4.4） |
| 5. **更新量是第一指标，直接关系全勤 RMB 奖励**：官方日更 ≥3,000 字得 500 元/月、允许一次断更 | 官方作者福利页 `i.sfacg.com/fuli.shtml`（§2.5）；两官方页面 + 征文公告口径冲突，阈值做成可配置、不替平台拍板 |
| 6. **"热力图"专指更新热力图**（某日更新字数），色阶锚全勤阈值、不做书内归一化 | 作者判达标要绝对线；2,900 字是个人高峰但仍不达标（§1.4） |
| 7. **更新量的数据来源分主备**：**章节时间戳为主**（`chaps` 逐章 `addTime`+`charCount`），观测差分为回退 | 主方案下「数据缺口」概念**不存在**——章节是历史事实，不依赖用户是否打开 App（§4.5.1） |
| 8. **图表只对观测列表的书生成**，不扩展到全库 | 观测数据只覆盖用户主动打开/订阅的书；全库时序数据不存在，画出来是编造（§6） |
| 9. **同期对照集是一等概念**：作者用自己的书 vs 同期其他作者的作品比较 | 累计指标受书龄与曝光分母混杂，**只有同期比较才合法**（报告 02/08）；`watchlist.role` 区分本人/对照（§1.5） |
| 10. **复合指标端上现算、不写表**：赞藏比、评论率、精确指标的日增 | 观测集 ≤100 本 × 180 天，现算是毫秒级；与全库 24.6 万行的预计算是不同场景（§4.7） |
| 11. **作者功能不污染种子统计**：观测值不写 `books`、不改分位分母 | 与 05 §5.3 一致；作者自己的书无论是否在种子里，都不改全库刻度（§7） |
| 12. **保留"全库不后台轮转、无服务端、不重算分位"三条底线** | 作者模块是端上、订阅式、作用于小集合；不打开任何全局通路（§5.1、§8） |
| 13. **App API 是可选增强，不是基线**：失效即降级，功能不残缺 | App API 无契约、随时可能变；web 端才稳定。移动版 HTML 必须始终可用（05 §3.5） |

## 1. 口径声明

### 1.1 两个用户角色，两套数据诉求

前六篇默认用户是**读者**：发现书、看排名、追踪自己关心的书的新值。
本篇引入**作者**角色，其诉求结构完全不同：

| 维度 | 读者 | 作者 |
| --- | --- | --- |
| 关心的书 | 别人写的、自己想读的 | **自己写的**（1–3 本）**+ 同期其他作者的书**（对照集，§1.5） |
| **关心的指标（首位）** | 收藏、分位（"值不值得看"） | **更新量/全勤达标**（直接关系 RMB 奖励，§2.5）——这是作者最在意的 |
| 其他指标 | — | 点赞、收藏、评论、长评、点击（"我的作品表现如何"）**+ 复合指标**（赞藏比、日增，§4.7） |
| 关心的比较 | 书值不值得读（绝对分位） | **我和同期比怎么样**（相对位置；累计指标只有同期比才合法） |
| 关心的时间尺度 | 当前值够用 | **逐日时间序列**（"这周涨势如何"） |
| 是否想"读"这本书 | 是 | 否（书是自己写的；对照书也未必想读） |
| 更新通路 | 打开详情页顺带刷新 | **主动订阅后台定期抓取** |

官方 App 只提供收藏的动态变化一个维度。作者若想知道点赞涨没涨、评论多没多、点击走势，
以及"我和同期那几本比谁涨得快"，目前都没有工具——这就是本产品的切入空间。

### 1.2 "观测列表"不是"书架"

02 §3.3 的 `shelf` 语义是"想读"，作者把自己的书放进去在语义上是错的（他不想"读"自己写的书）。
因此新建独立实体 `watchlist`，与 `shelf` 平行：

| | `shelf`（书架） | `watchlist`（观测列表） |
| --- | --- | --- |
| 语义 | 我想读的书 | 我要追踪数据的书 |
| 主要用户 | 读者 | 作者（也可被读者用于追踪竞品/追更） |
| 驱动抓取 | 否（书架本身不触发） | **是，可订阅后台定期爬取** |
| 展示 | 书封面列表 | 指标仪表盘 + 热力图 + 图表 |
| 是否可重叠 | 同一 nid 可同时在两表，互不干扰 | 同左 |

### 1.3 与 C 类观测榜的关系

03 §4.7 的 C 类"本地收藏涨幅榜"是**读者侧**的榜单——它从全设备观测里聚合，展示"本机见过的书里谁收藏涨得快"。
本篇的**作者工作台**是**作者侧**的仪表盘，只看观测列表里的书、看全指标、看逐日曲线。
两者共用 `observations` 作为数据源，但**入口、对象、指标、可视化形式全不同**：

| | C 类观测榜（03 §4.7） | 作者工作台（本篇） |
| --- | --- | --- |
| 对象 | 本机所有观测过的书 | 仅 `watchlist` 中的书 |
| 指标 | 仅 `favs`（精确整数） | 全指标（含点击绝对值、评论、长评、字数） |
| 形式 | 排行榜 | 仪表盘 + 热力图 + 时间序列图 |
| 触发 | 前台打开详情页 | 前台打开 + **后台定期爬取** |
| 样本不足 | 隐藏整榜 | 单书仍显示当前值，图表区标注"观测不足" |

### 1.4 "热力图"的确切定义：更新热力图

**本文所说"热力图"专指「更新热力图」**（日历贡献图式，形如 GitHub 绿点图），
**不是**"收藏/赞/点击的指标矩阵热力图"。它是作者工作台的首屏组件，
回答一个问题：**"这本书哪天更新了多少字——这个月的全勤稳不稳"**（全勤规则见 §2.5）。

| 维度 | 定义 |
| --- | --- |
| 形制 | 日历网格：行 = 周几（7 行），列 = 周；每格 = 一天 |
| 单元格 | 某书在某日的**新增字数** `Δwords`（§4.5 的归因规则） |
| 颜色 | **按全勤阈值分档**，不是按相对高低归一化（理由见下） |
| 默认跨度 | 最近 12 周（84 天），可切 4 / 12 / 26 周；观测保留期 180 天是硬上限 |
| 对象 | 默认显示 `role='self'` 的书；可切到 `role='peer'` 对照同期作者的更新节奏 |

**为什么颜色锚定绝对阈值、而非书内归一化**：作者看这张图是为了判断"今天够不够全勤"，
不是"今天比自己平时多还是少"。归一化会抹掉绝对门槛——
一天写 2,900 字可能是他的个人高峰，但全勤线是 3,000，仍然不达标，
归一化后却会显示成"高产"的深色。因此色阶固定锚在官方阈值上（§2.5），跨日、跨书可比。

**其他指标不出热力图**：收藏/赞/点击/评论走折线图与仪表盘（§6.1）。
此前草稿把"热力图"泛化为指标矩阵是理解偏差，此处更正——
那类矩阵既回答不了全勤，也会因跨书量级差误导（收藏 4 vs 353,958）。

### 1.5 "同期对照集"的定义

作者判断"我的书是否受欢迎"，本质是**比较**，不是看绝对值。
全库分析已经证明：累计指标受书龄与曝光分母混杂，**只有同期比较才有效**（报告 02/08、03 §3.3）。
因此 `watchlist` 里的书分两种角色：

| 角色 | `role` 值 | 含义 | 典型数量 |
| --- | --- | --- | --- |
| 本人作品 | `'self'` | 作者自己的书，主要观测对象 | 1–3 本 |
| 同期对照 | `'peer'` | 同期其他作者的书，用于对照 | 几本到几十本 |

"对照集" = `watchlist` 中 `role='peer'` 的全部书，是一个**扁平集合**，不做多组分层——
作者通常只有一组同期参照，多组是过度设计（§9 #9 列为上线后实测项）。

**"同期"怎么判定**：从种子 `books.est_year` 取定年（02 §2.1），加入对照集时 UI 显示
"与你本人作品相差 N 年"；相差 > 2 年给软警告"非同期，比较意义有限"，但**不硬拦**——
作者有时就是想跨代对照，只是需要知道口径风险。对不在种子里的书（`est_year` 未知），
标注"定年未知，无法判断是否同期"，仍可观测但不进同期对照图。

**关键约束**：对照集只提供**同期内的相对位置**，不输出"我的书比别人强"的绝对结论。
折线与散点可以并排看，但不给总排名——不同指标的领先者可能不是同一本。

## 2. 核心命题：官方只给收藏变化，我们给全指标时间序列

### 2.1 官方 App 的能力边界

官方 App 的作者后台只展示**收藏的动态变化**一个维度。
点赞、评论、长评、点击、字数的逐日走势，作者要么看不到，要么只能手动截图对比。
这个空白不是"我们多做几个图表"的问题——它是作者判断"作品是否受欢迎"的**唯一信息源缺口**。

### 2.2 作者真正关心的六个指标（更新量居首，详见 §2.5）

| 指标 | 作者为什么在意 | 来源 | 精确性 |
| --- | --- | --- | --- |
| **更新量 `Δwords`（首位）** | **直接决定全勤奖 500 元/月**（§2.5） | **主**：App API 逐章 `addTime`+`charCount` 直接聚合；**回退**：移动版 `words` 累计值逐次求差 | 整数；主方案是**正文口径**且可判单日，回退方案受观测缺口影响（§4.5） |
| 收藏 `favs` | "被认可"信号 | 移动版 `.book_interact` 第 1 项 / App `markCount` | 精确整数 |
| 点赞 `praises` | 比收藏轻量的即时反馈 | 移动版第 2 项 | 精确整数 |
| 累计字数 `words` | 更新量的来源（不是独立指标） | 移动版 `.book_info3` / App `charCount` | 精确整数，**只增不减**；本身不进榜 |
| 短评数 | 读者讨论热度 | `op=getcomment.ShortCommentNum` | 精确整数 |
| 长评数 | 深度反馈 | `op=getcomment.LongCommentNum` | 精确整数 |
| 点击 `clicks` | 曝光/流量信号 | **PC 版** `人气：…万` / **App** `viewTimes` | **按通路分档**：PC 版 ±500 量化，只显示绝对值；**App 精确整数，可做单书日增曲线**（§4.3） |

### 2.3 为什么这是核心竞争力

1. **需求真实且高频**：作者对自己的作品数据有持续、强烈的关注动机，远超普通读者对陌生书的兴趣。
2. **官方留白明确**：只给收藏变化，更新量全勤预警与其余五个维度都无处可看。我们补的是官方的结构性缺口，不是内卷已有功能。
3. **数据已经在手**：点赞/收藏/字数/状态来自已有的移动版详情抓取（05 §4.1）；点击来自 PC 版（多一次请求）；
   评论来自已有的 `op=getcomment`（05 §8.1 实测过）。**不需要新端点、不需要新数据源**——
   只是把已经能拿到的指标组织成作者要的形态。
4. **端上闭环**：无服务端（01 §6），作者数据只存在本设备。这既是隐私优势，也避免了"观测上报"那条被明确否决的路。

### 2.4 为什么必须引入同期对照

只看自己的绝对值，作者回答不了"我的书受欢迎吗"——收藏 500 算高还是低，取决于同期同题材的书是多少。
全库分析早已给出这条口径：

| 证据 | 结论 |
| --- | --- |
| 报告 02 / 08 | 累计指标（收藏 / 赞 / 点击）混杂书龄与曝光分母，跨世代横比无意义 |
| 03 §3.3 | 分位只在同世代内可比，不提供跨世代加总或平均 |
| 报告 19 | 低曝光样本上比值型指标会反向，对照必须限同期、同字数档 |

所以对照功能不是"多加几条折线"，而是把这套已验证的口径落到作者能用的形态：
`self` 与 `peer` 必须在同一时间轴、同一指标口径下并排比较，且定年差超 2 年要提示（§1.5）。
对照书必须进 `watchlist` 而不是只看种子快照——种子定格在 2026-05-03，
而作者问的是"这周我追上他了吗"，只有端上时序能回答。

**不提供的东西**：不给"同期总排名"。不同指标的领先者可能不是同一本，
合成单一名次必然丢失信息，还会诱导作者把复合指标当成权威评分（§4.7 红线）。

### 2.5 全勤奖：为什么"更新量"是第一指标

用户指出：**官方有勤更激励，拿到全勤可获额外 RMB 奖励，这对很大一部分作者是最重要的指标之一**。
这条改变了工作台的优先级——更新热力图不是"六个指标里的一项"，而是首屏主组件。

#### 2.5.1 官方规则（已查证，2026-11-17）

| 来源 | 条件 | 奖金 | 适用范围 |
| --- | --- | --- | --- |
| **官方作者福利页** `i.sfacg.com/fuli.shtml`（权威） | 日正常章节更新总字数 **≥ 3,000 字**，**每月允许一次断更**；正常章节 = 小说正文，不含人设/背景介绍/百科 | **500 元/月** | 所有已签约作品 |
| 第十四届征文公告（2026-05 公众号） | 上架作品日更 ≥3,000 → 500 元；≥6,000 → **1,000 元**；另有「勤更奖金」累计（总字数 100 万起最高 4,000 元、200 万起 8,000 元，上不封顶） | 500 / 1,000 元 | **上架 VIP 作品** |
| 第三方导航（2026-07，非官方） | 签约未上架：日更 ≥2,000 且月更 ≥ 天数×3,000，300 元；VIP：日更 ≥2,000 + 月均 3,000/6,000，分档 | 300 / 500 / 1,000 元 | 签约 / VIP |

**用户给的 `book.sfacg.com/fuli.shtml`**：抓取到的正文是**对话小说**的签约与获奖规则，
不含轻小说全勤段落——轻小说全勤条款在 `i.sfacg.com/fuli.shtml`。两个页面同属官方、内容不同，
本设计以 `i.sfacg.com` 为权威源。

#### 2.5.2 三处口径冲突，不由我们拍板

| 冲突 | 表现 | 处置 |
| --- | --- | --- |
| 日门槛 3,000 vs 2,000 | 官方福利页写 3,000；第三方写"日更 2,000 + 月均 3,000"双条件 | 阈值**可配置**，默认取官方 3,000 |
| 单档 500 vs 双档 500/1,000 | 官方福利页只有 500；征文公告称上架作品有 1,000 档 | 默认 3,000→500；1,000 档作为**可选目标线**（用户自己填），不默认开启 |
| "正常章节"排除项 | 官方明确排除人设/背景/百科 | **主方案下大幅收窄**：App API 逐章 `charCount` 就是正文口径（§4.5.2）；**回退方案**仍只有详情页总字数，**必须标注"以详情页总字数估算，非官方判定"** |
| 待审章是否计入 | 官方口径未公开；`chaps` 的 `auditStatus` 有待审态（`1`） | **单列标注**，不静默计入（§4.5.2） |

**设计原则**：App 提供的是**自查与预警**，不是官方结算。所有阈值带设置项与来源标注，
规则若变更由用户自行调整，避免我们把一条可能过期的规则硬编码进产品。

#### 2.5.3 由此确定的产品形态

- **更新热力图**（§1.4）色阶锚在配置的全勤线：达标日按超出比例分深浅，未达标日显浅色，断更日显式留空/标灰；
- **全勤达标看板**（§6.1）：本月累计字数 / 目标（当月天数 × 日门槛）、断更次数（已用 / 允许 1 次）、按当前进度预计是否达标；
- **同期对照**：可切换看 `peer` 书的更新热力图——"同期那本日更 6,000，我拿的是小全勤还是大全勤"，这是作者真实的比较动机。

## 3. 观测列表 `watchlist`

### 3.1 表结构（`user.db`，新建）

```sql
-- 3.8 观测列表：作者/读者主动订阅要追踪的书
CREATE TABLE watchlist(
  nid           INTEGER PRIMARY KEY,       -- 与 seed.books / discovered 共用 nid
  role          TEXT NOT NULL DEFAULT 'self', -- 'self' 本人作品 | 'peer' 同期对照（§1.5）
  added_at      INTEGER NOT NULL,          -- 加入时刻 unix 秒
  poll_enabled  INTEGER NOT NULL DEFAULT 1, -- 是否订阅后台定期爬取
  poll_interval INTEGER NOT NULL DEFAULT 86400, -- 爬取间隔秒，默认 24h
  last_poll_at  INTEGER,                   -- 上次后台爬取时刻
  note          TEXT                       -- 用户备注
);
CREATE INDEX idx_watch_poll ON watchlist(poll_enabled, last_poll_at);
CREATE INDEX idx_watch_role ON watchlist(role);
```

| 字段 | 取值约束 | 说明 |
| --- | --- | --- |
| `role` | `'self'` / `'peer'` | 决定图表里的角色：本人作品用实线、对照用虚线；默认 `'self'` |
| `poll_interval` | 最小 21,600 s（6 h），建议档 6 h / 24 h / 7 d | 防止用户设 1 秒把限速器打爆；Go 侧校验下限 |
| `poll_enabled` | 0/1 | 用户可暂停订阅而不删除列表 |
| `last_poll_at` | NULL = 从未后台爬取 | 前台打开详情页的抓取**不更新此字段**——两者独立 |

**`role` 可改**：作者把一本对照书"认领"为自己的作品（或反之）时，只 UPDATE 这一列，
不删行、不动 `observations`——历史曲线必须连续。

### 3.2 加入与移除

| 操作 | 行为 |
| --- | --- |
| 加入 | 从详情页/搜索/榜单均可加入；需选 `role`（self/peer，默认 self）；仅写 `watchlist` 一行，不写 `books`/`discovered` |
| 重复加入 | `nid` 主键天然去重；只更新 `added_at`，不重置 `last_poll_at` |
| 移除 | 只删 `watchlist` 行；**该书的 `observations` 历史保留**（观测不可重建，02 §3.1） |
| 暂停 | `poll_enabled=0`，不删历史；恢复订阅时不补跑暂停期间的缺口 |

**移除不删观测**这条必须守住：作者可能临时取消追踪，之后又加回来，历史曲线不能断。

### 3.3 容量与配额

| 项 | 值 | 理由 |
| --- | --- | --- |
| `watchlist` 行数上限 | **100 本**（self ≤ 20、peer ≤ 80 建议值） | 作者自己的书 1–3 本；对照集是主要占用者。硬上限仍是 100，分部建议只做 UI 提示不硬拦 |
| 超限处理 | 提示用户移除旧条目，不自动删 | 自动删会无声丢失用户明确的订阅意图 |
| 单本请求数/次 | 移动版 1（15 KB）+ 评论 1（1 KB）+ 仅点击需要时 PC 版 1（73 KB） | 见 §4、§5.3 |
| 后台日请求量上界 | 100 本 × 24h 间隔 × 3 请求 = **300 请求/日** | 与 04 §8.3 搜索 200 次/日的量级相当；实际远低于此（用户不会订满 100 本） |

### 3.4 与 `discovered` 清理的交互

04 §5.2 规定 `discovered` 超 5,000 条时清理"从未被打开过"的条目，判据是"出现在 `shelf` 或 `observations` 里"。
**新增一条豁免**：出现在 `watchlist` 里的条目同样永不清——订阅是比"打开过"更强的兴趣信号。
这条回填到 04 §5.2（见 §10）。

## 4. 多指标观测

### 4.1 写回路径总览

```
watchlist 中的书
  ├─ 前台打开详情页 → 05 的移动版抓取（基线，永远可用）
  │                    → observations(favs/praises/words/status/updated_at)
  │                    └─ 若该书在 watchlist 且用户开启点击 → 追加 PC 版抓取 → clicks
  ├─ 若启用 App API 通路（可选增强，失效即降级）
  │                    → GET /novels/{id}（0.7 KB）→ observations 补写 clicks/viewTimes、
  │                      addTime 记入 novel_chapters 的书籍级补充
  │                    └─ GET /novels/{id}/chaps（222–489 KB，一次性）
  │                           → novel_chapters（逐章 addTime + charCount）→ 更新热力图主方案
  └─ 后台定期爬取（§5）→ 同上，外加：
                       └─ op=getcomment → short_comments / long_comments
```

**三条通路的请求量对比**（单本每次轮询）：

| 组合 | 请求数 | 体积 |
| --- | --- | --- |
| 基线（移动版） | 1 | 15.7 KB |
| 基线 + 评论 | 2 | 15.7 + ~1 KB |
| 基线 + 评论 + PC 版点击 | 3 | ~90 KB |
| **App API 详情 + 章节（首次）** | 2 | **0.7 + 222–489 KB** |
| **App API 详情（后续轮询）** | 1 | **0.7 KB** |

> **App API 在请求体积上是压倒性优势**（0.7 KB vs 15.7 KB，22 倍），
> 代价是它可能失效——所以它是增强，基线永远在（05 §3.5）。

### 4.2 `observations` 表扩展

02 §3.1 的 `observations` 现有列：`nid / observed_at / clicks / favs / praises / words / status / updated_at / source`。
新增两列（精确整数，可变化观测）：

```sql
ALTER TABLE observations ADD COLUMN short_comments INTEGER;  -- v2 迁移，见 §7
ALTER TABLE observations ADD COLUMN long_comments  INTEGER;
```

| 列 | 来源 | 空值语义 |
| --- | --- | --- |
| `short_comments` | `op=getcomment.ShortCommentNum` | NULL = 本次未抓评论（普通详情页抓取） |
| `long_comments` | `op=getcomment.LongCommentNum` | 同上；**不是 0** |

### 4.3 点击：按通路分档（2026-11-17 修订）

原稿写的是"恢复写入绝对值、但不做变化"。这条判断的依据是 **PC 版的人气量化**（±500），
而精度是**通路的属性**——官方 App API 的 `viewTimes` 是**精确整数**，量化问题不存在。
因此改为按通路分档。

| | PC 版通路 | **App API 通路** |
| --- | --- | --- |
| 点击数字段 | `人气：11899.5万` → 量化步长 1,000、±500 | **`viewTimes` 精确整数**（示例 33,353,509） |
| 记录绝对值 | ✅（订阅书） | ✅（订阅书） |
| 单书日增曲线 | ❌ 差值可能全是取整噪声 | **✅ 可做**——差值是真差值 |
| `click_delta_30d` | ❌ | **❌ 仍不做**（理由不同，见下） |
| 跨书点击变化榜 | ❌ | **❌ 仍不做**（理由不同，见下） |
| 失效后的行为 | — | **曲线自动隐藏，其余功能不受影响**（05 §3.5） |

**为什么 App API 下仍不做 `click_delta_30d` 与跨书变化榜**——原因从"精度"换成了"累计量口径"：

- 点击是**累计量**（报告 02/08），跨时点不可比还叠加**曝光分母**与**书龄**；
- 跨书比较必须先切曝光档（报告 08 的做法），那是**全库口径**，端上只有一两本书、没有分母；
- `click_delta_30d` 是跨书的派生量，同样需要分母。

**但单书自己的曲线是合法的**：同书跨时点比较，虽然仍受书龄影响，作者关心的是
"我的书这周有没有涨"，而且基线是自己（起点为 0 或首日值），不是别人。
**必须标注"累计量，非独立日更"**——它反映的是累计曝光的增长，不是当天有多少新读者。

**热力图的关系**：热力图专指**更新量**（§1.4、§4.5），吃逐日 `Δwords`；
点击一律走折线，**不共用一张图**。

**低点击书的额外处理**（仅 PC 版通路）：人气显示可能不足 0.1 万（端点档案只测到
`11899.5万` 一种形态）。对这类书，绝对值折线仍可画（点可信），但 UI 标注"精度受限"，
且不参与任何跨书比较。App API 通路无此问题。

> **口径不变的部分**：`observations.clicks` 写入绝对值与 `user_stats.click_delta_30d`
> 恒 NULL **不矛盾**——前者是原始观测，后者是跨书派生差值（无论哪条通路都不算）。

### 4.4 评论/长评：精确整数，可做变化观测

`op=getcomment` 实测（端点档案 §6）：

| 项 | 值 | 说明 |
| --- | --- | --- |
| 短评数 | 82,291 | `ShortCommentNum`，精确整数 |
| 长评数 | 452 | `LongCommentNum`，精确整数 |
| 陷阱 | 返回的第一条是站方置顶公告（`CommentID=0`） | **解析时必须过滤**，否则计入评论数会错 |

评论/长评是**精确整数**，没有点击的量化问题，因此可以：
- 记录到 `observations.short_comments` / `long_comments`；
- 计算 30 天 delta（若需要，扩展 `user_stats`）；
- 画变化曲线（用户可切换绝对值/变化量）；**评论不进热力图**（§1.4）。

**这推翻了 05 §8.1 "v1 不抓评论"的决定**——其两条理由（无写回目标、逐本查代价）在观测列表场景中都不成立：
写回目标有了（`observations` 新列），逐本查正是作者对自己的一两本书的场景。
回填见 §10。

### 4.5 更新量：第一指标，及其归因规则

`words` 是累计总字数、**只增不减**，`Δwords` 才是"某天写了多少"。
它不进任何热度榜（书龄差异太大），但它是全勤奖的判定基础（§2.5），
在作者工作台里的优先级高于所有热度指标。

| 用途 | 做法 |
| --- | --- |
| 作者自己的书 | 更新热力图（§1.4）+ 全勤达标看板（§6.1）——最核心功能 |
| 同期对照 | 切到 `peer` 书看更新节奏；字数停滞也是"竞品是否弃坑"的情报 |
| 不做什么 | **字数不进任何热度榜、不做跨书量级比较**（书龄差异太大） |

#### 4.5.1 从累计字数到"某日更新量"：两套来源，主备分明

**2026-11-17 修订**：原稿只有一套来源——从 `observations` 的 `words` 差分推断，
并为此设计了三档置信度与"数据缺口"概念。官方 App API 的
`GET /novels/{id}/chaps` 提供**逐章 `addTime` + `charCount`**，
**章节本身就是"哪天写了多少字"的事实记录**——推断不再是主方案。

| | **主方案：章节时间戳** | **回退方案：观测差分** |
| --- | --- | --- |
| 数据来源 | App API `chaps` 逐章 `addTime` + `charCount` | `observations.words` 按自然日聚合后差分 |
| 单日更新量 | **直接可读**：该日所有章节的 `charCount` 之和 | 推断：当日累计值 − 上一个有观测日的累计值 |
| 断更识别 | **精确**：没有章节的自然日 | 只能靠"有观测且 Δ=0"间接判断 |
| 历史补齐 | **一次性**：拿到章节清单即得全历史 | 需长期积累，**越早期越缺** |
| 「数据缺口」概念 | **不存在**（章节是历史事实，不依赖用户是否打开 App） | **存在**：用户没开 App 的天数就是缺口 |
| 全勤单日判定 | **可做**（接近官方口径） | 不可做（缺口期） |
| 体积代价 | 744 章 222 KB、1,740 章 489 KB（一次性） | 0 |

**主方案的实现要点**：

1. 章节按 `addTime` 的**自然日**分组，每组 `charCount` 求和 → 该日更新字数。
2. **过滤三类章节**：`isRubbish`（废章）、`auditStatus` 待审态（`1`）、
   以及是否为"正常章节"（官方口径，含义待查）——**待审章是否计入官方全勤判定未知**，
   必须单列标注，不能静默计入（05 §8.3）。
3. `isVip` 单独统计——官方全勤对 VIP 章节的计法可能不同，UI 分开展示。
4. 章节清单**一次性抓取并落库**，之后只需增量更新（详情 0.7 KB）。
5. 章节 `charCount` 是**正文口径**，比详情页总字数更接近官方计法（§4.5.2）。

**回退方案（无 App API 时的降级）**：保留原稿的全套规则——
归因单位是**自然日**而非"相邻两次观测"（因为 `poll_interval` 可低至 6 h，同一天会有多次观测，
按相邻观测差分会使 6 h 间隔落在归类规则的空白区，且同一天的增量会被拆成 4 格）：

1. 把每个 `nid` 的观测按**自然日（本地时区）**分组，取每日**最后一次** `words` 作为该日累计值；
2. 某日更新量 = 该日累计值 − 上一个**有观测的自然日**的累计值（不是"昨天"）；
3. 该差值记在**后一个自然日**的格子里。

| 情形 | 归因 | 置信度 |
| --- | --- | --- |
| 相邻两个**有观测的自然日**相差 1 天 | `Δwords` 全部归到后一日 | **高**——可近似为"那天写的"；同日 6 h 多次观测已被合并 |
| 相差 N 天（N > 1） | `Δwords` 归到后一日，但标注"**含 N 天累计**"，不伪装成单日量 | 低——只能看趋势，不能判单日全勤 |
| 相差 > 7 天 | 中间格标为"数据缺口"，**不染色**（空白不是断更） | 无——不可判定 |
| 某日有观测且 `Δwords = 0` | 该日标"无更新"——真断更信号，要与"数据缺口"区分开 | 取决于观测连续 |
| 同一天多次观测但 `words` 无变化 | 只记一条日值，不产生额外格子 | 高 |

**关键**：回退方案下 `observations` 不保证每天有一个自然日的值，
用户没打开 App 的那几天就是缺口——
UI 必须把"没观测到"和"没更新"区分开，否则会把用户没打开 App 的那天误判成断更，
这是对这个功能最致命的误导。**主方案（章节时间戳）从根上消除了这个歧义。**

**对全勤看板的影响**：

| | 主方案（章节） | 回退（观测差分） |
| --- | --- | --- |
| 月累计 | 可算 | 可算（缺口期增量归到下一个有观测日，月内总量不丢） |
| 单日达标判定 | **可做** | 不可做——看板须显示"N 天未观测，本月达标状态不确定"，而非给出确定结论 |

#### 4.5.2 与官方判定的差距（可收窄但不可消除）

| 差距 | 影响 | 状态 |
| --- | --- | --- |
| 官方按"正常章节正文"计字数；回退方案只有详情页总字数（含人设/背景等） | 可能高估 | **主方案下大幅收窄**：章节 `charCount` 就是正文口径（§4.5.1） |
| 待审章节（`auditStatus=1`）是否计入官方判定 | 未知 | **必须单列标注**，不静默计入 |
| VIP 章节的计法 | 未知 | 分开展示，不混算 |
| 官方按月结算、允许一次断更；我们是逐日推算 | 全勤看板是**过程预警**，不是结算结果 | 不可消除——**UI 固定标注"估算值，非官方判定"** |
| 观测缺口 | 仅回退方案存在 | 主方案下不存在 |

无论哪套来源，**UI 固定标注"估算值、非官方判定"**——我们能算得越来越准，
但不能声称与官方结算一致。

字数日增 `Δwords/Δdays` 作为复合指标（§4.7）保留，但**它的首要用途是喂热力图与全勤看板**，
不是画一条普通折线。

### 4.6 三态判据仍先于解析

后台爬取同样遵守 05 §4.3 的三态判据：死亡/僵尸页**不写成绩观测**，只标注状态。
作者的书若被下架，工作台应显示"官方页面当前不可读（上次记录：…）"，而不是画一条断崖到 0 的假曲线。

### 4.7 复合指标：端上现算，不写表

官方给的是原始计数，作者要的是**比值与变化率**。二者之间差一层现算。

**存放策略：现算，不写表。** 两个理由：
1. 规模不同——观测集 ≤100 本 × 180 天 ≈ 1.8 万行，端上算比值是毫秒级；
   03 §3.1 的 "赞藏比必须预计算"针对的是**全库 24.6 万行 × 索引排序**（44.9 ms → 0.056 ms），
   这里没有全库排序需求，照搬预计算反而引入"定义改了要迁移"的负担。
2. 定义会迭代——复合指标集合是产品层可调的，现算才能加一个指标不改 schema。

| 复合指标 | 公式 | 门槛 / 限制 | 用途 |
| --- | --- | --- | --- |
| 赞藏比 `pr` | `praises / favs` | **`favs ≥ 10`** 才显示（02 §2.1、03 §4.2） | "留下的人有多愿意表达"；同期对照核心指标 |
| 评论率 `cr` | `(short_comments + long_comments) / favs` | `favs ≥ 10` 且两列都抓到 | 深度互动密度；比赞藏比更稀有、更稳定 |
| 收藏日增 | `Δfavs / Δdays` | 按自然日聚合后（§4.5.1），相邻有观测日相差 1 天才算 | 精确整数，可作变化观测 |
| 点赞日增 | `Δpraises / Δdays` | 同上 | 同上 |
| 评论日增 | `Δ(short+long) / Δdays` | 同上，且两日都抓了评论 | 精确整数，最适合做变化曲线 |
| 字数日增 | `Δwords / Δdays` | 按自然日聚合，不设门槛 | 更新追踪，**不进热度比较**；首要用途是喂热力图（§4.5） |

**明确不做的复合指标**：

| 不做 | 理由 |
| --- | --- |
| 收藏转化率 `favs / clicks` | 曝光分母效应（报告 08）；PC 版的 ±500 量化叠加其上，双重不可信。报告 19 证实低曝光下是伪信号。**App API 通路下曝光分母仍是问题，故仍不做** |
| **跨书**点击日增 / 点击变化率 | 累计量需曝光分母分档才能跨书比，端上没有分母（§4.3）。**单书**点击日增曲线在 App API 通路下可做（§4.3） |
| 跨世代复合指标比较 | 累计指标受书龄混杂（报告 02/08）；只在 `role='peer'` 且 `est_year` 相近时才并排（§1.5） |

**赞藏比的两条红线**（报告 08 §5、报告 19 §4.3）：

1. **`favs < 10` 不显示**——分母小会让比值爆表。这与种子 `books.pr` 的 NULL 规则一致（02 §2.1），
   作者端不能放宽；放宽后"我的赞藏比 8.0"毫无意义。
2. **只对同期、同字数档的书比**——报告 19 实测短篇里赞藏比方向**反转**
   （同字数档 × 同完结时长档内，pr-top5% 收藏中位 2.1 vs pr-bot5% 22.1），
   低曝光样本上成了反向指标。因此对照视图里的赞藏比必须带"同期对照"标签，
   且不做"谁更好"的结论；`est_year` 未知或定年差 > 2 年的对照书不进赞藏比图（§1.5）。

**与种子 `pr` 的关系**：若书在种子里，工作台可并排显示"种子赞藏比（2026-05-03）"
与"本机现值（观测算）"，但**不计算二者的差值**——跨时点的累计量比值不可横比
（同 §4.3 点击绝对值的逻辑：点可信，差不可信）。

## 5. 后台定期爬取（U5）

### 5.1 与"全库轮转"的本质区别

01 §6 / 06 §2 禁止的是**无差别、系统发起的全库后台刷新**。本节定义的是**用户显式订阅、
作用于自己书目的小集合、可随时关闭**的抓取——两者在请求量、意图、可控性上完全不同。

| 维度 | 全库 7 天轮转（禁止） | 观测列表订阅（本篇 U5） |
| --- | --- | --- |
| 发起方 | 系统自动 | **用户显式开启** |
| 对象 | 全库 24.6 万本 | `watchlist` 中的书（≤100，实际常 1–3） |
| 日请求量 | 数百万 | ≤300（实际上限远低于此） |
| 用户可关闭 | 不可 | **可随时 `poll_enabled=0`** |
| 与兴趣的关系 | 无关 | 完全由用户兴趣驱动 |

**06 §1 的四类"更新"新增第五类 U5**：用户订阅的后台观测爬取。
06 §2 "不叠加第二层数据调度"的论断收窄为"**不叠加全库数据调度**"——U5 是有边界的例外。

### 5.2 触发与频率

| 项 | 规则 |
| --- | --- |
| 触发条件 | `poll_enabled=1` 且 `now - last_poll_at >= poll_interval` |
| 检查时机 | App 启动时一次 + 前台活跃期间的定时器（如每 30 分钟检查一次） |
| 后台续跑 | **不做真后台服务**：iOS/Android 的后台执行受限且不可靠；App 未运行时不爬取，下次启动补一次（不补历史缺口） |
| 并发 | 串行，每次一本；两本之间至少 1 s（共用 §5.3 限速器） |
| 前台优先 | 用户正在看详情页时，后台任务暂停——前台抓取优先（05 §6.1） |

### 5.3 限速器集成

U5 与前台抓取、搜索共用 05 §6.1 的**全局单例限速器**，不另起实例：

| 规则 | 值 |
| --- | --- |
| 端点间隔 | ≥1 s，三端点（移动版/PC/评论）共享 |
| 队列优先级 | 前台详情页 > 搜索 > U5 后台观测 |
| 队列溢出 | U5 任务**直接丢弃**（下次启动重试），不积压、不挤占前台 |
| 日配额 | U5 独立上限 300 请求/日（§3.3），与搜索 200 次/日分开计数 |

### 5.4 失败与降级

| 情形 | 处理 |
| --- | --- |
| 三态判为死亡/僵尸 | 标注状态，**不写观测**，跳过该书本次爬取；不重试到死 |
| 网络/限流失败 | 记录 `last_poll_at` 为本次尝试时刻（避免反复重试打爆限速器），下次周期再试 |
| 解析失败 | 结构化 `ParseError` 落本机日志，UI 标注"本次抓取失败"，不写半截数据 |
| 连续失败 N 次 | 建议 N=3；暂停该书订阅并提示用户检查，不自动无限重试 |

产品可以诚实地告诉作者："官方只给你收藏变化，这里能看到你的**每日更新热力图与全勤达标预警**——
这直接关系你的全勤奖金——以及全部指标的逐日走势、和同期作品的同轴比较、自己算的复合指标。"

## 7. 数据模型变更汇总

本次对既有表结构的改动（均落在 `user.db`，不动 `seed.db`）：

| 变更 | 表 | 内容 | 迁移影响 |
| --- | --- | --- | --- |
| 新建 | `watchlist` | §3.1 的 10 列 + 2 索引（含 `role`） | 纯新增，无风险 |
| 加列 | `observations` | `short_comments` / `long_comments` | v2 迁移，`ALTER TABLE ADD COLUMN`，默认 NULL |
| 恢复写入 | `observations.clicks` | 从恒 NULL 改为对订阅点击的书写入绝对值 | **不改表结构**，只改写入逻辑（§4.3） |
| 不变 | `user_stats.click_delta_30d` | 保持恒 NULL | 与"跨书点击变化不做"一致（§4.3） |
| **不新增** | 复合指标（赞藏比 / 评论率 / 日增） | **端上现算，不落表、不加列** | 定义会迭代；观测集 ≤1.8 万行，现算是毫秒级（§4.7） |
| **新建** | `novel_chapters` | 章节快照（App API `chaps`），见下 | 纯新增，无风险 |

### 7.1 `novel_chapters`：章节快照（新建）

更新热力图的主方案需要逐章的「哪天写了多少字」，这是**章节级事实**，
与 `observations` 的「逐本当前值时间序列」语义不同，**必须分表**。

```sql
CREATE TABLE novel_chapters(
  nid         INTEGER NOT NULL,
  chap_id     INTEGER NOT NULL,   -- App API 的 chapId
  added_at    TEXT,                -- 章节创建时间 ISO 8601（主键归因依据）
  updated_at  TEXT,                -- 章节更新时间
  char_count  INTEGER,             -- 本章字数（正文口径）
  is_vip      INTEGER,             -- 0/1
  is_rubbish  INTEGER,             -- 0/1
  audit_status INTEGER,             -- 1 待审 / -1 正常（语义待查）
  fetched_at  INTEGER NOT NULL,    -- 本机抓取时刻 unix 秒
  PRIMARY KEY(nid, chap_id)
);
CREATE INDEX idx_chap_added ON novel_chapters(nid, added_at);
```

| 字段 | 用途 |
| --- | --- |
| `added_at` | **热力图的归因键**：按自然日分组求 `char_count` 之和 |
| `char_count` | 该日更新字数；**正文口径**，接近官方全勤计法 |
| `is_vip` / `is_rubbish` / `audit_status` | 分开展示——**待审章是否计入官方判定未知**，不能静默计入（§4.5.2） |
| `fetched_at` | 区分"章节事实"与"本机何时知道它"；**不是归因依据** |

**体积**：一本 1,740 章的书约 489 KB JSON；落库后每行约 60–80 B → 约 130 KB/本。
`watchlist` 上限 100 本 → 最坏约 13 MB，**可接受**；且只在订阅书上抓。

**清理**：与 `observations` 同保留期（180 天，02 §7 #2）——但**章节事实是历史**，
清理依据应是"该章已超出热力图可回溯窗口（默认 12 周）"，而非抓取时间。

**注意一处协同**：06 §4.2 此前把 `clicks` 列为"v1 恒 NULL、保留给 v2 恢复点击观测"的死列。
现在恢复时**不删列、不加列、不改 schema**，只是开始写入——这正验证了 v1 保留该列的价值。
回填见 §10。

**作者自己的书是否在种子里**：无所谓。`watchlist` 只存 `nid`，
若该书在 `books` 里则工作台可显示种子基线作对照；若不在（`discovered` 或全新书），
则只显示观测值，标注"本机收录，无基线"——与 04 §5.3 口径一致。

## 8. 明确不做

| 不做 | 原因 |
| --- | --- |
| 全库后台轮转 / 无差别定时刷新 | 01 §6、06 §2；U5 只作用于订阅的小集合 |
| 服务端观测上报 / 作者账号 / 云同步 | 无服务端（01 §6）；数据只在本设备 |
| **跨书**点击变化榜 / `click_delta_30d` / 跨书点击比较 | 累计量跨书比需曝光分母分档（报告 08），端上没有分母。**单书曲线在 App API 通路下可做**（§4.3） |
| 收藏转化率 `favs/clicks` | 曝光分母效应，两条通路下都不可信（§4.7） |
| 跨世代复合指标比较 / 同期总排名 | 累计指标跨世代不可比；不同指标领先者不同（§1.5、§2.4） |
| 全库热力图 | 全库时序数据不存在，画出来是编造（§6.2） |
| 作者功能写回 `books` / 改分位分母 | 分位参照系固定（02 §5.1、05 §5.3） |
| 真后台服务（App 未运行时爬取） | 平台后台执行受限不可靠；改为下次启动补一次（§5.2） |
| 用户自定义极短爬取间隔 | 最小 6 h 硬下限，防止打爆限速器（§3.1） |
| 把评论正文存下来 | 只取计数；正文是版权内容，且无分析价值（§4.4） |
| **取章节正文** | `/Chaps/{id}?expand=content` 实测 401/507 无权限；即便将来有权限，本产品也不取正文（05 §3.5） |
| **用 App API 取代 web 端基线** | App API 无契约、随时可能变；web 端稳定。App API 只做增强，失效即降级（05 §3.5） |
| **用 App API 的 `addTime` 替换项目定年** | 定年继续用 `log(nid)` 反推；`addTime` 只作旁证（05 §3.6） |
| **引入用户账号 / cookie 来访问 App API** | App 内置固定常量即可；引入用户凭据会带来凭据保管与合规负担（05 §3.5） |

## 11. 本篇的定位

01–06 回答的是"这个 App 是什么、怎么造"。
本篇回答的是"**除了读者，谁还会用、为什么用**"——
它是第一份以**用户价值**而非**技术结构**为主线组织的设计文档。

六篇技术文档里反复出现"不做"：不做全库、不做后台、不做服务端、不做点击变化。
本篇没有推翻这些判断的实质，只是把它们的前提说得更精确：

> 不做的是**无差别、系统发起、全库规模**的事；
> 用户**显式订阅、作用于自己书目的小集合**的事，不仅该做，而且是核心竞争力。

这就是作者工作台存在的理由。

**"四次补充"（App API 通路）也没有推翻任何"不做"的实质**，只是把精度与数据可得性的
前提说得更精确，并加了一条新的底线：

> App API 是**可选增强**——它无契约、随时可能变；
> web 端接口才是稳定基线，移动版 HTML 必须始终可用。
> 增强通路失效时，功能**降级而非残缺**（05 §3.5）。
