## 3. App API 供给能力（实测契约）

| 通路 | 一次请求 | 字段 | 体积 | 适用 |
| --- | --- | --- | --- | --- |
| `GET /novels?size=50&page=N` | **50 本** | **18 基础字段** | ~26 KB | 批量补新书书目 |
| `GET /novels/{id}?expand=tags,sysTags,intro` | **1 本** | 18 基础 + `expand` 嵌套 | ~2 KB | 逐本补标签/简介 |
| `GET /novels/{id}` | 1 本 | 18 基础 | ~700 B | 单本刷新 |

**18 基础字段**：`novelId` `novelName` `authorId` `authorName` `addTime` `lastUpdateTime` `markCount` `viewTimes` `charCount` `point` `isFinish` `signStatus` `typeId` `categoryId` `isSensitive` `allowDown` `novelCover` `bgBanner`。

**关键机制**：tags 不是独立端点，是 `expand` 展开参数；返回时嵌在 `data.expand` 里：

```json
"expand": {
  "tags": [],
  "sysTags": [{"sysTagId": 10, "tagName": "战斗"}, {"sysTagId": 398, "tagName": "搞笑"}],
  "intro": "……全文简介……"
}
```

**字段映射**（App → 种子 `books`）：

| App 字段 | 种子列 | 备注 |
| --- | --- | --- |
| `novelId` | `nid` | 主键 |
| `novelName` / `authorName` | `title` / `author` | 作者名同名即同人（`authorId` 是新增维度，但种子无此列） |
| `typeId` | `genre` | 需按 `tid→中文题材` 码表转换（9 值） |
| `signStatus` | `price_type` | `VIP`/`签约`→对应中文 |
| `isFinish` | `status` | bool→`已完结`/`连载中` |
| `markCount` / `viewTimes` / `charCount` | `favs` / `clicks` / `words` | 精确整数 |
| `lastUpdateTime` | `updated_at` | 秒级，直接可存 |
| `novelCover` | `cover_url` | 含 `YYYY/MM/` → 仍是运营时间 |
| `sysTags[].tagName` | `tags` / `book_tags` | 逐本 expand 才有 |
| `addTime` | **见 §4 决策点** | **不直接进定年** |

**分位五列**（`fav_pctl/click_pctl/praise_pctl/pr/pctl_pr`）API 不提供，只能在构建期从 universe 算——新书不在 universe 里，故分位为 NULL（同 licensed 的处理）。

## 4. 核心决策点：新书的 `est_year` / `est_date` 怎么给？（须拍板）

这是方案**唯一真正的拦路问题**，因为它触及既有红线：

- 种子 `est_year` 上界是 2025，分位按世代分组；新书是 2026 上架。
- 报告 20 已验证：`log(nid)` 定年在**外推段（nid>774,850）误差 131–153 天**，不可用。
- `01-tech-stack.md` §3.5 / `05-detail-fetch.md` 多次定案：**addTime 不进定年，只作独立旁证**。

三个口径供选择，**方案默认按 X 实施以守红线**：

| 口径 | 做法 | 收益 | 代价 |
| --- | --- | --- | --- |
| **X（推荐，守红线）** | 新书 `est_year/est_date` 仍走 `eras.estimate(nid)`；`addTime` 只存旁证、不参与定年 | 不动定年体系；符合所有既有设计 | 外推段误差 131–153 天，`est_year` 可能落 2025 或 2026 |
| Y（破红线） | 用 `addTime` 直接填 `est_date`，`est_year=2026`，`est_conf='app_addtime'` | 日期精确 | 打破"addTime 不进定年"，需重新定案并同步 9 份报告的相关表述 |
| Z（限域折中） | `est_year` 用 addTime 年份**仅用于展示分组**，不进统计 universe；分位 NULL、不进 A 类榜 | 展示合理又不污染统计 | 语义上仍是 addTime 参与定年字段，需明确标注 |

> 无论哪种口径，新书都按 **supplement 批次**处理：分位五列 NULL、不进 A 类榜与世代统计、可搜索/详情/书架可见——与 licensed 47 本的隔离方式一致。这样即使 est_year 有误差，也不影响任何排行榜口径。

## 5. 方案设计

### 5.1 范围（两批，优先级分明）

| 批次 | 内容 | 来源 | 优先级 |
| --- | --- | --- | --- |
| **S1 新鲜度补入** | 上界后新书（2026-05-04 起逐月） | 列表 50/次 + 入选书逐本 expand 补标签 | **P0，解决"0 覆盖"** |
| S2 字段增强 | 现有种子 30,878 本补 `authorId` / 秒级 `addTime` / 精确 `viewTimes` | 逐本 detail | P1，收益小（3 字段），**建议暂缓** |

### 5.2 S1 构建管线（改动点）

不重写现有流程，在 `build_seed.py` 之后追加一个 **supplement 阶段**：

```
build_csv.py → build_frames() → [现有 30,878 本 base]
                                      ↓
              supplement_from_app_api(new_books.jsonl)
                                      ↓
              合并 → 新 books 表 + book_tags + seed_meta 增补计数
```

1. **采集**：按 `tid` 九类，从最新页往前翻，直到 `addTime ≤ content_end` 的连续页出现即停（列表按更新时间降序，新书集中在前部）。增量去重按 `nid`。
2. **选书**：新书全量补入（因数量是万本量级、且冷门书正是探索覆盖所需），或按 §5.3 的候选规则筛。
3. **标签**：仅对入选书逐本 `expand=tags,sysTags,intro`，`sysTags[].tagName` → `book_tags`。
4. **分位**：NULL（新书不在 universe）。
5. **元信息**：`seed_meta` 增加 `supplement_count` / `supplement_content_end`，`manifest.json` 同步；**schema 版本与 24 列不变**（不新增列，用 `est_conf` 承载口径标记 if Y/Z）。

### 5.3 选书策略（待定）

- **方案 A（全量补入）**：万本量级全收，体积增量约 2–3 MB（gz），探索覆盖最完整。
- **方案 B（按现行口味筛）**：复用 `seed_set()` 的思路，但阈值要重定——新书收藏中位仅 4，`Top 20k favs` 对它们几乎不适用。建议改用「每月每题材 Top N + 近 90 天更新」的滚动池。

> 倾向 A：新书数量可控、冷门书正是探索价值所在；B 的阈值需重新标定，容易重蹈"遗漏偏短新"的覆辙（报告 10）。

### 5.4 验证

- 沿用 `validate.py` 的断言风格，新增：supplement 数量、nid 零重复、分位 NULL 一致性、tags 行数、`content_end` 前移后的不变量。
- 手工抽检：从新书里取当月 Top5，核对标题/作者/字数/标签与详情页一致。

# 附录 A：战略转向——从「堆新书」到「深榜」（2026-11-17 追加）

> **本附录的优先级高于正文 §0–§8**。用户 2026-11-17 明确观点：
> 「种子装大量新书是**无用数据**——推荐新书官方 App 做到了极致。我们能做的是**扩展官方榜单**：
> 官方大部分榜单只有 top50，如果我们能给出 **top200**，就可以和官方 App 竞争。」
> 据此，正文 S1「新鲜度补入」**降级为实现深榜的副产品，不再是目标本身**。

## A.1 为什么这个判断成立（档案证据）

| 榜 | 官方深度 | 来源 |
| --- | --- | --- |
| web 六榜（人气/收藏/新书/日轻/热销/月票） | **top20** | `sfacg-live-ranks.md` §1 |
| `MonthlyBoy.ashx` 历史月票榜 | top20；新书榜 **top10** | 同上 |
| App `/novels?filter=recom` | 实测 **20 条**（非 50） | 本次请求 |
| App 全局日/周/月榜 | **端点不存在**（`dayRank`/`weekRank`/`monthRank` 全无，`filter=dayRank` 返回 0 条） | `sfacg-app-api.md` §4.1 + 本次请求实测 |
| App `/specialpush` | 77 推送位，每位置 1–100 条，是运营位不是排名榜 | `sfacg-app-api.md` §4 |

**结论**：官方榜单的两层天花板——**深度浅（top20）**、**App 侧无全局榜端点**。这不是我们爬得不够，是官方公开的就这么多。这正是可竞争的空档。

## A.2 我们能不能做出 top200？（离线验证，已答：能）

用本地已采的 App 枚举（114,381 条，魔幻完整 + 玄幻部分）模拟「近 30 天新书榜」：

- 近 30 天上界前新书样本 **481 本**（魔幻 362 / 玄幻 119）。
- 按 `markCount`（收藏）排序：**top50 门槛 157、top200 门槛 8** → 说明榜尾还有充足的书可排，**200 名不是凑数**。
- 按 `viewTimes`（精确整数）排序：top50 门槛 10,768、top200 门槛 374。
- 两种口径的 top10 高度重合（nid 773281 / 774426 / 773746 / 774244 / 774567…）——与官方新书榜的头部逻辑一致，但**我们能把榜延伸到 200**。

> 关键：**深榜不需要新数据**。App 列表端点每条自带 `addTime`/`markCount`/`viewTimes`，
> 而官方只把 top20 摆出来。我们的优势是**有全库本地数据 + 可枚举官方书目**，
> 能按任意时间窗 / 题材 / 指标组合重排，给出官方不提供的深度与切分。

## A.3 产品形态建议（供拍板）

| 方案 | 榜单内容 | 数据来源 | 相对官方的差异 | 工作量 |
| --- | --- | --- | --- | --- |
| **D1（推荐）** | 近 30 天新书 Top200，按收藏/点击/字数分三榜；可切题材 | 本地宽表 + App 枚举补新书 | 官方新书榜 top20 且无数值；我们 **10 倍深度 + 带数值 + 可切分** | 中（需补枚举） |
| **D2** | 全库「世代内 Top200」（按 `est_year` 分组，用分位五列） | **纯本地 24 万宽表，零请求** | 官方没有任何按世代的榜；这是报告 03/18 的独有能力 | **低（现有数据即可）** |
| **D3** | 历史月榜扩展：每月 Top200（官方只存 top20） | `MonthlyBoy.ashx` 仅有 top20，**无法扩展到 200** | ❌ 数据源 ceiling 就是 20，做不到 | — |

**D2 尤其值得关注**：它**不依赖任何新采集**——分位五列与 `est_year` 已在种子里，端上按世代筛 + 排序就是 Top200。这是"现在就能做、官方做不到"的差异点，建议先做 D2 验证产品价值，再投入 D1 的枚举成本。

## A.4 对种子设计的连带影响

1. **种子不必堆新书**。种子的作用是"深榜的本地分母 + 探索池"——需要的是**覆盖各题材/世代的代表书**，不是最新 3,600 本。正文 §5.3 选书策略应改为"**按深榜入选反推种子**"：把 D1/D2 各榜 Top200 的并集纳入种子，而非全量补入。
2. **定年决策点（§4）随之降级**：D2 用现成 `est_year`，D1 新书榜用 `addTime` **只做时间窗筛选、不做定年**（不触红线）——两个方案都绕开了 X/Y/Z 的冲突。
3. **体积更小**：Top200×N 榜并集约几千本，比全量补新书省一个数量级。

## A.5 待拍板（替代正文 §8 的优先级）

1. **先做哪个**：D2（零请求、立刻可做）还是 D1（需补枚举）？建议 D2 优先。
2. 榜单深度定为 200 还是 500？（本地数据显示新书榜 top200 门槛仅 8 收藏，500 名会开始失真）
3. 是否接受"深榜数据随 App 枚举快照过期"——需接受定期重采（月度）才能维持新鲜。

> 附录同样**未发起任何采集请求**（除 §A.1 标注的 2 次参数验证与上次实测的 1 次，共 3 次只读 GET），未修改任何设计文档。

| 项 | 值 |

## 附录 D：小说形式字段 `books.form`（2026-11-18 定规则，未实施）

> **本附录与附录 C 同属「只写规则、种子重建并入 release 优化种子统一做」**。
> 用户 2026-11-18 观察：官方 `genre` 只按**主题**分 9 类，不按**形式**分；
> 这造成榜单噪声——成绩好的对话小说会混进长篇榜、中篇与短篇互相挤压。
> 本附录在 `books` 主表加一列 `form`，做**互斥单值**分类，优化榜单过滤。
> **可执行权威口径见 `app/docs/13-form-definitions.md`**（优先级、伪代码、现算分布）；
> 本附录保留决策理由与论证，13 是其开发落地细化。

### D.1 问题：主题轴无法过滤形式噪声（本地实测）

9 大 `genre` 全是主题、无形式轴（原始 jsonl 的 `categoryId`/`typeId` 全 `None`）。
按累计 favs 排序时，不同形式的书混在同一榜，产生两类噪声：

**噪声一：对话小说污染长篇榜。** 对话征文 10,304 本里 **208 本 >15 万字**、
favs 中位 **1,384**——只按字数分它们会进长篇榜。对只看长篇的用户，
这些"每章 500 字、整本很长"的对话小说是明显噪声。

**噪声二：中篇并入短篇会让真短篇永无出头之日。** 若按官方 2026 口径把中篇并入短篇
（1–15w 一刀切），favs Top200 里 **197 本是中篇、仅 3 本是真短篇（1–3w）**。
字数极大影响累计指标，中篇（3–15w）数字天然高于纯短篇，合并等于让短篇永远拿不到推荐位。

| 组 | 本数 | favs 中位 | 签约率 |
|---|---:|---:|---:|
| 长篇征文 | 29,211 | 11 | 19.0% |
| 中篇征文 | 6,432 | 4 | 4.0% |
| 短篇征文 | 5,231 | 4 | 3.1% |
| 字数 >30 万字档 | 8,594 | 3,465 | 80.7% |

短篇 favs Top100 中 31% 带征文标记、0 本 featured、12% 为 2023+ 新书——
运营位完全不覆盖短篇，印证「短篇流量靠征文获奖者与新书」。

### D.2 官方口径变更（外部证据，已核原文）

- 2023 第十一届：三档——长篇 ≥15 万、中篇 3–15 万、短篇 1–3 万；
- 2026 第十四届：只剩两档——长篇计划 ≥100 万（截稿前 ≥5 万）、短篇 1–15 万，
  中篇整档取消，原中篇区间并入短篇。
- 2026 征文规则第 8 条列三种形式：「常规小说、对话小说、互动小说」。

**我们不完全照搬官方**：官方为投稿评审取消中篇，**我们为榜单过滤必须保留中篇**——
D.1 噪声二证明合并会毁掉短篇榜。形式字段取 `短/中/长/对话/IP合作` 五值，
按用户约定：**互动并入对话**（子集、后期才独立、用户不喜欢→失败原因之一），
**IP 合作单列**（官方联动/合作征文）。

### D.3 字段定义（books 主表加列，24 → 25 列）

取值（互斥单值）：short / medium / long / dialogue / ip_collab

### D.4 判定规则（可复现，全部离线）

**取值定义**（边界已由用户 2026-11-18 更新，**以 `13-form-definitions.md` 为准**：
短篇 ≤5 万、中篇 5–15 万、长篇 >15 万；下列 3 万为当时的初始提案值）：
- `short` 短篇：字数 ≤3 万字（含 <1 万字未成形作品——用户定归入短篇，不设 tiny 档）；
- `medium` 中篇：3万 < 字数 ≤15 万字（**保留中篇档**，理由见 D.1）；
- `long` 长篇：字数 >15 万字；
- `dialogue` 对话：对话/点鸭征文 + 报告 22 形态判据（互动并入此档）；
- `ip_collab` IP合作：**征文名称命中已知 IP 合作/联动征文名单**即判定（确定性规则，见下）。
  已知名单（六类，universe 内 **935 本**）：楚楚动仁=咪咕×SFACG、崩坏3、
  少女前线、龙之谷（游戏联动）、失业魔王、英雄再临——均为历史征文。
  **「超新星杯」不是 IP 合作，是站内短篇赛事**（464 本，`contest` 含"短篇"），
  按字数/征文命名归入 `short`，不计入本档——报告 06 §4 已明确「超新星杯为站内短篇赛」。

**IP 合作判定 = 征文名称精确匹配（用户 2026-11-18 定）**。用户理由：
「SFACG 近几年没有过 IP 合作征文」——即这类征文是**封闭的历史名单**（集中在
2016–2019，如崩坏3 联动 2019-01、楚楚动仁 2016），近年无新增，故名单确定、
不会增长、可按 `contest` 名称精确命中。这条规则带来三个后果：
- **确定性判定**：命中名单→`ip_collab`，无需抽样、无需启发式、无优先级争议；
- **标题 IP 词不是 IP 合作判据**：米哈游系 IP 词（芙宁娜/钟离/琪亚娜等）是
  对话/互动小说的同人特征（报告 22 §4），不属于 IP 合作征文；抽样表里 IP 合作组
  「标题 IP 词 26.1%」只是伴随现象，不能拿来做判据；
- **优先级争议只剩「对话 vs 短篇」**：抽样已证 IP∩对话=0、IP∩短篇=0，IP 合作
  独立成档，不进入重叠抽样。

**字数兜底边界**：征文命名优先 → 无命名按字数 3万/15万 切档（2023 口径，
因数据集主体是旧口径年份；官方 2026 的 15万单切点会毁短篇榜，不采用）。
征文命名仅覆盖 16.9%，**83% 靠字数兜底**——本方案最大软肋，需标注「形式为估计值」。

**优先级：待查，不写死（仅剩「对话 vs 短篇」）。** 用户 2026-11-18 初判
「短篇、IP合作、对话特征高度相似，需抽样查证后再定优先级」；但 IP 合作已由
征文名称确定性判定（见上），不再需要抽样。抽样结果（见下）显示对话与短篇
征文标记几乎互斥，优先级只在一处重叠上有分歧：

| 类别 | 本数 | 字数中位 | 同人 genre | 标题 IP 词 |
|---|---:|---:|---:|---:|
| 对话/点鸭 | 10,304 | 4,062 | 46.2% | 18.4% |
| IP 合作（6 类，不含超新星杯） | 935 | 10,101 | 0% | 26.1% |
| 短篇征文（含超新星杯 464 本） | 5,227 | 7,943 | 2% | 1.7% |

> 数字为本地 `out/novels.csv` + `eras` 定年现算（universe：非授权、est_year 2007–2025）。
> IP 合作口径为六类名单（楚楚动仁/崩坏3/少女前线/龙之谷/失业魔王/英雄再临），
> **不含「超新星杯」**——后者 464 本归入短篇征文组（该组口径即 `contest` 含"短篇"=5,227 本）。

重叠实测：对话∩IP=0、IP∩短篇=0、三者都中=0，**仅对话∩短篇=357 本**（占对话 3.5%）。
对话靠同人 genre、短篇靠字数与题材区分，不靠标题 IP 词；真正原创短篇标题 IP 词仅 1.7%。
IP 合作靠征文名称直接判定（见上），不参与本抽样。
**已定案（以 `13-form-definitions.md` 为准）**：对话征文/形态判据**优先于篇幅命名**，
重叠部分一律归 `dialogue`，**无需抽样**——理由是对话小说可长至 88 万字
（锚点 570712），若按字数归入 `long` 会污染长篇榜。上表保留当时的待抽样论证痕迹，
但权威优先级与边界（含短篇 5 万新边界）见 13。

**互动小说**：不单列（并入 `dialogue`），本地无法单独识别（691941 contest 空、
genre=古风），不硬猜第三值。
