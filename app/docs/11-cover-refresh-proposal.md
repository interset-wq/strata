## 0. 先厘清三个前提（否则会做无用功）

用户诉求是"种子必须有封面"。但核算发现三个必须先确认的事实：

1. **App UI 当前完全不显示封面**：`app/ui/lib/` 下 `Image.network` / `Image.asset` / `cover` 一次都没有。
   即"种子有封面"目前只是数据完整性问题，**不是 UI 阻塞**。若近期不打算在 UI 加封面墙/书卡，
   补封面的收益仅体现在数据质量，不能直接转化为产品竞争力。
2. **"缺封面"不等于"源头没封面"**：种子 30,831 本（非授权）里 18,724 本 `cover_url` 为空（60.7%），
   但其中 **16,976 本（90.7%）在原始 jsonl 里本来有真实 URL**，是构建期 `dedup_covers` 主动置空的
   ——判定依据是"同封面挂多书=novel_hub 爬虫选择器缺陷"（属主吻合率 89.8% vs 非属主 19.5%）。
   这些 URL **不能直接用**（会挂错图），必须按 nid 从官方源重取。
3. **只有 1,748 本是真默认封面**（文件名 `default` 开头），这才需要默认封面兜底。

**因此真正要补的是 16,976 本错配置空的书，不是 18,724 本"空封面"，更不是全库 131,814 本。**

## 2. 数据源能力：App API 是唯一现实选择

`GET /novels/{id}` 的默认 18 字段含 **`novelCover`（完整 https URL）**，

对比其他源：

| 源 | 封面 | 判断 |
|---|---|---|

串行 + 间隔 ≥0.5 s，App API 为可选增强通路、web 端为稳定基线。

## 3. 页数 / 请求量估算（核心问题回答）

待补 16,976 本里，**6,457 本已在本地 App 样本中**（URL 直接可用，零请求），
**10,519 本样本外，需要发起请求**。三种口径：

### 口径 A：只补封面 URL（写入 `cover_url` 字符串，App 运行时联网加载）
| 策略 | 请求量 | 说明 |
|---|---:|---|
| **A1 逐本详情** `GET /novels/{nid}` | **10,519 次** | 精确按 nid 取，零浪费；@0.5s ≈ 88 分钟串行 |
| A2 列表深翻 `/novels?size=50&page=N` | ~5,108 页 | 全库九类 255,408 本 ÷ 50；页内无序需全量去重，**为 10,519 本扫全库不划算** |
| A3 全量刷新种子 | 30,831 次 / 617 页 | 连已有 12,107 本也刷新为官方 URL；无必要 |

**结论：口径 A 选 A1，10,519 次请求。** 这是"补 URL"的最小成本。

### 口径 B：下载封面图片本身（打包进 App，离线可见）
- 待下图片 16,976 张（含样本内 6,457，URL 已在手），按 50 KB/张估 ≈ **829 MB**。
- 加上现有 12,107 本 = 29,083 张 ≈ 1.4 GB，**远超 App 随包资源合理体积**（现 seed.db.gz 仅 7.45 MB）。
- **结论：B 不可行**，除非只打包头部书（如深榜 Top200 并集约 7,856 本 → ~380 MB，仍偏大）。

### 口径 C：补 URL + 端上缓存
- 补 URL（A1 的 10,519 次）后，App 首次显示封面时联网拉取并本地缓存；失败则用默认封面。
- 这是"B 的离线体验"与"体积可控"的折中，但引入运行时网络依赖，与"App 离线可查"现状冲突，需产品拍板。

## 4. 方案（决策点 2 已定：存 URL）

用户 2026-11-17 拍板**存 URL**（不下图片本体、不做端上缓存预下载）。封面以官方
`novelCover` 直链字符串入库，运行时按需加载、失败用默认图兜底。其余细节仍按 §5 逐项拍板。

**推荐：口径 A1 + 默认封面兜底**
1. 目标池 = 16,976 本错配置空书；其中 6,457 本用本地样本 URL（零请求），10,519 本逐本取。
2. 写回：新增一张只读 `covers` 表（`nid, cover_url, source=app_api, fetched_at`），
   **不改 `books`**（保持 30,878 本 / 24 列与分位分母不变），与深榜表同款追加式设计。
3. 1,748 本默认封面：`cover_url` 留 NULL，端上/构建期用默认图兜底。
4. 不下载图片本体；UI 若未来显示封面，走 `Image.network(cover_url, errorBuilder→默认图)`。
5. 采集脚本独立于 `fetch_app_api_novels.py`，读本地缺口清单、按 nid 逐本取、断点续采、可复现。

**请求预算**：10,519 次，串行约 88 分钟（@0.5s），或 42 分钟（若放宽到 0.25s，需评估合规）。

## 8. 采集器实现：队列模式（2026-11-17）

决策点 2（存 URL）已定后，落地脚本为
`analysis/fetchers/cover_queue.py`（已实现、已离线验证；**未发起任何真实请求**）。
把 10,519 次请求拆成可持久化的「批量入队 → 批量出队 → 回填」队列，为 CI 分片预留接口。

### 8.1 状态机与持久化

- 队列 SQLite `analysis/out/cover_queue.db`（运行态、被 gitignore 忽略，不入库）。
- 状态：`skip_default`（1,748，源头默认封面、不请求）／`done`（6,457 本地样本直取 +
  已采集）／`pending`（10,519 需请求）→ `running` → `done`／`failed`（重试上限 3 次沉底）。
- **`out/cover_urls.jsonl` 是跨进程的唯一持久进度**：`fetch`／`ack` 成功即追加；
  队列 db 丢失后 `enqueue` 会从本地源 + 结果文件重建，已采集条目不回退
  （source 与 fetched_at 语义保留）。离线复跑核算与提案一致：18,724 / 1,748 / 16,976 /
  6,457 / 10,519。

### 8.2 命令

```bash
cd analysis
uv run python fetchers/cover_queue.py enqueue --dry-run   # 离线核算，不写库
uv run python fetchers/cover_queue.py enqueue             # 批量入队（读本地源 + 已有结果）
uv run python fetchers/cover_queue.py status              # 队列状态
uv run python fetchers/cover_queue.py fetch --max-requests 30 --delay 0.6  # 单进程小批验证
uv run python fetchers/cover_queue.py dequeue --batch 100 --out batch.json  # 原子出队（不联网）
uv run python fetchers/cover_queue.py ack --result result.jsonl            # 回填
uv run python fetchers/cover_queue.py requeue-expired --lease 600          # worker 崩溃恢复
uv run python fetchers/cover_queue.py export              # 导出 URL → out/cover_urls.jsonl
```

### 8.3 CI 接入方案（后续实施，尚未建 workflow）

结果 jsonl 是唯一持久状态，故 **job 间无需传递队列 db**：

1. 每次 CI run：checkout → `enqueue`（自动读上一轮上传的结果 jsonl 续采）→ 采集。
2. 分片：matrix 每个 job 跑 `fetch --shard i/n` 或 `dequeue/ack --shard i/n`
   （按 `nid % n == i` 取子集，无共享可变状态、无竞态）。验证 `0/4` 与 `1/4`
   的 nid 集合无交集、各自满足取模。
3. 各 job 上传结果 jsonl 为 artifact；最终 job 合并 → `export` → 交给 `build_seed.py`
   追加 `covers` 表（不改 `books` 24 列与分位分母，同 D2 深榜追加式设计）。
4. 合规校验保留在脚本内：`delay` 强制 ≥0.5s；只取 `novelCover`；不取正文、不登录、
   不用用户 cookie。`fetch --dry-run` 全程不出网（已验证）。

**当前状态**：脚本与离线验证完成；真实采集（10,519 次）仍待正式 UI 定型后按决策点 5 拍板启动。
