# Novly · 架构设计

> 定位：手机端「榜单驱动」的找书工具
> 变更：放弃离线优先 / 放弃桌面端 / 放弃全库捆绑

---

## 1. 三个被推翻的前提

| 原设计 | 问题 | 当前决策 |
| --- | --- | --- |
| 离线优先，内置 24 万本（hot 1.6MB + cold 3×20MB，约 60MB gz） | 首启解压 + 三片 cold 后台合并，十几秒；数据在发版瞬间冻结 | **只内置「榜位闭包 ∪ 标签闭包 ∪ banner 全集」19,856 本，实测 gzip 2.4 MB**（覆盖 100% 的可消费榜位） |
| 数据靠 `nookdata → build_chunks.py → 发版` 更新 | 一次更新要发一个版本，hot 才月更，cold 永不更新 | **本地引擎在线抓取，写回 SQLite**；种子包可随时增量替换 |
| 桌面 + Web + 移动三端 | 80% 的复杂度来自跨端兼容（Tauri、wa-sqlite、CORS） | **只做手机端**，砍掉桌面与 Web |

## 2. 「localhost」的正确形态

原方案的意图是对的：**详情页数据由本地抓取、写入本地库，UI 只读本地库**。
但实现不应该是「手机里起一个 HTTP 服务」——那是 go-music-dl 的约束（前端跑在 WebView 里，只能走 HTTP），Flutter 没有这个约束。

新架构把它做成 **进程内数据引擎**：

```
┌──────────────── Flutter App ─────────────────┐
│  UI (Riverpod)                               │
│     ↑ watch / 只读                            │
│  Repository ──► Drift (SQLite)  ◄── 唯一真相  │
│                      ▲                        │
│                      │ 独立事务写入            │
│  Engine Isolate ─────┘                        │
│    ├─ scheduler  排队 / 限速 / 退避            │
│    ├─ fetcher    dio + 条件请求               │
│    ├─ parser     纯函数，可 golden test       │
│    └─ Stream<Progress> → UI 进度条            │
└──────────────────────────────────────────────┘
```

三条铁律：

1. **UI 永远只读本地库**，不直接发网络请求 → 任何网络故障都不会导致白屏。
2. **Engine 只写本地库**，写完发一个 Stream 事件 → UI 自动刷新。
3. **Engine 跑在独立 Isolate** → HTML/JSON 解析不卡主线程动画。

> 这不是「离线优先」。离线优先 = 背 60MB 数据换无网可用；
> 这里是 **stale-while-revalidate** = 用 60KB 的 schema + 2.4MB 种子换「启动 0 等待」。
>
> 注意：**种子只装「榜位闭包」，不装全库。** 因为降序榜没人滑到第 2000 名（见 §4）。

## 3. 技术栈

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 框架 | Flutter 3.x / Dart 3 | 独立 Isolate 真并行；后台任务生态（workmanager）比 RN 成熟 |
| 数据库 | **drift** | 类型安全 SQL、内置 migration、支持 FTS5 与 trigram |
| 状态 | riverpod | StreamProvider 天然适配「库变更驱动 UI」 |
| 网络 | dio | 拦截器做全局限速 + 重试 |
| 路由 | go_router | — |
| 模型 | freezed + json_serializable | 解析层不可变模型 |

**关于是否换 Flutter**：这个产品 70% 的价值在数据引擎（抓取、解析、去重、调度、SQLite 写入），30% 在 UI。RN 的 expo-sqlite 是单线程且没有 Isolate，重写入会直接卡交互；Flutter 在这块是结构性优势。

**代价与收益要算清**：现有 RN 页面全部重写。但这不是损失——**本项目的 UI 不复用 novly 的任何设计**（配色、信息架构、页面结构一律重做）。novly 的界面是为「离线全库浏览」服务的，它的核心是分类树 + 无限下滑；而本产品的核心是「200 条榜位 × 320 种排法 × 成绩可信度可视化」，两者的交互模型不同，照搬会互相拖累。

唯一值得从旧工程搬的是**非 UI 的常量**：`utils/urls.ts` 里的 SFACG 接口地址与封面前缀。

## 4. 数据分层与体积

| 层 | 内容 | 体积 | 来源 |
| --- | --- | --- | --- |
| **APK 内置（种子）** | **19,856 本** = 榜位闭包 11,442（80 个 facet 组合各 top 200）∪ 标签闭包 12,478（全部 active 标签各 top 200，快照时 106 个）∪ **banner 全集 667（其中 65 本不落在前两层里）**<br>+ 72,922 条标签关系 + N 行标签统计（快照时 106）+ 667 行 banner<br>+ **`nid_epoch` 85 行 / `era_stats` 16 行**（时间基础设施，≈1 KB） | **gz 2.4 MB（实测）** | 打包内置 |
| **详情** | 简介 / 章节数 / 最新章节 / 背投 | 单本 ~2KB | 点开时按需抓取 |
| **搜索** | 在线接口 + 本地缓存已查看过的书 | 0 | 按需 |

**关键修正 3（本版）**：上一版说「全库 24 万行走 12MB 数据包」，这个结论也不成立了。

因为**降序榜单没人会滑到第 2000 名**。实测（见 `data-findings.md` §11）：

- 第 2000 名之后，45% 的名次是**并列**的，排序伪随机
- 第 15 万名之后，99.4% 并列——名次彻底无意义
- 全库 88.3% 的书 `view_num` 与他人并列，**没有唯一名次**
- 全站总榜前 1000 名里，cold 分片只占 **4 本**

所以「全库目录」这一层的投入产出比是负的：12MB 下载换来的 24 万行里，
真正会被消费的榜位全部落在前 1 万本内。

**正确做法：内置的是「榜位闭包」，不是「全库」。**

```
榜位闭包  A：9 genre × 3 status × 3 ptype = 80 组，每组 top 200 → 11,442 本（单值字段，零重叠）
标签闭包  B：全部 active 标签，每个 top 200              → 12,478 本（快照时 106 个）
官方榜快照 C：App 11 个榜 × top 20 × 9 个分类子榜        → 约 1,100 条榜位（多为已含在 A 内）
并集      A ∪ B ∪ C                                      → 约 19,800 本
```

**为什么 C 必须纳入**：官方 11 个榜全是「当期热度」（种草榜 15 分钟刷新、
月票按月清零、完结榜也只算当期），而我们是「累计成绩」。两者一对比，
**「官方第 3 名 / 我们第 47 名」本身就是产品里最有信息量的一句话**——
它精确指出「这本书现在很火，但历史上不算什么」，反之亦然。
这正是 `rank_snapshots` 表存在的目的。

C 的体积可忽略（top20 × 20 个榜位面 ≈ 400 行），但它给了我们一个官方没有的维度：**时间**。

**体积必须按实测说，不能按估算。** 早期用「每本 60 字节」推出 223 KB，错了约 10 倍
（中文标题三字节/字、封面 URL 70 字节、SQLite 行头开销）：

| 方案 | 书数 | 原始 | gzip |
| --- | --- | --- | --- |
| 榜位闭包，无封面 | 11,442 | 1,200 KB | 657 KB |
| 榜位闭包 + 封面 | 11,442 | 2,400 KB | **1,053 KB** |
| 榜位 ∪ 标签，无标签关系 | 19,791 | 4,044 KB | 1,776 KB |
| **榜位 ∪ 标签 + 全标签关系 + 封面** | **19,791** | **5,576 KB** | **2,407 KB** |

顺手否掉一个看似聪明的优化：封面只存后缀（剥掉 54 字符前缀）只省 **20 KB**，
因为 gzip 早已把那串重复前缀压掉了。**不值得为它增加一层拼接逻辑。**

**2.4 MB 覆盖 100% 的可消费榜位；约 30 MB 覆盖 4.7% 的可消费榜位 + 95.3% 的伪随机名次。**

连带三个收益：

1. **数据更新包从 60MB 降到 2.4MB** —— 没 WiFi 也能更新完，不再需要「等一次下载」
2. **没有「首次下载」这一步** —— 种子直接打进 APK，冷启动零网络就能看全榜 + 全标签
3. **采集量降到约 2,837 个 API 请求/天**（19,856 本 7 天轮转）。
   注意算的是**请求数不是本数**：列表页只有 nid/标题/作者/封面，成绩全在详情页，
   所以每本 1 个请求，没有批量捷径（实测见 §6.5）。1s 间隔约 47 分钟/天。
   ★ 但每 1 个请求换回的字段比以前多得多：人气精确值、收藏、赞、月票、评分、
     章节数、上架日、简介、官方标签（含 sysTagId）—— 一次拿全。

对比原方案：**APK 60MB → 约 8MB；首启十几秒 → 秒开；数据更新 60MB → 2.4MB。**

**代价（必须接受）**：没有本地全库搜索。搜索走在线接口。
但这不是损失——SFACG 的搜索本来就弱，而用户找书靠的是**筛选与排序**，不是关键词。
80 个 facet 组合 × 4 个排序维度 = 320 种榜，全部离线可用。

### 我们不继承 novly 的分片 + 运行时合并

novly 的 60MB 装不进一次顺畅的冷启动，所以它把数据切成 hot + cold_1/2/3，
首屏只解压 hot（~3s），cold 在后台 ATTACH 合并，合完原子替换 + 写 marker，
再提示用户「重启应用以使用全量数据」（机制细节见 `data-findings.md` §0）。

这套设计是对的，但它是**为 60MB 服务的**。数据缩到 2.4MB 之后，整类复杂度都可以删掉：

| | novly | 本方案 |
| --- | --- | --- |
| 打包形态 | hot + cold×3，4 个独立库 | **单库** `seed.sqlite.gz` |
| 冷启动 | 前台解压 hot → 后台合并 cold（几十秒到分钟级） | 一次性解压单库 |
| 合并阶段 | `ATTACH` + 分批 `INSERT` + **id 重映射** | **无** |
| 首启期间的数据完整性 | 只有 hot，cold 缺席；页面要处理"数据正在补齐" | 一开始就是全量 |
| 容错 | marker 与库可能不一致（进程死在 swap 阶段），需删库重建 | 解压失败就重新解压 |
| 收尾 | 弹窗要求用户重启 | 无 |

`pitfalls.md` 里第 12 / 13 / 14 条（cold 合并必须用不同文件路径、大 gz 必须让出事件循环、
gradle 从不清理残留 gz 资产导致 APK 膨胀到 164MB）**全部是这套机制的衍生 bug**，
随数据缩小一并消失。这是「砍数据」带来的隐性收益：不是省了 57MB，是删掉了一整类故障。

**唯一值得抄的一处**：它的 id 重映射写法（`INSERT OR IGNORE` 灌 name，再按 name JOIN 回填）。
我们的单库不需要它，但只要将来做**增量 patch**（而不是整包替换），就必须复用这套对齐逻辑。

### 数据可继承，判定不继承

我们只在第一次开发时借用上游数据。此后自建爬虫维护种子，
所以**任何字段的语义都必须由我们自己的采集能力定义**，不能继承上游的二次加工结论——
因为我们无法验证它当时是怎么算的。

划线很简单，看它是「页面上的东西」还是「别人算出来的结论」：

| | 例子 | 用不用 |
| --- | --- | --- |
| **原始事实**（站方页面直接显示的） | nid、标题、作者、分类、封面、人气、收藏、赞、字数、状态、免费/签约/VIP、有没有 banner 位 | ✅ 用 |
| **第三方的二次加工** | `status=5/6`（A 后缀）、`warm/cold/hot` 分片、任何「质量判断」字段 | ❌ 不用 |

落地三处改动：

1. **删掉 `stats_level`**（1 = 只信点击 / 2 = 全指标）。
   它的「2」恰好等于上游的 A 组，那是**上游的划分**；而它被当成了「数据可信度」，
   会让人误以为这是我们自己的判断。换成两个只依赖我们自己的字段：
   `stats_src`（`'own'` / `'upstream'`）+ `stats_at`（采集时间）。
   它顺带成了「摆脱第三方」的进度条：`SELECT stats_src, COUNT(*) FROM catalog GROUP BY 1`。
2. **删掉 `quality`**（综合质量分）。任何加权都等于替用户决定「点击和收藏哪个更重要」，
   而这个答案因人而异。一个神奇数字存在久了，就一定有人拿它排序，
   然后没人能解释第 7 名为什么是第 7 名。
3. **保留 `is_banner`，但限权**。它只用于「官方精选」入口的收录条件，不进任何加权。
   它和 A 后缀的区别是：banner 是**站方在页面上放了张图**（事实），
   A 是**第三方作者按规则打了个标**（判断）。

### 字段名也不能继承——它坏了三层

上面说的是「判定」，但**字段名本身也是一层需要验证的东西**。
上游 `like_num` 实际是**收藏**、`praise_num` 才是**赞**——语义正好反了。
任何人写 `ORDER BY like_num DESC` 都会以为在排「点赞最多的书」，
实际排的是收藏榜，而这两个榜在 SFACG 上结论完全不同（同人区点赞率是其他 genre 的 80 倍）。

完整的实测见 data-findings §14，这里只留结论：

| 层 | 上游怎么做的 | 后果 |
| --- | --- | --- |
| **命名** | 中文直译：看到「收藏」选了 `like`（Facebook 语境里 like = 点赞） | 语义反了，且**不报错** |
| **提取** | 位置解包 `btns[-2:]`、`values` 四元解包 | 站方加了「分享/举报」两个按钮 → 取到空串 → `int('')` 崩；崩之前已经静默错位 |
| **精度** | 「10839.2万」还原成 `INTEGER` 108392000 | 类型声明精确到个位，实际只到千位 |

这三层有个共同点：**全都不会报错**。字段有值、类型合法、量级也对，
只有拿另一份数据逐一对账才能发现。

所以定三条：

1. **字段名一律跟随 API key，不自创英文名。**
   `viewTimes → view_num`、`markCount → mark_num`、`fav → fav_num`。
   API 的 key 是站方对同一份数据的命名，比我们从中文直译可靠一个数量级。
2. **每个字段入库前做三方对账**：上游库 / API / 页面文本，至少两方数值吻合。
   例：`like_num 195,141 ≈ markCount 196,097 ≈ 页面「收藏 196096」`，三点成线才可用。
3. **采集器禁止位置解包。** 只能按可见文本匹配（`赞 (\d+)` / `收藏 (\d+)`），
   取不到就报错。位置解包的本质是「假设页面永远不变」，而这个假设每次都应验到它失效为止。

顺带记一条：上游 `_row` 的注释写「点击：4757.4万」，今天的页面写「人气：10903.2万」。
**站方自己改过这四个字。** 所以 `click_num` 不是错译，是「当年对、现在过期」——
上游把**页面标签**当成了字段语义，而页面标签会变。

### 我们自己的三条判定规则

**① 收录按覆盖，不按质量。**
取「所有可能被看到的集合」：80 个 facet 组合各 top 200 + 全部 active 标签各 top 200
+ **banner 全集**，并集 **19,856**。
不做编辑精选——「选哪些书」正是上游做过、而且做窄了的事（A 组只捞到 2,515 本）。

**banner 必须显式并入，不能靠前两层兜住**（`data-findings.md` §17.10）：
667 本里中位组内名次是 346，榜位闭包只覆盖 544 本，再加上标签闭包也只到 602 本，
**剩下 65 本（9.7%）永远进不来**。而 banner 的授予逻辑本来就和人气反着来
（文豪野犬点击 475 挂十年）——能被 top 200 兜住的 banner 书，恰恰是「不需要 banner 也能被找到」的那批。
→ 这是「按成绩 top N 截断」的第二次翻车（第一次是标签的 95% 假象，§16.6）：
**凡是「人的判断」驱动的集合，都不能用成绩榜单去截断。**

**② 可用性看字段是否为 NULL，不看来源等级。**
`view_num IS NULL` = 还没采到；`mark_num IS NULL` = 不可用（不能当 0）；
`stats_at` 超过 30 天 = 标记待更新。字段自己的 NULL 就是最好的质量标记，
不需要再发明一个等级字段去描述它。

**③ 排序单维度 + 必有二级键。**

```sql
ORDER BY view_num DESC, mark_num DESC, id ASC
```

二级键不是装饰，但理由和我原来写的不同。

**上一个版本的推理错了**：我以为并列来自「4757.4万」这种 5 位有效数字的显示精度。
那是网页的显示，而 `api.sfacg.com` 返回的是 `viewTimes: 109032154` —— **精确到个位**。
所以在我们自己的数据里，并列是真同分，不是精度假象。

**「88.3% 没有唯一名次」这个数字也不再适用于我们**，因为它是全库 24.6 万本
不分格直接排出来的。实测按「genre × status × ptype 分格 + 每格 top 200」重算
（用 5,320 本精确池模拟，44 个有效格、4,028 个位次）：

| 口径 | 并列率 |
| --- | --- |
| 全库不分格（旧结论） | 88.3% |
| 全精确池整体 | 23.6% |
| **分格后每格 top 200 内** | **4.05%** |

**拉到 4% 靠的是「分格 + 只取 top200」，不是精度。** 同一格里的书量级本来就挨得近，
不会出现「第 3000 名一大堆并列」那种情况。

保留二级键的真实理由是**防同分抖动**：人气恰好相同（或都还没采到）时，
按 `mark_num` 再按 `id` 排，保证顺序稳定、翻页不跳。这是工程需要，不是数据修正。
那 4% 的并列也不需要「第 51 名起诚实提示」——它落在可接受范围内。

## 5. 产品定位：不是更好的 SFACG，是它漏掉的 90%

官方 App 的运营是一条**单向漏斗**：新书上架 → 新书榜 → 编辑选签约 → 再选 VIP → 少数给 banner。

实测漏斗宽度：免费 226,158 本（91.9%）→ 签约 12,933 本（转化 **5.7%**）→ VIP 6,954 本（转化 53.8%）。
第一道筛子极窄，第二道很宽：**能不能签约是生死线**。

于是产生一个结构性后果：

> **一本书的字数一旦长起来、离开新书期，就永久失去上榜资格——无论之后成绩多好。**

这不是猜测。`warm`（站方曝光过的）里 VIP 书字数中位 **95.7 万**，
`cold`（从未曝光的）里 VIP 书字数中位只有 **46 万**。
长篇 VIP 老书在官方体系里**没有对应的榜**。

### 「榜上全是短书」不是短书更好，是短书才有资格

实测反直觉：字数与成绩**正相关**（连载中 0–10 万字平均点击 3,779，
300 万字以上 1,569 万）。但新书榜候选池只有字数 < 10 万的 **1,453 本**，
其中 1,061 本点击 < 1,000。

所以正确的因果是「短 → 有资格 → 少数被选中展示」，不是「短 → 排名高」。

### 产品定义：三层错位

| 层 | 官方 App | Novly |
| --- | --- | --- |
| **覆盖的生命周期** | 前 10%（新书期） | **全部 100%** |
| **排序键** | **商业现值**（还在赚钱吗） | **历史成绩**（有多少人读过） |
| **完结的权重** | **减分项**（不能变现了） | **加分项**（能一口气读完） |

**第一层（生命周期）**：离开新书期即失去上榜资格，无论成绩多好。

**第二层（排序键）**：这是最硬的一条。实测同是 VIP 书——

| | 本数 | 中位点击 |
| --- | --- | --- |
| 连载中 VIP | 487 | 634,908 |
| 完结 · VIP | 1,322 | **3,269,000** |

完结书成绩是连载书的 **5.1 倍**，官方却把前者撤榜、后者留榜。
说明榜单的排序键根本不是 `view_num`，而是 `view_num × 是否还在产生收入`。

《英雄再临》是最好的注脚：全站点击第一（1.19 亿），漫画长期霸占腾讯漫画榜单、
有动画、有实体出版，2024 年 3 月完结后从官方推荐位消失。
**它的 1.19 亿点击是永久资产，但官方没有入口让新读者找到它**——因为它不再产生订阅。

**第三层（完结权重）**：官方压制完结书（不能变现），而读者的真实需求恰恰是「能读完」。
这一层是纯价值主张，不需要任何额外数据。

### 一个反直觉的事实：成绩不随时间衰减

| 完结距今 | 本数 | 平均点击 |
| --- | --- | --- |
| 1 年内 | 103 | 5,115,329 |
| 1–2 年 | 183 | 6,856,627 |
| 2–5 年 | 659 | 5,809,174 |
| **5 年以上** | **443** | **5,362,941** |

5 年前完结的书，平均点击和 1 年内完结的几乎一样。
因为累计点击只增不减：撤榜那一刻曝光归零，数字就冻结在那里。

**「老书会被遗忘」是错的——在数据层面它只是停止增长，从不减少。**

用户场景不冲突：想追新书的人开官方 App；想找「当年那本」的人，官方 App 里永远翻不到。

### 两个池子撑起差异化

`ptype` 是编辑筛选的层级标记，本身就是质量信号。用它和 `view_num` 做二维，得到四象限：

|  | 编辑认可（VIP / banner） | 编辑未认可（免费） |
| --- | --- | --- |
| **读者认可**（高点击） | 商业验证的完本神作<br>4,009 + warm 2,515 | **被埋没的好书 4,930** ← 灵魂 |
| **读者不认可**（低点击） | 运营位 / 版权引进日轻 | 墓碑（约 22 万） |

左下角那个 4,930 本的池子，是产品存在的全部理由。样本：

- 《穿越者将会死于凯文卡斯兰那》—— 377 万点击、10 万字、完结、**从未签约**
- 《我原神史莱姆强无敌》—— 371 万点击、25 万字、断更、**从未签约**

它不是没人看，它是**在官方体系里不存在**。

> 上一版设计里我写「按累计点击排序会再次埋没老书」，这个判断是错的。
> 它把「近期热度」和「累计成绩」混为一谈了。老书缺的是**资格**，不缺成绩。

## 5.1 榜单设计：六个入口

**先看清对手。** App 有 11 个榜：推荐 / 人气 / 畅销 / 新书 / 收藏 / 月票 / 打赏 / 种草 / 粉丝 / 角色 / 完结。
它们**全部是当期榜**——种草榜 15 分钟刷新，月票和打赏按月清零，
完结榜也只是「完结的书里现在最火的」。官方回答「现在什么火」，没有一个是「过去什么好」。

这不是疏忽，是商业模式：**只有当期的货能变现**。一本 2015 年完结的神作，
哪怕当年是巅峰，放上去也不产生任何收入。而实测它的成绩**不随时间衰减**
（5 年前完结 536 万 ≈ 1 年内完结 511 万）。

所以下面六个入口不需要跟那 11 个榜「错位」，而是**结构性地站在它们之外**：
用累计值、用可解释的单维度、覆盖到第 200 名、并且把「没被签约」的书也算进来。

按「置信度 × 差异度」排序，殿堂置顶。

### 入口 0：年度殿堂（19 本，每年 1 本）

**原设计是错的，这里改掉。** 旧方案是 `is_banner=1 AND view_num ≥ 5000万` → 14 本，
听起来是「全站置信度最高的集合」，实际是**一个时间窗口的假象**：

| 上架年 | 2012 | 2015 | 2016 | 2017 | 2018 | 2019 | 2020 | 2022 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 本数 | 1 | 1 | 2 | 2 | 3 | 2 | 2 | 1 |

**14 本全部落在 2015–2022。** 2006–2014 的书（灼眼的夏娜、刀剑神域、魔法禁书目录）
当年用户少，累计人气上不去；2023–2025 的书时间不够，攒不到 5000 万。
所以它不是「最好的 14 本」，而是「**2015–2022 上架的书里最好的 14 本**」。

绝对人气门槛天生偏向「上架早 + 连载久」——这和 `data-findings` §18.4 是同一个错误：
`view_num` 混了「当年用户规模」和「累计时间」，**不能跨年比较**。

**改成「每年 1 本」后，问题自然消失**——因为只在同年上架的书之间比较，
积累时间相同，排序是公平的：

| 年 | 当年王者 | 人气 | 字数 |
| --- | --- | --- | --- |
| 2006 | 灼眼的夏娜 | 627 万 | 244 万 |
| 2007 | 魔法的禁书目录 | 1,895 万 | 258 万 |

| 2013 | 弑魔者的简单生活 | 1,772 万 | 607 万 |
| 2014 | 魔法机械的激斗恋曲 | 916 万 | 762 万 |
| 2015 | 变身之后，我与她的狂想曲 | **1.08 亿** | 1,461 万 |
| 2016 | 英雄再临（英雄？我早就不当了） | **1.19 亿** | 545 万 |

（2008 年缺，那年只有 1 张 banner 且落在别的年份区间；年份由 `nid_epoch` 插值，
±1 周误差，边界上的书可能挪一年，不影响分年榜的性质。）

这张表本身就是产品的叙事骨架：**2006–2014 是正版引进期**（角川系），
**2015 起是原创期**，而 2015–2019 每年的王者都在亿级。用户一眼能看懂
「这个站曾经有多热，现在是什么光景」。

取法：

```sql
-- 每年取 1 本：年内比较，免疫累计时间偏差
SELECT b.add_year, c.id, c.title, c.author, c.view_num, c.word_num
FROM banners b JOIN catalog c ON c.id = b.book_id
WHERE b.era_pct >= 90                    -- 挡掉引进的低人气书（2015 年后）
  AND c.id = (SELECT c2.id FROM banners b2 JOIN catalog c2 ON c2.id = b2.book_id
              WHERE b2.add_year = b.add_year AND b2.era_pct >= 90
              ORDER BY c2.view_num DESC LIMIT 1)
ORDER BY b.add_year DESC;
-- 2006–2014 的引进期王者要单独保留（它们的 era_pct 也是当年头部，
-- 但 book_count 只有 3~9，样本太小，UI 上应标注「引进期」而不是混进原创榜）
```

**为什么不用「每年 top 3」或「综合含金量指数」**：
前者把 19 本变成 57 本，失去「一屏看完一个时代」的锐度；
后者要把「数量之最」和「成绩之最」加权（§18.7），而我们解释不了那个权重。
一年一本，规则一句话说完，用户不会质疑。

### 入口 1：一口气读完（1,422 本）

`status = '完结'` + `word_num ≥ 100 万` + `view_num ≥ 10 万`。

官方把「完结」当减分项，读者把它当加分项。这是纯价值主张：
**读者找书的第一需求是「能读完」，不是「正在更」。**

### 入口 2：被埋没的好书（4,930 本）

`ptype = 2`（从未签约）+ `is_banner = 0` + `status ∈ ('完结','断更')` + `view_num ≥ 10 万`。

最锋利的一个：**读者用点击投了票，编辑一票否决**。
它们不在新书榜（已完结/断更了），也没有任何推荐位，在官方 App 里彻底不存在。

宽口径放宽到 `ptype ∈ (2,3,4)` → 约 11,700 本，用于「再挖一层」。

两种口径在**上游数据上只能按 view_num 排序**：这批书的 `mark_num`/`fav_num` 是被 cap 的假值。
等我们自采完成，它们才能进入收藏榜。

### 入口 3：考古（956 本）

`status = '完结'` + `add_time` 早于 5 年前 + `view_num ≥ 50 万`。

依据是 §5 那个反直觉事实：**成绩不随时间衰减**（5 年以上完结组平均点击 536 万）。
这些书被遗忘不是因为它们不值得读，是因为它们的曝光数字冻结在撤榜那一天。

### 入口 4：官方精选（667 本）+ 首页轮播

这是全库**最值钱也最稀缺**的信号：只有 667 本书（0.27%）带 banner。
但 667 本里有两类，必须说清：

| 类 | 规模 | 特征 |
| --- | --- | --- |
| **成绩认可**（原创） | ~637 本 | 字数中位 158 万、99.4% VIP、64% 完结 |
| **引进推广**（正版日轻） | 30 本 | 点击可低至 475，2023-08-03 一天上 4 本 |

第二类是版号/版权方要求，与成绩无关。**不分字段、不隐藏**，
只用 `era_pct` 排序让它们自然沉底（见下）。

**点击 475 却能挂十年 banner，这只能是人给的，不是数据算的。**
官方 App 里这 667 本散落在各个推荐位，无法聚合成榜。把它们收拢成一屏，
就是任何爬虫都复现不了的东西——**因为它不是数据，是人的判断。**

**而且它自带一张横版宣传图**（`banners` 表，data-findings §17）：750×430、纯插画、
不含书名，实测 666/667 可下载且含 2013 年的书。所以同一份数据同时供两个用途：

| 用途 | 取法 |
| --- | --- |
| 官方精选榜 | `FROM banners JOIN catalog ORDER BY era_pct DESC, view_num DESC` |
| 首页轮播图 | `WHERE active=1 AND era_pct>=20` + 日轮换（见下） |

**注意精选榜按 `era_pct` 排而不是 `view_num`**：否则 2023-08-03 批量引进的 4 本日轻
会和原创神作混在一起，用户点进去发现 3,532 人气，信任就没了。
每条可以带一句语境：**「2019 年 · 当年 24,347 本新书里 91 本获官方横幅」**——
这句话本身就是产品价值，它把「banner 有多难得」量化给用户看（数据来自 `era_stats`）。

**轮播图必须自己叠书名**——图上没有书名，只有插画（`2242` 那张左上角还有一行
日方版权小字，所以叠字不能放左上角）。两张实测图的明度差极大（浅米底 / 满色城市），
所以**必须有渐变遮罩**，不能指望图本身给对比度。

**轮播怎么排：日轮换，不假装「最新」，权重用 `era_pct` 而不是人气。**

banner 没有可信的**图片**时间信号（`Last-Modified` 是批量上传时刻，16/23 集中在一分钟内，§17.6）。
但书的**上架年**是有的 —— 由 `nid_epoch` 插值（§18.1，85 个锚点、0 次逆序、误差 4 天）。

```
当天的 5 张 = (当天日期 ^ client_id) 做种子的加权随机
权重 = banners.era_pct（当年全库人气分位），并要求 era_pct >= 20
```

**为什么不能用 `view_num` 加权**（上一版就是这么写的，错）：人气是累计值，
它同时装着「当年用户规模」和「已经攒了多久」。2016 年上架的书攒了 10 年、
2024 年的只攒了 2 年 —— 直接加权会让轮播永远被黄金五年的老书占满，而且是最早那批。

用 `era_pct` 就公平了：每本在**自己的年代**里都是 top 1%（实测中位 98.5–99.97%，
十一年几乎不变），出现频率自然由各年 banner 数量决定（2015–2019 占 65%）。
**不做「按年分层配额」**：5 个位要覆盖 11 个年份，比例配额会让 2020–2025 永远轮不到
（2025 全年 7 本，配额 0.05 个位 → 0）。均匀随机已经自然给了黄金五年 65%。

`era_pct >= 20` 这一条挡掉的是正版引进的日轻 —— 文豪野犬 475、天魔黑兔 3,532、
电波女与青春男 5,170，实测 30 本点击 < 50 万。它们有 banner 是因为**版号/版权方要求**，
不是因为成绩（2023-08-03 一天上了 4 本）。**我们不设 origin 字段去人工分类**，
只让数据说话：低分位的自然沉底，不隐藏、不删除。

站方的 banner 是「当期」的，我们的是「历年全部」的 667 张：同样的好图，覆盖长 20 倍。
这是入口 4 的轮播版本，也是「过去什么好」在视觉上的直接兑现。

### 入口 5：标签（当前 106 个，会增减 —— 第二个独立维度）

标签和 `genre` 是两个**正交**的坐标系，不是包含关系。实测任一标签都横跨全部 9 个 genre
（`系统`/`重生`/`女性主角`/`嫁人`/`仙侠` 全部命中 genre 2–10）。

所以标签不是「分类的子页」，而是和分类并列的一层。快照时 106 个标签，
平均每本 3.17 个。**但标签集合会变**（官方每年新增 award 类），所以端上必须能处理
「比我认识的标签更新的标签」——采集到未知 sysTagId 时按新增处理，而不是丢弃。

**⚠️ 「95% 的书有标签」是个假象，别拿它当准入前提。** 按年份拆开（data-findings §16.6）：

| 年份 | 平均标签数 |
| --- | --- |
| 2010–2014 | **0.53**（一半的书一个都没有） |
| 2016 | 1.29 |
| 2019–2022 | ~3.15 |
| 2026 | **4.24** |

标签系统是 2016 年后才变成常规操作的。所以**任何 `JOIN book_tags` 的查询都天然排除老书**——
这跟我们「过去什么好」的定位正好相反。结论：
**标签只能当「发现新书」的维度，不能当「找被埋没的好书」的入口。**
「被埋没」「考古」那几个入口必须走成绩 + 字数，不能挂标签。

**标签的身份是字符串，不是实体**（data-findings §16）：上游 `name` 有 UNIQUE，id 是代理键；
而站方换词（百合→橘味）是**新建词条 + 旧关系不迁移**——标题含「百合」的 303 本里
只有 1 本带「橘味」。所以：
- 数据层按 `name` 对齐，`sys_tag_id` 只当「号段≈年份」的批次指纹；
- **不做别名合并，也不做同义词映射**——合并只会把两个不相交的集合并起来、
  `book_count` 虚高；而「搜 A 带出 B」不增加召回，只是把不相干的书塞进同一页；
- 同义标签（末世/末日）**就是两个独立标签**，并列展示、各自按 density 排位。
  多一个近义入口 = 多一条找书路径，这是 feature；
- 唯一要认的代价：不知道「橘味」是委婉语的新用户，一步内找不到那 6,214 本。
  补偿走「搜索无结果推荐热门标签」，**不走伪造同义词**；
- 反方向也不行：语义相近不等于同一实体——「末世」8,813 本和「末日」465 本
  **一本书都不重合**，而「末日」2026-04 还在用。站方不做语义去重，我们也别替它做。

**导航必须按「神作密度」排，不能按本数排**——这是这一节唯一必须记住的规则：

| 按本数排（错） | 本数 | 按密度排（对） | 密度 |
| --- | --- | --- | --- |
| 战斗 | 65,700 | **倒追** | **7.4%** |
| 日常 | 65,696 | 运动 | 5.9% |
| 异世界 | 59,638 | 嫁人 | 5.8% |
| 恋爱 | 59,136 | 追夫 | 5.2% |
| 女性主角 | 46,488 | 变身 | 5.1% |

（密度 = 该标签下 view_num≥100 万的书占比，全库基线 1.5%）

按本数排，前三名占了全库 27%，**用户点进去和「全部」没有区别**——宽泛标签等于没筛。

**标签集合会变，带三个连带后果**（机制实测见 data-findings §15）：

1. **种子包大小会波动。** 标签闭包 =「当前全部 active 标签各 top 200」，
   多一个标签最多多 200 本（gzip 约 +25 KB）。可以接受，但不能把它当常量写死。
2. **`kind` 必须有 `other` 兜底。** 官方新增的标签若不属于现有 5 类，
   CHECK 约束会让 INSERT 直接失败——采集器崩在一个「我们没预见到的好标签」上，
   是最不该发生的故障。自动归类规则：`^\d{4}萌神$` → award，其余 → other。
3. **端上要能显示「字典里没有的标签」。** 用户升级种子后多出来的标签不能整条消失，
   按 `other` 分组显示即可；`tag_stats` 缺行时只显示标签、不显示密度，也不要丢。
按密度排才看见真正的主场：`倒追`/`嫁人`/`变身`/`橘味` 这一族是基线的 3–5 倍。

标签按语义分五组（`kind`）：题材 `subject`、角色关系 `role`、情绪 `mood`、同人 IP `ip`、
年度评选 `award`。最后一组是意外发现：2018–2024 共 14 个「萌神」名额，比 banner（667）稀有 47 倍，
适合做荣誉徽章而不是可浏览标签。

**组合能更准，也能更差。** 以「异世界」为底（密度 1.1%）：

- 异世界 + 女性主角 → **2.2%** ↑（10,928 本）
- 异世界 + 无敌 → **2.1%** ↑（8,298 本）
- 异世界 + 战斗 → **0.7%** ↓（20,510 本，加了等于没加）

三标签的真配方极强：`倒追+橘味+纯爱` 全库 37 本，其中 9 本破百万 = **24.3%（基线 16 倍）**。
这张表只能在构建期算（端上无全库），所以落成 `tag_combos`。

### 入口 6：年代轴（★ 新增，之前整个设计缺的那一维）

**这是 banner 时代论的副产品，但它比 banner 本身更重要。**

之前所有入口都是「现在谁的分高」——按人气、按月票、按评分。
而产品定位是「**过去什么好**」，居然没有任何一条时间维度。这是设计漏洞，不是取舍。

补上它的成本是 **85 行锚点表**（`nid_epoch`）：nid 单调递增，
实测 85 个跨全库锚点 **0 次逆序**，分段插值误差 4 天。
于是 24.6 万本全部拿到 `add_time`，**零 API 请求**（data-findings §18.1）。

**为什么非要自己做，而不去抓 24 万次 API**：不是省钱，是**它们没有这个字段**。
上游库只有 `last_update`（活动时间），而 banner 那批书长时间连载，
`last_update` 全被拽到 2026 年（64.8% 的 banner 书是 2015–2019 上架的，
但按 `last_update` 分年全堆在 2025–2026）。**只有上架年才是它们的身份。**

三个形态：

| 形态 | 取法 | 用户看到什么 |
| --- | --- | --- |
| 年代总览 | `FROM era_stats WHERE books>=1000` | 每年一行：「2019 · 新书 24,347 本 · 91 张官方横幅 · top1% 门槛 273 万」 |
| 年代榜 | `WHERE add_time BETWEEN :y0 AND :y1 ORDER BY view_num DESC` | 「2016 年 top 100」 |
| 书龄筛选 | `WHERE add_time >= :t0` | 「近三年」「十年前」这类条件，接在通用榜上 |

`era_stats` 的 `books` 是**全库**统计（不是种子闭包 2 万），端上算不出来，
必须构建期算好存进来（16 行，体积可忽略）。

**年代榜把「时代背景」变成了可展示的数据**，这是它和普通筛选器的区别：
用户看到 2019 年「top1% 门槛 273 万」，再看 2025 年「75 万」，
就理解了「不同年份的成绩不能直接比」——**不需要我们解释，数据自己说。**

### 通用榜：累计成绩（老书主场）

榜单**必须按排序键的可信度分两套池**，不能混排：

| 榜 | 排序键 | 可用池 | facet 粒度 | 榜长 |
| --- | --- | --- | --- | --- |
| 点击榜 / 字数榜 / 更新时间榜 | 全指标真实的字段 | **19,791 本闭包** | 80 格（genre × status × ptype）+ N 个 active 标签 | 200 |
| 收藏榜 / 点赞榜 | `mark_num` / `fav_num` | **5,320 本精确池** | 27 格（genre × status） | 有多少给多少 |

为什么口碑榜要降粒度：精确池拆到三层维度后，**70 个格子里有 33 个（47%）不足 20 本**
（genre 10 完结只有 6 本、genre 4 断更只有 1 本）。硬拆成 200 条的榜只会暴露空洞。

降到 `genre × status` 后每格最少 6 本、最多 474 本。**榜长是上限，不是承诺**——
小分类给小榜，比硬凑 200 条诚实得多。

### 辅助榜：变化

- **增长榜**：近 7 / 30 天涨幅（两期快照差分）—— 发现「老书翻红」
- **掉榜预警 / 新入榜**：给常看的用户提供变化感

### 明确不做

- **新书榜**：官方已经做得很好，做它没有差异化价值，还会稀释「老书」这个定位。
- **按未采到的字段排序**：把「已采到 mark」和「还没采到 mark」的书放进同一个
  `ORDER BY mark_num`，结果是先采的那一批永久霸榜。
  **那不是「收藏最多」，是「哪一批先采过」。** 正确写法是 `WHERE mark_num IS NOT NULL`。

### 为什么还要保留 `rank_snapshots`

主力榜是累计值，一条 `ORDER BY view_num DESC` 就够了。但「这周哪本老书翻红了」「哪本掉出前 100」
需要时间序列。所以榜位历史照存，只是它服务的是**变化**，不是排序。

---

### 不做综合质量分，但「效率」可以单独成榜

累计值有个天然缺陷：2013 年上架的书靠早期红利永远霸榜，也容易被运营灌量。
直觉的解法是算一个综合分。**但我们不做**——理由见 §4：加权即代用户做价值判断。

只保留一个**可解释**的派生指标：点赞率（点进来的人里，有多大比例真的点赞）。

```
效率 = (fav_num + m × prior) / (view_num + m)     m ≈ 3000，贝叶斯平滑防小样本虚高
```

它单独成一个榜（「点进来的人有多少真的喜欢」），不参与任何其他排序，
也不与点击榜混排。用户看到的是一个能解释的比值，不是一个神秘分数。

前提是分子分母都站得住：`fav_num` 必须是我们自己采到的整数；
`view_num` 采到的是精确整数（API 的 viewTimes），分子分母都站得住。
上游数据里 `fav_num` 上限 9,928、`mark_num` 上限 9,999，
算出来的「转化率」其实是**采集器的显示天花板**——所以这条榜只在自采数据上成立。

「埋没指数」同理：分母 `view_num` 可信而分子 `fav_num` 不可信时，指数没有意义。
替代方案是入口 2 那条绝对量规则（`view_num ≥ 10 万` + `is_banner = 0` + 已完结）。

## 5.5 搜索：本地索引 + 官方接口混合

种子里只有 19,791 本，而官方全库 24 万+ 且每天增长。
**用户搜不到书会直接判定「这 App 不好用」——空结果是产品死亡的第一因。**

所以搜索不能只有本地，也不能只有官方。实测三个接口（详见 **`archive/search.md`**）：

| 接口 | 条数 | 独有字段 |
| --- | --- | --- |
| `m.sfacg.com/API/HTML5.ashx?op=search` | **固定 12 条，无分页** | `TypeName` 分类、`Point` 评分 0–10 |
| `s.sfacg.com/?Key=&SS=0&S=1` | **全量**（实测 29 条） | **`intro` 简介**、`last_update` |
| `m.sfacg.com/API/Book.ashx?op=searchreffer` | 15 条书名 | 联想词（可纠错） |

三层架构：

```
L0 联想   本地标题前缀 + 拼音首字母 / 官方联想词     0ms / 150ms
L1 本地   19,791 条内存索引，命中即刻渲染            <20ms
L2 官方   HTML 全量 + API 评分，按 id 合并追加      200–500ms
```

合并后分两组：**A 组已收录**（有成绩，可重排）、**B 组未收录**（标「未收录」，可看官方页）。
默认 A 组按成绩排 —— 官方搜索是按相关度排的（实测第 5 名 429 万点击排在第 6 名 614 万前面），
**同样的结果集按成绩重排后信息量完全不同，这才是我们的价值。**

### 搜索即采集（投入产出比最高的一条）

简介在原库 100% 缺失，逐本详情页抓要 `1 本 = 1 请求`。
而一次 HTML 搜索 `29 本 = 1 请求`，带回 `intro` + `last_update` + `cover` + 作者 + 分类 + 评分。

于是每次搜索顺手做三件事：补 `details`、校正 `genre`、把库外的书写进 `search_miss`。

**`search_miss` 是最有价值的一张表：用户的搜索行为自动告诉我们该收录哪些书。**
下次种子包生成时优先纳入这些书——它们已经被真实需求验证过。

### 本地搜索不用 FTS5

2 万条数据太小，trigram 索引（1–2MB）比数据本身还大，
且中文两字词不足 3 字符时 `MATCH` 直接失效。改用内存前缀 + 子串 + 拼音首字母匹配，
遍历 2 万条约 20ms。`catalog_fts` 在 schema 里已注释停用。

### 空结果三档兜底

1. 联想词给出近似书名（可治记错书名、别名、全角括号）
2. 同分类的经典（该分类点击 top 10）
3. 全站热门 top 10 + 「换个词试试」

**永远不给出真正的空页面。**

## 6. 刷新策略

| 数据 | 触发时机 | 频率 |
| --- | --- | --- |
| 榜单 top N | App 前台 + 下拉刷新 + 后台任务 | 6 小时 |
| 书架内书籍成绩 | 打开书架时 | 24 小时 |
| 详情页 | 进入详情页且 `fetched_at` 超 7 天 | 按需 |
| 官方搜索（搜索即采集） | 用户搜索时，防抖 400ms | 同词 24h 一次，单日 200 次上限 |
| 种子版本检查 | App 启动（异步、不阻塞首屏） | 每 24h 一次；有新种子则后台下载，下次启动生效 |

**种子与 App 版本解耦**（§6.5）：走高版本才更新种子 = 不更新 App 的用户永远吃旧数据。
反方向也要防：旧 App 遇到 `seed_format_version` 更高的种子必须能**安全忽略**，
不能解压后崩在 `no such column`。

iOS 后台执行受限（约 30s，且系统调度），不依赖它——**榜单刷新只在 App 处于前台时进行**，配合下拉刷新给出即时反馈。

### 限速与礼貌

- 全局串行（并发 1–2），请求间隔 ≥ 800ms，指数退避（1s → 2s → 4s，最多 5 次）
- 只取公开元数据：书名 / 作者 / 字数 / 点击 / 收藏 / 点赞 / 简介 / 状态 / 封面
- **不碰正文，不做任何绕过登录或风控的事**
- 详情页抓取失败 → 保留旧数据 → UI 展示「数据可能过期」而不是报错

## 6.5 数据生产与分发：分三期，v1 完全没有服务端

先定调：**第一版是纯静态架构**。种子里打包好数据、从 GitHub Release 分发、端上按需抓详情，
全程没有服务端。FastAPI 后端属于第三期，等自己的爬虫跑通并稳定之后再慢慢做。

| 期 | 种子来源 | 端上写入 | 出网请求 | 何时进入 |
| --- | --- | --- | --- | --- |
| **P0 bootstrap**（现在） | 上游 novly 快照 + 我们补采 | `catalog` 可写 + `user_patch` 日志 | 只抓详情 / 搜索 | 立刻 |
| **P1 自产** | 100% 自己的爬虫 | 同上 | 同上 | 爬虫满足四条判据（见 §6.5 末） |
| **P2 回流** | 自己的爬虫 **+** 用户观测聚合 | 同上 + 批量上报 | 多一个 FastAPI | 进入条件见本节末（原 `cloud.md` 已并入） |

**P0 和 P1 都没有服务端。** 两者用的库结构、写入逻辑、抓取策略完全相同，
差别只在种子里有多少行是 `stats_src='own'`——即「多大程度上不再依赖第三方」。
第三期加后端，解决的也**不是**「没有后端就转不动」，而是两件 P0/P1 做不到的事：
闭包外的长尾（用户点开一本 6 月后上架、我们列表页还没扫到的书）、
以及两次构建之间的新鲜度。这两件事在 P0/P1 可以先用「扩大闭包 + 缩短构建周期」硬扛，
代价是采集时间线性涨——所以先量一量值不值（判据在下面「该不该进 P2」）。

### 没有后端时，种子怎么更新

唯一的通道是 **GitHub Release 静态文件**，不是 App 版本：

```
App 启动 → GET releases/latest（或 raw 的 seed-manifest.json）
        → 比对 seed_version > 本地
        → 后台下载 seed.sqlite.gz（2.4 MB）→ 校验 → 原子替换 → 重放 user_patch
```

所以「种子随版本发」是错的：**用户半年不更新 App 就要吃半年旧数据**。
种子版本必须与 App 版本解耦，靠 `meta.seed_format_version` 做兼容判断
（端上认得的格式才替换，认不得就跳过——旧 App 遇到新格式种子必须能安全忽略，
而不是崩在解压后的 `no such column`）。

这条通道顺便解决了一个隐性问题：**新用户装上就有数据**。不需要首启联网预热，
也不需要「请稍等，正在初始化」。

### 零后端的应急降级：种子兼作配置通道

没有后端就没有下发开关的地方。但种子本身是从 GitHub 拉的静态文件，
它是唯一能「不经过发版」到达所有客户端的外来数据，所以把配置塞进 `seed.db` 的 `meta`：

| key | 作用 | 端上行为 |
| --- | --- | --- |
| `crawl_enabled` | `0` = 停止端上详情抓取 | 立刻降级为纯离线浏览，只用已有数据 |
| `crawl_min_interval_ms` | 每设备请求下限 | 覆盖 App 内置默认值 |
| `detail_ttl_days` | 详情缓存有效期 | 默认 14，风控收紧时可拉长 |

**代价要说清楚**：配置生效延迟 = 种子更新周期（可能几天）。
「站方开始封禁、需要立刻全体停机」这种应急操作，靠种子太慢。
所以另加一个更快的通道：Release 里放一个纯文本 `flags.json`，App 启动时读它，
失败就沿用种子里的值。**这不是后端，是一个静态文件**——没有进程、没有数据库、
没有可用性问题（读不到就走兜底），但它把应急响应从「天」降到「分钟」。

### 种子必须可写，但不能只是"可写"

**这一节在 P0 就成立，与有没有后端无关。** 端上两个库（DDL 见 `schema.sql` 顶部）：

| 库 | 内容 | 种子更新时 |
| --- | --- | --- |
| `seed.db` | catalog / banners / tags / book_tags / tag_stats / tag_combos / rank_lists / rank_snapshots / meta | **整包替换**，但 catalog 与 banners 用户可写 |
| `user.db` | details / shelf / search_log / search_miss / user_patch / local_meta | **永不替换** |

直接往 `catalog` 里写是不够的：下次种子替换，用户改的东西全部消失。
所以真正的写入顺序是 **先写日志、再物化**：

```
① 事务写 user.db›user_patch   （payload + src + observed_at + base_seed）
② UPDATE seed.db›catalog      （失败无所谓，下次启动重放）
```

`user_patch` 是 source of truth，`catalog` 只是它的物化结果。
种子替换后启动时重放：`observed_at <= 新种子 snapshot_at` 的观测作废，
其余写回 catalog。**这是全 App 唯一需要跨库的地方，且只在启动时跑一次。**

### 两个写入口

| 触发 | 写什么 | src |
| --- | --- | --- |
| 用户点开详情页 | 详情 API 一次返回全指标 → `catalog` 更新 + `details` 缓存 + `user_patch` | `detail` |
| 搜索命中种子外的书 | 自动收录：`catalog` 插一行（`stats_src='own'`）+ `user_patch` | `search` |

自动收录的书**没有榜位**（`rank_snapshots` 是构建期快照，本地不重算——否则用户看一次详情页
就能把榜顶动，榜就不可解释了）。UI 必须能显示「有书、无排名」。

第一次收录失败（网络/解析/已下架）才落 `search_miss`，下次启动重试；`retry_cnt >= 3` 放弃。

### P2：回流（端上 → 后端 → 新种子）—— 现在不做

```
user_patch WHERE synced_at IS NULL AND observed_at > now-30d
   └─ POST /v1/observations  （批量 200 条，匿名 client_id）
        └─ FastAPI Cloud ──→ Neon Postgres（聚合表，一本书一行）
             └─ GitHub Actions 每周拉一次聚合结果
                  └─ 生成新 seed.db（用户观测优先于上游旧值）
```

- **只报 payload**（公开可爬的书籍元数据）+ `observed_at` + 匿名 `client_id`。
  **不报** `shelf` / `search_log` / 任何设备标识。阅读偏好不是数据资产。
- **「从客户端获取信息」的边界划在这里**：只收**原本就在公开网页上、人人用浏览器也能看到**的
  那几个数字。不收停留时长、跳出率、点击热区——那些是行为数据，
  一旦开始收，「帮我少爬几次」就变成了「拿用户画像换服务」。
  判断标准很简单：**这份数据我能不能用一条 curl 自己拿到？** 能，才可以收。
- P2 后端只做两件事：收、聚合，不存用户、不发推送、没有登录。原 `cloud.md` 的
  FastAPI + Neon 具体实现蓝图未落地、已删除；其**四条进入条件**保留在本节末。

**注意 `observed_at > now-30d` 这个过滤**：P2 上线时，设备上可能已经攒了半年的
`user_patch`。这些旧观测对「这本书现在多少人气」毫无价值（半年前的数），
一起上报等于往聚合表里灌历史数据。只有 30 天内、且晚于种子里 `stats_at` 的才值得报。
更老的记录只保留一个用处：证明「这本书存在过、标题作者是这两个字」。

### v1 就要埋的四个伏笔（不做就等于 P2 白干）

1. **`local_meta.client_id` 首次启动就生成**（随机 UUID，无设备指纹）。
   P2 上线时若没有它，所有存量设备都会被当成「新设备」，
   `clients >= 3` 这条防脏数据的阈值永远达不到——因为每台机器每次都算第一次。
2. **`user_patch.synced_at` 在 v1 恒为 `NULL`。** 这不是缺陷，是正确的语义：
   「有日志、未上报」。P2 加一个上报模块就能直接接手，无需数据迁移。
3. **将来补报必须有窗口**（见上面 30 天）。这条现在写下来，是为了防止 P2 时
   「既然有日志就全报上去」的直觉——那会把聚合表变成历史归档。
4. **`search_miss` 要记 `keyword` 和 `title`**，即使 v1 只拿它做失败重试。
   它是 P2 最有价值的信号：**用户搜了、库里没有** = 种子闭包漏了哪一块。
   没有这条记录，P2 就只剩「用户点开过的书」这一类信号，而那类信号天然偏向头部。

### 该不该进 P2：v1 自己就能算，不用等后端起

`user_patch` 已经在本地记了每一本被点开/被搜到的书，所以进入条件不需要后端数据：

```sql
SELECT COUNT(*)                                              AS 被观测的书,
       SUM(CASE WHEN c.id IS NULL THEN 1 ELSE 0 END)         AS 闭包外,
       ROUND(100.0 * SUM(CASE WHEN c.id IS NULL THEN 1 ELSE 0 END)
             / COUNT(*), 1)                                  AS 闭包外占比
FROM user_patch p LEFT JOIN catalog c ON c.id = p.book_id;
```

若「闭包外占比」长期 > 5%，说明用户真正去看了、而我的采集范围够不着的书，
已经占了可观比例——**这才是建后端的真实理由**（要么扩闭包，要么回收观测）。
若这个数一直 < 1%，那后端的主要价值就只剩「两次构建之间的新鲜度」，
而那件事缩短构建周期更快、更省事。

### 采集：走 App API，不解析 HTML

**先说结论**：`api.sfacg.com` 一次请求就能拿全所有字段，且人气是精确整数。
解析 HTML 只作为兜底（API 改版或封禁时）。

```http
GET https://api.sfacg.com/novels/{nid}
    ?expand=latestchapter,chapterCount,typeName,intro,fav,ticket,pointCount,tags,sysTags,signlevel
authorization: Basic <App 内置固定串，见 data-findings.md §13.2>
```

返回：`viewTimes`（人气，精确到个位）、`markCount`（收藏）、`expand.fav`（赞）、
`expand.ticket`（月票）、`point`（评分）、`charCount`、`chapterCount`、
`expand.intro`（**简介，不用再单独抓**）、`expand.sysTags[]`（含 `sysTagId`）、`addTime`。

**为什么不再解析 HTML**：网页上人气显示为「10903.2万」——只有 5 位有效数字，
造成大批假并列；API 给的是 `109032154`。而 HTML 唯一的优势是不需要认证头。

| 范围 | 请求数 | 1s 间隔耗时 |
| --- | --- | --- |
| 种子闭包 19,856 本 | **19,856**（列表页 990 个用于发现新书） | 约 5.5 小时（摊 7 天 = 47 分钟/天） |
| 全库 246,045 本 | 246,045 | 约 68 小时，不可行 |

**「只内置闭包」的真正意义**：不是省 20MB 流量，是把一次不可行的全量重采
变成每天 47 分钟的例行任务。

**新书发现**走列表页（`book.sfacg.com/List/default.aspx` 只有 nid/标题/作者/分类/封面，
没有成绩），一天一页翻到「更新超过 7 天」为止。

**注意这是两套 API**：web/mobile-web 一套 HTML 页面，App 一套 `api.sfacg.com`。
**App 有 10 多个榜单（用户确认），web 只有 6 个**，而 App 的榜单端点尚未公开暴露
（`/rank`、`/ranks`、`/home/rank` 全 404，`/novels?sort=` 被忽略）。
**待办：抓包确认 App 榜单端点**——如果能直接拿到官方 10 个榜的排名，
它就是我们「榜位闭包」的一部分，比我们自己推算更省事。

### 「爬虫跑通」的判据（P1 的门槛，四条缺一不可）

不是「能跑一次成功」，是下面四条同时成立才允许停掉上游依赖：

| # | 判据 | 怎么验 | 不过关的后果 |
| --- | --- | --- | --- |
| 1 | **自主发现**：新增书覆盖 ≥ 95% | 连续 7 天列表页翻页结果 vs 站方 `addTime`，按天对账 | 新书永远落后别人，产品看起来像停更了 |
| 2 | **一轮 ≤ 24h** | 19,856 本 × 1s ≈ 5.5h，留 4 倍余量给退避重试 | 采集追不上变化，数据自相矛盾 |
| 3 | **无人值守 14 天** | GitHub Actions 连续全绿，零人工介入 | 「跑通」是假象，一断就没人知道 |
| 4 | **diff 可解释** | 每日变化落在预期区间（人气 +0.1%~2%，收藏 +0~1%）；10× 跳变必须**告警**而非静默写入 | 字段语义又一次悄悄坏掉（§4 那三层断层就是这样来的） |

第 4 条最容易被跳过，也最致命：上游 `like_num` 那个错误的成因，正是
「数字变大了、看着更好、没人报警」。所以我们自己的采集器第一天就要带阈值告警，
哪怕初期误报多——误报是噪音，静默是数据损坏。

P1 完成后，`stats_src` 里 `'upstream'` 的行应该只剩历史存量，且随着每轮采集逐步清零。
这个清零进度是**P1 是否真的完成**的唯一客观指标。

**P2 服务端（原 `cloud.md` §7 四条进入条件，该文件已删除，条件内联于此）**：
以下四条**同时成立**才动手建后端，缺一条就不写——后端一旦存在，
就会有账号同步、云备份、推送等引力把「零服务端」变成需要值班的东西。

| # | 条件 | 阈值 | 理由 |
| --- | --- | --- | --- |
| 1 | 自己的爬虫稳定 | ≥ 4 周连续全绿、零人工介入 | 「跑通」是假象，一断就没人知道 |
| 2 | 种子构建周期 | > 2 周 | 若构建足够快，「两次构建之间的新鲜度」不是问题，不需要后端补 |
| 3 | 端上闭包外占比（上文 SQL） | > 5% | 用户真正去看了、而采集范围够不着的书占可观比例 |
| 4 | 日活观测 | ≥ 50 条新观测/日 | 观测回流有足够样本，否则收上来的数据不足以聚合 |

v1 与 P1 均为**零服务端**：客户端只抓详情/搜索、只写本地 `user_patch`，不上传。

## 9. 风险

1. **上游改版**：parser 一崩，详情页就补不上。用 golden test 锁住解析结果，失败静默降级。
2. **种子边界感**：种子 19,791 本，用户翻到种子之外的书时只能在线补——做好骨架屏，不要白屏。
   但实测这个边界几乎不会被触到：榜长 200 × 80 个 facet 组合已远超任何人会滑的深度。
3. **搜索依赖网络**：本地只索引 19,791 本，官方搜索接口挂掉时用户会漏掉未收录的书。
   → 三层降级：HTML 搜索失败退 API（12 条无简介），再失败退纯本地；文案要诚实，不假装搜过全库。
4. **搜索接口本身会被改版**：`s.sfacg.com` 是 HTML 页面，结构一变就崩。
   → 用 61KB 真实样本做 golden test；`TypeName` 出现「玄幻」这类新分类时保留原文，不强行塞进 9 个 genre。
5. **排序质量即产品质量**：榜长只有 200 条，数据量再大也救不了烂排序。
   **护城河是「同样的 200 条有多少种排法」，不是「收集了多少数据」。**
6. **法律与合规**：仅公开元数据、限速、可一键关闭采集。不要因为"能爬"就扩大范围。
7. **跨库 id 混用（静默数据损坏）**：上游分片里 `tags.id` / `contests.id` **是废号**——
   不只是「片内有效」，而是连片内序号都不是（cold 99 行却撑到 710,395 号，
   三片 81 个共有 name 的**同 id 率 0%**）；只有 `books.id`（官方 nid）是全局的。
   构建 seed 时任何跨片 JOIN 都必须以 `name` 对齐，否则会把全部标签关系映射错，**且不报任何错**。
   → 构建器加硬断言：导入后 `book_tags` 行数、`tags` 行数必须与源库合计一致，不一致直接失败。
   详见 `data-findings.md` §16.2 / §12。
8. **给标签做语义合并（最隐蔽的错误）**：把「百合」并进「橘味」、把「末日」并进「末世」，
   看起来是数据清洗，实际会把两批不相交的书混成一个假标签——「末世」8,813 本与
   「末日」465 本**交集为 0**，合并后 `book_count`、`density`、`tag_stats` 全部失真，
   而且没有任何下游信号能发现（数字看着更大了，像是更好）。
   → **禁止任何形式的语义映射**：不合并 `book_tags`、不加别名表、不做同义词召回扩展。
   `tags.name` 的 UNIQUE 只保证字符串不重复，不保证语义；同义标签当两个标签用。
9. **过早建后端（项目管理风险，不是技术风险）**：后端一旦存在，就会有「让它顺便做个 X」的引力
   ——账号同步、书架云备份、推送、运营配置——每一条单看都合理，合起来就把「零服务端」
   变成一个需要值班的东西。而它当前唯一不可替代的价值（闭包外长尾）是**可以量化的**：
   `user_patch` 的闭包外占比在 v1 本地就能算（见 §6.5），不到 5% 就不该建。
   → 进入条件四条见本节末，缺一条就不写（原 `cloud.md` 已并入）。

10. **绝对门槛制造时间窗口假象（最容易被包装成「权威」的错误）**：
    「殿堂」旧定义是 `is_banner=1 AND view_num>=5000万` → 14 本，看起来是「全站最强」，
    实际**全部落在 2015–2022**（2006–2014 用户少、2023–2025 时间不够）。
    这类门槛不会报错，只会安静地排除掉整个时代，而结果是**看起来更权威了**。
    → 凡是跨年比较，一律用当年分位（`era_pct`）或年内排序；
    任何「绝对人气 / 绝对收藏」的门槛都要标注它偏向哪一段时间。
    已知的同类陷阱：`view_num` 给轮播加权、`view_num>=5000万` 定殿堂、
    用 `last_update` 分年（长时间连载的书全堆在 2026）。
