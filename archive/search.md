# Novly · 搜索设计：本地索引 + 官方接口混合

> 背景：种子里只有 11,442 本（覆盖全部可消费榜位），而 SFACG 全库 24 万+ 且每天增长。
> 用户搜不到书会直接判定「这 App 不好用」——**空结果是产品死亡的第一因**。
> 所以搜索不能只有本地，也不能只有官方。必须混合。

---

## 1. 三个官方接口的实测边界

全部来自 `temp/sfacg_tools/sfacglib/search.py`，已用真实请求验证（2026-11-15）。

| 接口 | 端点 | 返回 | 条数 | 关键字段 |
| --- | --- | --- | --- | --- |
| **JSON 搜索** | `m.sfacg.com/API/HTML5.ashx?op=search&keyword=` | JSON, 2KB | **固定 12 条，无分页** | `NovelID` `NovelName` `AuthorName` **`TypeName`** **`Point`** `NovelCover` |
| **HTML 搜索** | `s.sfacg.com/?Key=&SS=0&S=1` | HTML, 61KB | **全量**（实测 29 条） | `NovelID` `NovelName` `AuthorName` `last_update` **`intro`** `cover` |
| **联想词** | `m.sfacg.com/API/Book.ashx?op=searchreffer`（POST） | JSON | 15 条 | `keywords[]`（完整书名） |

### 实测结论

**① 两个搜索接口的字段互补，不能只用其中一个。**

```
HTML 有：简介、最后更新时间、封面、作者     → 没有评分
API  有：评分 Point(0–10)、分类 TypeName     → 没有简介，且只有 12 条
```

`intro` 是**决定性差异**：原库完全没有简介（见 `data-findings.md` §5），
而 HTML 搜索一次就带回 29 本完整简介。

**② 官方搜索不是按成绩排的。** 实测「英雄」的返回顺序：

| 序号 | id | 点击 | 说明 |
| --- | --- | --- | --- |
| 1 | 48704 英雄再临 | 1.19 亿 | |
| 2 | 120384 拜托请不要再找我当超级英雄了 | 1512 万 | |
| 3 | 208296 我只是个路过的超级英雄 | 1254 万 | |
| 5 | 111608 复活的英雄是女孩 | **429 万** | |
| 6 | 651053 谁说光速退役的不算英雄 | **614 万** | ← 点击更高却排在后面 |

前 4 条严格递减，之后打乱。所以是**相关度排序**（标题匹配度 + 热度混合），
不是成绩排序。这恰好是我们的机会：**同样的结果集，按成绩重排后信息量完全不同。**

**③ API 硬上限 12 条，且无分页。** 实测 `page=2` / `pi=2` / `p=2` / `PageIndex=2` 全部仍返回 12 条。
要更多结果只能走 HTML 版。

**④ 官方库也有遗漏，不只是「新书未收录」。**
「英雄」的 29 条结果里有 2 条不在我们的 24.6 万本库里：
- `53831` 退役英雄的我现在正带着孩子（2017-07 上架的老书）
- `485894`

所以本地搜不到 ≠ 书是新的。**是官方数据本身有洞。**

**⑤ 作者名可搜。** 「无聊看看天」返回 7 本，含 2026 年新书
`693020 长生？真是有够逆天`（453 万点击）——这本书**在我们的库里**（hot 分片），
说明 novly 快照追到了 2026-06，缺的主要是最近几个月。

**⑥ 无结果时干净返回** `{"Status":200,"Novels":[]}`，不报错、不返回 HTML 错误页。

**⑦ `TypeName` 是中文分类**（科幻 / 魔幻 / 都市 / **玄幻**）。
注意「玄幻」不在原库的 9 个 genre 编码里，需要一张映射表兜底。

## 2. 三层搜索架构

```
用户输入
  │
  ├─ L0 联想（0ms 本地 / 150ms 官方）
  │   本地：11,442 条标题前缀 + 拼音首字母
  │   官方：op=searchreffer → 15 个完整书名
  │
  ├─ L1 本地结果（<20ms，同步）
  │   内存索引命中 → 立即渲染，带全字段成绩
  │
  └─ L2 官方结果（200–500ms，异步追加）
      HTML 全量 + API 评分 → 按 id 与 L1 合并
      → 新 id 追加为「未收录」，并写入 details（永久缓存）
```

**关键体验约束：任何一层的失败都不能导致白屏或空列表。**
L2 超时 → 保留 L1 结果 + 显示「网络不佳，仅显示已收录的 N 本」。
L1 无命中 → 骨架屏 + 「正在搜索全库…」，等 L2。

## 3. 合并与排序

### 分组

| 组 | 条件 | 展示 |
| --- | --- | --- |
| **A 组（已收录）** | id 命中本地 11,442 本 | 全字段：点击/字数/状态/分类/评分，可点进详情 |
| **B 组（未收录）** | 仅在官方结果中出现 | 书名/作者/分类/评分/简介；标注「未收录」，点进去给出官方页链接 |

### 排序

默认：**A 组按用户当前选择的维度排，B 组按官方相关度附后。**

理由：用户来这个 App 是为了「按成绩找书」，不是要一个官方搜索的镜像。
搜「英雄」时，把 1.19 亿点击的《英雄再临》放在第一位，比官方按相关度排更有用。

提供一键切换：`按成绩` ↔ `按相关度`。
按相关度时 A/B 混排，完全跟随官方顺序（用于「我知道书名，帮我找那本」的场景）。

### 去重

按 `NovelID`。官方两个接口自身都可能返回重复（联想词里有
`英雄再临(英雄？我早就不当了)` 和全角括号版本两条），合并时统一规范化后去重。

## 4. 搜索即采集：一次请求补 29 本简介

这是本设计里投入产出比最高的一条。

**现状**：简介在本地 100% 缺失，逐本详情页抓取要 `1 本 = 1 请求`。
**现在**：一次 HTML 搜索 `29 本 = 1 请求`，带回 `intro` + `last_update` + `cover` + 作者。

于是每次搜索都顺手做三件事：

```dart
// 伪代码
final results = await officialSearch(keyword);   // 1 个请求
for (final r in results) {
  await details.upsertPartial(
    bookId: r.id,
    intro: r.intro,              // 从无到有
    lastUpdate: r.lastUpdate,    // 判断完结/断更
    typeName: r.typeName,        // 校正 genre
    point: r.point,              // 新维度：评分 0–10
    source: 'search',
    fetchedAt: now,
  );
  if (r.id 不在 catalog) {
    await searchMiss.add(r.id, keyword);   // 下次种子包的候选
  }
}
```

**限制条件（必须遵守，否则会变成滥用）：**

- 同一关键词 24 小时内只打一次官方接口（本地缓存结果集）
- 用户输入停止 400ms 后才发请求（防抖）
- 单日官方搜索请求上限（如 200 次），超出后纯本地搜索
- 不因为「想补数据」而主动构造搜索词 —— **只记录用户真实搜索**

## 5. 空结果的三档兜底

用户说「搜不到会很沮丧」，所以**永远不能给出一个真正的空页面**。

| 档 | 触发 | 展示 |
| --- | --- | --- |
| 1 | 官方返回近似书名（联想词命中） | 「你是不是想找：xxx / yyy / zzz」 |
| 2 | 无近似书名，但能推断分类 | 「同分类的经典」→ 该分类点击榜 top 10 |
| 3 | 什么都没有 | 「全站热门」→ 总榜 top 10 + 「换个词试试」提示 |

第 1 档最有用。实测联想词对「英雄」返回 15 个书名，包含
`英雄我早就不当了`（即《英雄再临》的别名）——这说明联想词能补上
**用户记错书名**和**别名/全角括号**这类问题。

## 5.5 标签不做同义词扩展（一个明确的「不做」）

用户在搜索框打「百合」，书名匹配命中 **303 本**；站方对应的词是「橘味」（6,214 本），
其中只有 1 本落在那 303 本里（站方换词时不回写旧关系，data-findings §16.3）。
所以「搜百合也带出橘味」看起来能多召回 6 千本——**但我们不做**，理由三条：

1. **两批书不重合，桥接等于编造关系。** 303 本和 6,213 本是**两个不相交的集合**，
   硬拼成一个结果块，用户会以为「这些书都叫百合」。
2. **同义是语义判断，不是数据判断。** 唯一能验证的同类案例反而证伪了它：
   「末世」8,813 本和「末日」465 本**交集为 0**，而「末日」2026-04 还在用——
   站方不做语义去重，两批作者各打各的词。既然连"明显同义"的都不能合并，
   就更没有可自动化的判据。
3. **用户不需要我们替它决定。** 同义标签并存不是噪音，是**多一条入口**：
   看到「末世」和「末日」并列，用户自己知道哪个更贴他要的东西。
   多给一个词，比少给一个词安全。

替代路径本来就通，不需要额外机制：

```
搜「百合」→ 303 本书名命中 → 点进任一本 → 详情页标签「恋爱/热血/同人」可点
                                              → 顺着标签跳，而不是顺着同义词跳
```

所以搜索层与标签层**零耦合**：书名搜索只匹配书名/作者/拼音，标签只做浏览维度。
`tags` 表里唯一约束就是 `name UNIQUE`，没有别名表、没有映射表、没有 canonical 字段。

⚠️ 一个诚实的代价：不知道「橘味」这个委婉语的新用户，**一步之内找不到那 6,214 本**。
接受这个代价——因为猜错的代价更高（把 303 本硬塞进 6,214 本里，
用户点进去发现"这书名里根本没提百合"，信任就没了）。
想补这一档的话，正确做法是**搜索无结果时推荐热门标签**（§5 第 2 档），
而不是给某个词伪造同义词。

## 6. 本地索引：不用 FTS5

`schema` 里原本建了 `catalog_fts`（trigram），但这里要改掉：

| | FTS5 trigram | 内存匹配 |
| --- | --- | --- |
| 索引体积 | +1–2 MB | 0 |
| 中文两字词 | **MATCH 失效**（schema 已注明），实际只能用 `LIKE '%kw%'`，等于全表扫 | 天然支持 |
| 拼音首字母 | 不支持 | 支持（`yxlz` → 英雄再临） |
| 延迟 | 10–30 ms | 11,442 条遍历 < 10 ms |

11,442 条数据太小，**索引本身比数据大**，得不偿失。

实现：启动时把 `id / title / author / 拼音首字母 / 分类 / 点击 / 字数` 载入内存
（约 1.1 MB RAM），构建：

```dart
Map<String, List<int>> _prefixIndex;   // 单字前缀 → id 列表
List<int> search(String q) {
  // 1. 规范化：全半角统一、去空格、小写
  // 2. 前缀命中（最快，覆盖 80% 输入）
  // 3. 子串命中（作者名、书名中间词）
  // 4. 拼音首字母命中
  // 5. 按 view_num DESC 排序，取 top 50
}
```

`catalog_fts` 保留但不建 —— 或直接删掉，减少 schema 复杂度。

## 7. Schema 增量

```sql
-- details 表补 4 个字段（搜索接口能直接给）
ALTER TABLE details ADD COLUMN type_name   TEXT;     -- 官方中文分类
ALTER TABLE details ADD COLUMN point       REAL;     -- 评分 0–10，原库没有
ALTER TABLE details ADD COLUMN last_update INTEGER;  -- unix 天，判断完结/断更
ALTER TABLE details ADD COLUMN source      TEXT;     -- 'search' / 'detail_page'

-- 搜索日志（本地，用于热词与排序权重）
CREATE TABLE search_log (
  keyword    TEXT NOT NULL,
  hits_local INTEGER NOT NULL,
  hits_remote INTEGER NOT NULL,
  searched_at INTEGER NOT NULL
);

-- 库外书（用户搜到但种子没收录）→ 下次种子包的候选清单
CREATE TABLE search_miss (
  book_id    INTEGER PRIMARY KEY,
  title      TEXT,
  author     TEXT,
  type_name  TEXT,
  point      REAL,
  keyword    TEXT,
  first_seen INTEGER NOT NULL
);
```

`search_miss` 是最有价值的一张表：**用户的搜索行为自动告诉我们该收录哪些书**。
下次生成种子包时，`search_miss` 里的书优先纳入（它们已经被真实需求验证过）。

## 8. 与种子策略的关系

搜索层不改变种子规模（11,442 本 / 223 KB），但改变了「种子够不够用」的答案：

| 场景 | 无官方搜索 | 有官方搜索 |
| --- | --- | --- |
| 搜到已收录的书 | 命中，有成绩 | 命中，有成绩（**体验相同**） |
| 搜到未收录的新书 | **空结果，用户流失** | 显示基本信息 + 简介，标「未收录」 |
| 搜错字 | 空结果 | 联想词纠正 |
| 搜到官方库遗漏的书 | 空结果 | 显示，可看官方页 |

结论：**11,442 本的种子 + 官方搜索 = 全库搜索体验，且带成绩重排。**
这是「不捆绑大数据」这个约束下唯一可行的组合。

## 9. 风险

1. **接口随时可能变**：`s.sfacg.com` 的 HTML 结构一改就崩。
   → parser 抽成纯函数 + 用本次抓到的 61KB 样本做 golden test；失败降级到 API（12 条无简介）。
2. **被限流**：搜索接口是公开的，但高频仍会触发风控。
   → 关键词 24h 缓存 + 400ms 防抖 + 单日上限；超限后纯本地。
3. **`TypeName` 无法映射**：出现「玄幻」这类新分类。
   → 映射表 miss 时保留原文，不强行塞进现有 9 个 genre。
4. **B 组结果的质量**：未收录的书没有成绩，用户可能误判为「差书」。
   → 明确标注「未收录」，并显示能拿到的 `Point` 评分作为参考。
5. **隐私**：搜索词是个人偏好数据。
   → 只存本地，不上传；提供一键清空。
