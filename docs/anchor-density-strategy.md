## 1. 结论

用户提议「小 id 区少放锚点（空位多、误差本来就大），高 id 区多放锚点（让外推更准）」。结论：**后半句方向对但机制错，前半句因果反了。**

1. **「小 id 误差大」是事实，但原因是锚点/数据源少，不是锚点多。** <1 万区只有 9 个锚点、LOO p90≈117d（全库 interp 整体 p90=3d）；把 <5 万区锚点删掉一半，整体 p90 仅从 3.0→3.4d，但全库最大误差从 428d 暴增到 **3632d**——早期锚点是关键支点，不是可裁剪的冗余。
2. **「高 id 加密让外推更准」机制错。** 外推只发生在 `nid > max(anchors)`（当前 788076）之外；区间内全是内插，70 万+ 已有 97 个锚点（全库最密、每锚点仅覆盖 310 本书），区间内 p90≈1d，再加密无收益。真正有效的是**持续把最大锚点往前推**，缩短外推距离。
3. **真正的密度洼地是 40–70 万**，每锚点覆盖 2000–2700 本书（vs 高 id 区 310）；但该段 LOO p90 仅 0–4d，补锚点边际收益有限——不是优先项。
4. **可操作建议**：把「调整密度」改成「**常态化补最新锚点**」——每有新的 exact `addTime` 就把 max anchor 往前推一次。这是唯一能实质降低外推误差的手段，且成本极低（一次一条）；早期锚点保留，不删。

|---|---:|---:|---:|---:|---|

## 3. 用户假设逐条验证

### 3.1 「小 id 空位多、误差大 → 少放锚点」：因果反了

<1 万区 nid 跨度小、锚点稀疏且多为 `manual_early` 人工核定，LOO p90 117d；误差大**正是因为锚点少/数据源稀缺**，减少锚点只会让内插区间更宽、误差更大。删锚点模拟（快照现算）：

| 操作 | 锚点数 | interp p90 | 全库最大误差 |
|---|---:|---:|---:|
| 不动 | 281 | 3.00d | 428d |
| 删 <5 万的一半 | 249 | 3.40d | **3632d** |
| 删 <1 万的前 3 个 | 278 | 2.00d* | （误差被转移，非消除） |

\* 该「p90 下降」是**评估口径假象**：删掉 2242/2243/2347 后，这三个早期锚点不再进入 LOO 留出集，原本落在这些 nid 的书改走 `extrap_low`，误差被藏起来而非消失。**不能据此删早期锚点。**

### 3.2 「高 id 多放锚点让外推更准确」：机制错

定年模型是 `log(nid) ↔ day` 分段线性（Python `eras._Model` / Go `eras.Estimate`）：

- `nid <= max(anchors)` → **内插**，取两侧锚点线性插值；70 万+ 区间内已有 97 个锚点、p90≈1d，**区间内加密没有改善空间**。
- `nid > max(anchors)` → **外推**，斜率由 `_edge_slopes()` 取最后两个不同秒锚点算；误差 ≈ 斜率 × `ln(nid) - ln(max_anchor)`，**只与超出距离有关**。

所以在高 id 区间内部增减锚点，对推到 80 万+ 的新书毫无帮助；唯一有效的是**让 max anchor 本身往前移**。举例（快照现算）：末尾两点 786862(2026-10-17) 与 788076(2026-11-01) 相差 15 天 / 1,214 nid，按此外推到 nid 800,000 约偏 **147 天**；若把 max anchor 补到 800,000 附近，该误差直接归零。

**另一个约束**：今天（2026-11-21）距最新锚点（2026-11-01）已 20 天，期间新书都在外推段；外推误差随时间线性累积——这是当前最大的时效短板，与「区间内密度」无关。

## 4. 操作：修正后的策略

按优先级：

**P0 — 常态化补最新锚点（唯一能实质降低外推误差，已定为常规动作）**
- 每拿到一条新的 exact `addTime`（App API 秒级字段，或用户 App 观测），若其 nid > 当前 max，就追加到 `nid_anchors.jsonl`。
- 目标：max anchor 与当前最新 nid 的距离 ≤ 几天，而不是落后几周。
- 成本：一次一条，无需批量爬虫。追加后跑生成脚本同步 Go 与 golden test。

**P1 — 早期锚点全部保留**
- 不为「简化」删早期锚点；它们是低 nid 内插的关键支点，删除会把误差转移到外推段。

**P2 — 中段 40–70 万按需补（低优先）**
- 密度洼地，但 LOO p90 已 0–4d，边际收益很小；若要做，目标「每锚点覆盖 ≤1,000 本书」（每段补到 30–40 个锚点），仅在有现成 exact 数据时顺手补，不专门爬。

**P3 — 外推斜率的稳健性（可选，需改算法，不在本轮范围）**
- `_edge_slopes()` 只用最后两个不同秒锚点，若受审核积压/批量导入影响会失真；可考虑用尾部 N 个锚点做稳健回归，但须保留「跳过同秒点」逻辑。属算法改动，`app/` 冻结期间不做。

## 5. 边界与风险

- **数字均为现算快照**：锚点每追加一条，分布与 LOO 都会变，不要硬编码。
- **LOO 的 extrap 样本极少**（高 1、低 2），不能用来估计真实外推误差；真实误差看 §3.2 的 ln 距离推算。
- **nid 不一定严格均匀增长**：审核积压、批量导入会让相邻锚点的 nid/时间比失真，「按每 N 本书采一个」只是初始网格，实际以 exact 数据可用性为准。
- **采样禁区**：不把 `20XX萌神` 年份、featured 封面时间戳、征文页起止时间当锚点。新增 max anchor 取当前能拿到的最大 nid 且带 exact `addTime` 的书；中段从 universe 按 nid 排序每隔约 1,000 本取一本（须 exact、优先已有快照、不新爬）；早期不删不加。

生成链路（改 jsonl 后）：
```

# 产出 app/engine/internal/eras/{anchors.go, eras_golden_test.go}
```
