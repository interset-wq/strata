# 定年锚点密度策略：按 id 区调整是否成立

> **口径**：本文所有计数/误差均为 2026-11-21 对当前锚点表（`analysis/anchors/nid_anchors.jsonl`
> 281 条，nid 2242–788076 / 2006-08-26–2026-11-01）的现算值，仅供参考，随锚点版本变化。
> 不硬编码进代码。Go 与 Python 同表：`app/engine/internal/eras/anchors.go` 由
> `temp/gen_eras_anchors.py` 从该 jsonl 生成，golden test 也由 Python 侧算出——
> **改锚点只改 jsonl + 重跑生成脚本，不要手改 Go**。
>
> 用户提议：小 id 区少放锚点（"空位多、误差本身就大"），高 id 区多放锚点（"让外推更准确"）。
> 结论：**后半句方向对但机制错，前半句因果反了。** 详见 §2。

## 0. 结论速览

1. **"小 id 误差大"是事实，但原因是锚点/数据源少，不是锚点多。** <1 万区只有 9 个锚点，
   LOO p90≈117d（全库 interp 整体 p90=3d）；把 <5 万区锚点删掉一半，整体 p90 仅从 3.0→3.4d，
   但全库最大误差从 428d 暴增到 **3632d**——早期锚点是关键支点，不是可裁剪的冗余。
2. **"高 id 加密让外推更准"机制错。** 外推只发生在 `nid > max(anchors)`（当前 788076）之外；
   区间内全是内插，70 万+ 已有 97 个锚点（全库最密，每锚点仅覆盖 310 本书），
   区间内 p90≈1d，再加密无收益。真正有效的是**持续把最大锚点往前推**，缩短外推距离。
3. **真正的密度洼地是 40–70 万**，每锚点覆盖 2000–2700 本书（vs 高 id 区 310）。
   但该段 LOO p90 仅 0–4d，补锚点边际收益有限——不是优先项。
4. **可操作建议**：把"调整密度"改成"**常态化补最新锚点**"——每有新的 exact `addTime`
   就把 max anchor 往前推一次。这是唯一能实质降低外推误差的手段，且成本极低（一次一条）。
   早期锚点保留，不删。

## 1. 现状：锚点分布与误差结构

### 1.1 按 nid 段的密度（现算）

| nid 段 | 锚点数 | 书数 | 每锚点覆盖书数 | LOO interp p90 |
|---|---:|---:|---:|---:|
| <1 万 | 9 | 2,448 | 272 | **117d** |
| 1–5 万 | 54 | 18,567 | 344 | 5d |
| 5–10 万 | 8 | 13,114 | 1,639 | 7d |
| 10–20 万 | 19 | 25,792 | 1,357 | 1d |
| 20–30 万 | 28 | 25,277 | 903 | 1d |
| 30–40 万 | 20 | 21,222 | 1,061 | 1d |
| 40–50 万 | 12 | 32,528 | **2,711** | 0d |
| 50–60 万 | 15 | 37,553 | **2,504** | 0.6d |
| 60–70 万 | 19 | 39,356 | **2,071** | 4d |
| 70 万+ | 97 | 30,030 | 310 | 1d |

分布是**两头密、中间疏**：<5 万和 70 万+ 锚点密，40–70 万最疏。
这与"高 id 该多放锚点"的直觉相反——高 id 区已经最密了。

### 1.2 误差结构（LOO，留出单元=同一秒整组锚点）

| 模式 | 样本 | 误差中位 | p90 | 最大 | 说明 |
|---|---:|---:|---:|---:|---|
| interp | 278 | 0d | 3d | 218d | 早期少数锚点贡献长尾 |
| extrap_high | 1 | 14d | 14d | 14d | 留出最大锚点 788076 时 |
| extrap_low | 2 | 426d | 428d | 428d | 留出最小锚点时（nid<2242 几乎无书，业务影响可忽略） |

**关键**：`extrap_high` 只有 1 个 LOO 样本是因为只有一个最大锚点；它 14d 的误差
**不代表外推到真实新书也这么准**。工作记忆里"外推误差 131–153d"指的是推到
nid 80 万以上的量级——那是外推距离（ln 距离）决定的，与区间内锚点密度无关。

## 2. 用户假设逐条验证

### 2.1 "小 id 空位多、误差本身就大 → 少放锚点"：因果反了

- **前半句对**：<1 万区 nid 跨度 6,523（2242→8765 前的早期），nid 增长慢，
  同样时间跨的 nid 跨度小；该段锚点稀疏且多为 `manual_early` 人工核定，LOO p90 117d。
- **推论错**：误差大**正是因为锚点少/数据源稀缺**，减少锚点只会让内插区间更宽、误差更大。
- **实测**（删锚点模拟）：

  | 操作 | 锚点数 | interp p90 | 全库最大误差 |
  |---|---:|---:|---:|
  | 不动 | 281 | 3.00d | 428d |
  | 删 <5 万的一半 | 249 | 3.40d | **3632d** |
  | 删 <1 万的前 3 个 | 278 | 2.00d* | （误差被转移，非消除） |

  \* 那个"p90 下降"是**评估口径假象**：删掉 2242/2243/2347 后，这三个早期锚点
  不再进入 LOO 留出集，看起来误差变小；实际上原本落在这几个 nid 的书会改走
  `extrap_low`，误差被藏起来而不是消失。**不能据此删早期锚点。**

### 2.2 "高 id 多放锚点让外推更准确"：机制错

定年模型是 `log(nid) ↔ day` 分段线性（Python `eras._Model` / Go `eras.Estimate`）：

- `nid <= max(anchors)` → **内插**，取两侧锚点线性插值。当前 70 万+ 区间内
  已有 97 个锚点、p90≈1d，**区间内加密没有改善空间**。
- `nid > max(anchors)` → **外推**，斜率由 `_edge_slopes()` 取最后两个不同秒锚点算。
  误差 ≈ 斜率 × `ln(nid) - ln(max_anchor)`，**只与超出距离有关**。

所以在高 id 区间内部增减锚点，**对推到 80 万+ 的新书毫无帮助**；
唯一有效的是**让 max anchor 本身往前移**。举例（现算、随版本变化）：
当前末尾两点 786862(2026-10-17) 与 788076(2026-11-01) 相差 15 天 / 1,214 nid，
按此外推到 nid 800,000 约偏 **147 天**——这个数量级与工作记忆的外推误差一致。
若能把 max anchor 补到 800,000 附近，该误差直接归零。

**另一个约束**：今天（2026-11-21）距最新锚点（2026-11-01）已 20 天，
期间新书都在外推段。外推误差随时间线性累积——这是当前最大的时效短板，
与"区间内密度"无关。

## 3. 修正后的策略

按优先级：

**P0 — 常态化补最新锚点（唯一能实质降低外推误差）**
- 每拿到一条新的 exact `addTime`（App API 秒级字段，或用户 App 观测），
  若其 nid > 当前 max，就追加到 `nid_anchors.jsonl`。
- 目标：max anchor 与当前最新 nid 的距离 ≤ 几天，而不是让它落后几周。
- 成本：一次一条，无需批量爬虫。追加后跑生成脚本同步 Go 与 golden test。

**P1 — 早期锚点全部保留**
- 不为"简化"删早期锚点；它们是低 nid 内插的关键支点，删除会把误差转移到外推段。

**P2 — 中段 40–70 万按需补（低优先）**
- 这是密度洼地，但 LOO p90 已经 0–4d，补锚点边际收益很小。
- 若要做，目标设为"每锚点覆盖 ≤1,000 本书"，即每段补到 30–40 个锚点；
  仅在有现成 exact 数据时顺手补，不为它专门爬。

**P3 — 外推斜率的稳健性（可选，需改算法）**
- 当前 `_edge_slopes()` 只用最后两个不同秒锚点；若这两点恰好受审核积压/批量导入影响，
  斜率会失真。可考虑用尾部 N 个锚点做稳健回归，但必须保留"跳过同秒点"的逻辑。
- 这属于算法改动，**不在本轮范围**（app/ 冻结）。

## 4. 采样方法：如果要补，采哪些 nid

1. **新增 max anchor**：取当前能拿到的最大 nid 且带 exact `addTime` 的书（App API 详情页）。
2. **中段补点**：从 universe 按 nid 排序，**每隔约 1,000 本取一本**，
   且必须有 exact `addTime`；优先已有 API 快照里的记录，不新爬。
3. **早期**：不删不加（除非用户 App 观测到新的早期书 exact 时间）。
4. **禁止**：把 `20XX萌神` 年份、featured 封面时间戳、征文页起止时间当锚点
   （见工作记忆硬约束）。

生成链路（改 jsonl 后）：
```
cd analysis && uv run python ../temp/gen_eras_anchors.py
# 产出 app/engine/internal/eras/{anchors.go, eras_golden_test.go}
```
注意 `temp/gen_eras_anchors.py` 是一次性脚本目录里的文件，若已清理需先恢复；
Go 端测试 `go test ./internal/eras` 必须过（golden 用例覆盖锚点/内插/两端外推）。

## 5. 边界与风险

- **本文数字均为现算快照**：锚点每追加一条，分布与 LOO 都会变；不要把这些数硬编码。
- **LOO 的 extrap 样本极少**（高 1、低 2），不能用来估计真实外推误差；
  真实误差看 §2.2 的 ln 距离推算。
- **nid 不一定是严格均匀增长的**：审核积压、批量导入会让相邻锚点的 nid/时间比失真，
  所以"按每 N 本书采一个"只是初始网格，实际仍以 exact 数据可用性为准。
- **app/ 当前冻结**：本轮只出策略文档；追加锚点 jsonl 与重跑生成脚本需待放行。
