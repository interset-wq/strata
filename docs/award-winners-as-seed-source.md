## 0. 结论

1. **数据通路成立，且比预想的好**：获奖名单不在 API，而是**写死在活动页 JS 里的静态 JSON**
   （webpack 模块 `JSON.parse('[{"novelId","novelName"}]')`）。一次 GET 拿一份 JS 即得全量名单，
   无分页、无鉴权、无速率压力。字段只有 `novelId` + `novelName`，**成绩字段要去 dataset/app 另取**。
2. **"获奖=优质"被数据强力证实**：真正的获奖子集（终审金银铜模块）收藏中位 **1112–8372**，
   是全站中位（8）的 140–1000 倍；在其定年世代的收藏分位中位 **0.96–0.97**，
   **62–64% 落在同代 p90 以上**。这比"favs 高"更可信——它是评审+读者双重背书。
3. **能补种的量（复核后修正）**：早期工作抓到 1,411 本去重（含各阶段），其中 412 本不在 universe；
   但复核发现**台账混入了入围书**——按获奖模块 nid 精确过滤后，十二征获奖仅 **363 本**（非 503）、
   十三征 **446 本**（非 669），两模块是**子集关系**（140⊂363、223⊂445），不可相加。
   全库净获奖 **911 本**（11 届）、其中 **140 本库外**是真·欠采。详见 §3/§8。
4. **关键陷阱**：活动页 JS 里**不是每组数组都是获奖**。初审/复审模块（favs 中位 4–16）
   和获奖模块混在一起，整包抓会把大量入围书当获奖，稀释优质池、破坏"获奖"语义。
   **本轮复核确认污染实际发生**：原台账 1,480 行里 602 本是入围（favs 多为 <100），已剔除。

### 1.1 来源不是 API，是静态 JSON

- 抓 `https://pages.sfacg.com/h5/act/zw20240504/js/index.820980da.js`（十二征，242 KB）
  与 `.../zw20250504/js/index.d34358c7.js`（十三征，202 KB）。

### 1.3 每份 JS 的时效

活动页是**赛事期快照**：终审结果公布后写进 JS，之后随活动页长期留存。获奖名单是最终态、不会变，
**比参赛清单更适合做种子**——清单是赛期快照可能缺早期投稿，获奖是定稿。

## 3. 入种前的必做筛选（否则污染）

1. **只取获奖模块**：按 §1.2 判定，弃掉初审/复审/入围模块。宁可少收，不可把 4–16 favs 的入围书标成获奖。
2. **奖项分级要留字段**：金银铜/优秀奖是不同强度的信号，种子需新增 `award` 列（见 §4），
   不要压成一个布尔 `is_winner`——铜奖和特等奖的价值不同。
3. **去重与归属**：同一本可能多模块出现（实测十二征「140 条集」⊂「363 条集」、十三征 223⊂445，
   是子集而非并列），按 nid 去重、保留最高奖项；跨届重名按 nid 区分。
4. **成绩字段另取**：JS 只有 nid/书名，favs/words/收藏等要去 `dataset/out/books.csv`
   （历史快照 999/1411 本在，字段完整度：作者/字数/状态/点赞 100%，封面 90.2%；净获奖口径见 §8）或 App 详情抓取。
5. **第二/三类僵尸要排除**：获奖书也可能 later 变僵尸（正文替换），沿用 `form_user_verified.jsonl`
   裁定表过滤，不因获奖就豁免。

## 4. 种子表设计（建议，待裁定）

现有 `seed.db` schema v4 有 5 张表（books / book_tags / deep_ranks / calendar_universe / seed_meta）。
获奖是**作品级属性 + 可分级 + 多届累积**，建议**新增一张独立表**，不塞进 books 列：

```sql
CREATE TABLE contest_awards(
  nid        INTEGER NOT NULL,
  edition    TEXT    NOT NULL,   -- '十二征'/'十三征'/... 或 year
  award      TEXT    NOT NULL,   -- '金奖'/'银奖'/'铜奖'/'优秀奖'
  category   TEXT,              -- 长篇/中篇/短篇/对话（若能从页面判定）
  source_nid TEXT    NOT NULL,   -- 来源活动页标识 zw20240504
  PRIMARY KEY(nid, edition)
);
```

理由：
- **不与 books 的 form/分位耦合**：获奖是外加标签，不是形态，也不是排序池分母（呼应 E.23 形态禁传播）。
- **可多届**：一书可多届获奖（虽然罕见），独立表天然支持。
- **可增量**：新一届公布后只追加这张表 + 补 books，不动既有列、不动索引、不动报告口径。
- **App 专页**：书籍详情读这张表显示"本书获第 X 届征文金奖"，专页按 `edition/award/category` 聚合。

## 5. 专门页面的数据来源（与现有设计衔接）

`contest-display-in-app.md` 的三层数据可加第四层：

| 层 | 来源 | 用途 |
|---|---|---|
| 本地种子 contest 字段 | 书页标签 | 参赛标注（已有） |
| 征文清单 API | 参赛清单浏览页 | 补全种子外参赛书（已有） |
| 赛事元数据 | contest-editions.md 静态表 | 档案页骨架（已有） |
| **获奖表 contest_awards（新增）** | **活动页 JS 静态 JSON** | **获奖专页 + 书页获奖徽标** |

专页排序仍用现有信号（`fav_pctl` 同代分位），**不造新指标**；获奖本身作为筛选条件，不作为打分项——
避免"获奖"和"高收藏"双重计权。
