# 征文信息在 App 内的展示：赛事档案页 + 参赛清单浏览页（设计定案）

> **用户设想（2026-11-20）**：基于已验证的征文清单 API，在我们的 app 里「以我们的形式」展示征文信息。
> 用户选定两种形态：**赛事档案页**（赛事元数据 + 参赛作品聚合）与**参赛清单浏览页**（按赛事 → 赛道分页浏览）。
> 本轮**只写设计文档，不碰 `app/` 代码**；app 实现由开发 agent 负责，本文不规定其代码结构。
>
> **口径置顶**：文中所有计数、比例、日期均为某次快照的现算值或档案实测值，**仅供参考**，随数据版本变化；
> 禁止硬编码进代码、禁止每次重算精确数字。语义拿不准的直接问维护者，不要翻 API 硬查。
>
> **权威来源**：端点事实 `docs/contest-roster-harvest.md` 与 `docs/sfacg-endpoints.md` §7.4；
> 赛事日期/届次 `analysis/references/contest-editions.md`；假短/中篇治理 `docs/fake-complete-short-medium.md`；
> form 定义 `docs/form-definitions.md`；双模式 `app/docs/12-dual-mode.md`；详情抓取写回 `app/docs/05-detail-fetch.md`。

## 0. 结论先行

1. **三源分工，别混**：① 本地种子 `contest` 字段（零请求，赛事档案页骨架 + form/信号徽标）；
   ② 征文清单 API（按需请求，补全种子外的参赛作品）；③ 赛事元数据——日期/奖项内置配置（**无清单端点**），
   获奖名单另有**活动页 JS 静态 JSON**（不在清单接口里，每届模块需现场判定，见 `award-winners-as-seed-source.md`）。
2. **能零请求先做的是「赛事档案页的本地视图」**：只用 `seed.books.contest` 聚合即得赛事列表、参赛书、
   form 分布、头部作品——完全符合「用我们已有数据长出视图」的既有路线（cf. `app/docs/14-discovery-views.md`）。
3. **参赛清单浏览页的最大约束是 tagId 地图**，不是接口本身：地图不完整（春/秋征未摸到、早期静态页无 API、
   sandbox/生产不同号），且赛事结束后活动页可能改版/下线。这决定了「历史赛事拿不到完整清单」是常态，需降级。
4. **「以我们的形式」= 用已有信号筛选排序，不造新指标**：form 六值（剔 invalid / 第二类僵尸 / 长篇征文假短中篇）、
   `fav_pctl` 同代分位、已有 `lqs`（归档未落地，不接入）。app 主线是 novly/classic，**不引入征文专项指标**，
   这是展示层新视图，**不进推荐打分**。
5. **赛事元数据（尤其获奖名单）是硬缺口**：清单 API 只返回作品，不返回赛事名/日期/奖项/获奖。
   不要为它爬活动页——日期表在 `analysis/references/contest-editions.md` 已有用户逐届核实版；
   获奖名单**有来源**：活动页 JS 静态 JSON（`/js/index.<hash>.js` 里的 webpack 模块，见 `award-winners-as-seed-source.md`），
   不是清单接口、也不是私有 API（§8.4 已修正旧误读）；但每届获奖模块需现场判定，仍待裁定（§6）。
6. **接入征文是「低成本、高杠杆」的覆盖更新手段，但只直接解决「书目层」的新鲜度**（§0.1）：
   新世代征文占比极高，接入清单能持续拿到新书书目；但清单**不含成绩字段**，也不覆盖非征文与未参赛短篇，
   不能替代详情抓取与种子发版。定位为**书目发现 / 覆盖补强**，不是成绩刷新、不是全量覆盖。

### 0.1 战略价值：为什么接入征文能缓解「数据落后」（用户论点，已用现成报告数据核验）

> 用户判断（2026-11-20）：「接入征文赛事后，我的 app 就不必太担心数据落后，因为新世代参加征文的书在所有书中比例非常高。」
> 结论：**方向成立，但「数据落后」有三层，征文只直接解决其中一层**。下表的数字来自既有报告、
> 均为快照/报告现算值，**仅供参考、随版本变化**，不硬编码进代码、不为本文重算。

**支持该判断的证据**（口径已标注，勿混用）

| 证据 | 数值（仅供参考） | 来源与口径 |
| --- | --- | --- |
| 库内带 `contest` 标注的书占比 | 2016 约 20.0% → 2024 约 59.7% | 报告 15 §1，**按创建年、库内**口径 |
| 月票榜上榜书里征文占比 | 2016 13.5% → 2024 约 97.8% | 报告 15 §1，**头部榜单**口径（非全部新书，勿外推） |
| 十三征单届主体簇占当年新增 | 约 14.7%（全序列最高） | 报告 06 §2 |
| 征文日历 | 秋征 → 冬征 → 春征 → X 征首尾相接，间隔 0–1 天；每届启动后 1–3 周进入投稿主体期 | 报告 06 §1 / `contest-editions.md` |

即新世代「书从哪来」越来越以征文为主，且全年无断档；征文清单 API 正是这条供给泵的目录——
每届启动后按需拉一次，即可在种子发版之外持续获得新书书目。这是用户判断成立的部分。

**必须精确化的三层「数据落后」**

| 层 | 征文能否解决 | 说明 |
| --- | --- | --- |
| **书目层**（有哪些新书 / 发现入口） | **基本能，且是最大价值** | 清单给 nid/标题/作者/封面/赛道，正是新书发现所需；高占比意味着覆盖大部分新世代 |
| **成绩层**（收藏/点击/状态等数值新鲜度） | **不能** | 清单不含任何成绩字段、也不含定年；刷新仍靠详情页抓取写回（05 §3）与用户观测，或种子发版 |
| **覆盖层**（是否覆盖全部新书） | **只覆盖一部分** | 2024 库内仍有约 40% 非征文；一次性完本、未参赛的短篇（已知欠采最严重的一批）**不在征文里，清单抓不到** |

时效约束另有两点：① 征文清单依赖 tagId 地图，而**春/秋征恰是未摸到的缺口**（`contest-roster-harvest.md` §5），
新世代覆盖反而不全；② 活动页随赛事改版/下线，清单是「赛事期间的快照」，历史届次可能失效（§3.2）。

**定位**：征文接入 = **书目发现 / 覆盖补强**通路（对样本池与发现流价值最大），与详情页抓取（成绩刷新）、
种子发版（全量基线）互补。它让「有哪些新书」不再主要依赖种子发版，但不构成「成绩实时」或「全量覆盖」的替代。

### 0.2 「四季征文 API → 少请求覆盖热门书」论点核验（用户追问 2026-11-21）

> 用户判断：「春夏秋冬这 4 个固定征文的 API 我们知道多少？如果有这些 API，就几乎能覆盖某时代的大部分热门书——
> 时代越新，进官方榜单的参赛书越多，而且需要的请求次数少。」

**结论：论点的两个前提各有对错，需拆开看——「榜单被征文主导」成立，「请求少」成立，但「知道 4 个 API 就够」不成立。**

| 前提 | 核验 | 来源 / 口径 |
| --- | --- | --- |
| 时代越新，参赛书越主导榜单 | **成立**（头部榜单口径）：月票榜上榜书征文占比 2016 13.5%→2024 **97.8%**，2022 后稳定 85–95%；95.5% 征文书在创建当年上榜 | 报告 15 §1/§6，**月票榜 top20 右截断**，非全部热门书 |
| 请求次数少 | **成立**：新接口 `size=500`，一届 3 赛道各 1–几页；四季全年约十几个 tag、几十次请求即可拿到当年参赛书目全集 | `contest-roster-harvest.md` §3/§6 |
| 我们知道这 4 个 API | **不成立**：四季是 4 条持续系列、每届新增 tagId，无「固定 4 个端点」；初查只掌握 X 征 + 冬征，**经试号+页面实证已补回 2024 春征(699，日期式 SPA)、2024 秋征(725，UUID 页)、九征冬征(774，UUID 页)、点鸭秋色回忆(724，试号)**；春/秋征 2023 及更早仍空白 | `contest-roster-harvest.md` §2.1/§2.2 |

**所以用户的战略意图对——缺口在「我们还没拿到新时代的四季 API」，不在「这条路走不通」。**
具体说，2024–2026 的新赛事里，X 征十一/十二/十三征本就有清单 API；
2024 春征已日期式 SPA 实证(699)、2024/2025 秋征已页面实证(725/772)、春征 2025/2026(746/789)已 UUID 页实证、冬征六/七/八/九届(485/692/726/774)已全部页面实证，
而这批恰是榜单征文占比最高的年代（报告 15）。落地前**先补剩余缺口**，再谈「四季全覆盖」。
补全有两条路（详见 `contest-roster-harvest.md` §2.2 实证）：① 用户 App DevTools 现场取（`contest-roster-fields.md` §7.3）；
② **试号探活**——tagId 全局连续分配、年间隔约 47（655→702→752），可用 `size=1` 扫空档几十次请求找 active tag，
再按定年聚集筛候选、用户观测确认。② 成本极低但**不能只靠推算**：空档里混着题材/活动标签，categoryID 也无法区分。

**两个不能省的边界**（否则「覆盖热门书」会被误读）：
1. **清单给的是「参赛书全集」，不是「热门子集」**：95,433 本征文书只有 335 本上过月票榜（0.35%，报告 15 §2）。
   清单无成绩字段，无法从中识别哪本是热门——发现书目可以，判断热度仍需榜单/详情成绩。
2. **上榜 ≠ 参赛带来的因果效应**：控制 VIP 后征文上榜率反低于非征文（0.67×），同作者内对照仅 1.18×（报告 15 §3）。
   征文筛的是作者、不是比赛；「覆盖参赛书」不等于「覆盖有能力上榜的人」之外的额外红利。

## 1. 三层数据从哪来

| 数据项 | 来源 | 请求 | 稳定性 / 缺口 |
| --- | --- | --- | --- |
| 赛事名 / 届次 | 本地种子 `contest` 字段 | 零 | 单值、99 种取值、约 38.8% 有值；字符串里带「长篇/中篇/短篇/对话」赛道字样 |
| 参赛作品（库内） | 本地种子 `books` | 零 | 只含被扫描抓到的书；短篇欠采已知（`docs/fake-complete-short-medium.md` §2） |
| 作品 form / favs / fav_pctl | 本地种子 + 用户观测覆盖层 | 零 | 覆盖层优先、种子兜底（05 §3）；库外书没有这些 |
| 参赛作品（库外） | 征文清单 API | 按需 | 清单里约 29% 的 nid 不在 db，是补全短/中篇的关键 |
| 起止时间 / 赛程节点 | 内置静态配置（从 `contest-editions.md` 导出） | 零 | 官方无端点；配置会过期，随发版更新；早期届次无精确日 |
| 奖项 / 获奖名单 | **活动页 JS 静态 JSON**（`/js/index.<hash>.js` 内 webpack 模块，仅 novelId+novelName）；每届获奖模块需现场判定 | `award-winners-as-seed-source.md`；`contest-roster-fields.md` §8.4 |

### 1.1 本地种子层（零请求，先做）

`contest` 是**单值 TEXT**，取值形如「七征长篇」「五征短篇」「2025春季征文」「五征对话小说」——**赛道信息编码在字符串里**。
因此本地即可按赛事名聚合、并按「长篇/中篇/短篇/对话」字样粗分赛道，**不需要 tagId**。

- 可得到：赛事枚举、每赛事的库内参赛书、这些书的 form / favs / 封面 / 作者 / 定年。
- 得不到：**完整参赛清单**（欠采书不在）、精确赛道 tagId、赛事日期、获奖信息。
- 约束：`contest` 是作品级标签，旧书参赛是长尾（`contest-editions.md` §届次表），
  **不能用参赛书的 nid 下界推赛事启动日**（cohort bulk 下界定年一致晚于启动 9–20 天）。

### 1.2 征文清单 API 层（按需请求，补库外）

两套端点按活动页年代分（完整档案见 `docs/contest-roster-harvest.md`）：

| | 旧 H5 页（2018–2022） | 新 SPA 页（2023 起） |
| --- | --- | --- |
| 地址 | `GET pages.sfacg.com/ajax/ashx/Common.ashx?op=getNovelsByTag` | `GET pages.sfacg.com/api/essay/getNovels` |
| 参数 | `op=getNovelsByTag&tagId={t}&ps=200&pi={0起}` | `tagIds={t}&page={1起}&size={500}` |
| 条目 | `NovelID/NovelName/AuthorName/Intro/Cover/CategoryID` | `novelID/novelName/authorName/intro/cover/categoryID` |

**四条必须遵守的解析规则**（踩过的坑）：

1. **字段名大小写两套**，解析器要同时兼容 `NovelID` 与 `novelID`。
2. **tagId 是「赛事 × 赛道」编号，不能猜**：长/中/短各有独立 id；同一赛事 sandbox 与生产号不同
   （十二征短篇 `533` vs `704`）；必须从活动页 JS 按 `location.host` 前缀选生产环境再取。已实测的 tag 表在专题文档。
3. **`categoryID` 不能当 form 真值**：与 `forms` 的 categoryId 判据同源，但 E.28 只正向用 `1/4`（对话），
   `0/3` 不判形态；清单里的值只可用于「赛道提示」，不可直接写 form。
4. 清单的 `intro` 是**作品简介**，不是作者 intro（作者资料走 `docs/author-profile-on-demand.md`）。

### 1.3 赛事元数据层（官方无端点）

清单 API 只返回作品，**不返回赛事名/届次/日期/奖项/获奖**。可得来源：

- **届次 + 起止时间/赛程节点**：`analysis/references/contest-editions.md` 已有用户逐届 App 核实 + 官方页面版
  （X 征 4–13 届、冬征 1–9 届、2024 秋征起的春/秋/主题征）。**这是分析档案，不是 app 数据**；
  若要做赛事档案页，从该文件**导出一份内置静态表**，**不要在本文或 app 里另维护副本**（单一真源）。
- **早期精确日稀缺**：四征有官方精确窗口（2016-07-08→10-06），多数届次只有 URL 年份或 App 核实的起止区间。
- **获奖名单**：**有来源，且不是 API**——是活动页 JS 里的**静态 JSON 模块**
  （`JSON.parse('[{"novelId","novelName"}]')`，一次 GET 拿全、无分页无鉴权）。
  实证与"获奖≠全部静态数组"的筛选陷阱见 `award-winners-as-seed-source.md` 与 `contest-roster-fields.md` §8.4。
  获奖页 URL 末尾那串随机路径是 JS 里写死的路由（**每届漂移、语义会变**，见 §8.3），无法从届次推导。
  每届哪几个模块是获奖需现场判定（奖项图标邻域 + favs 跃升），不要硬编码 module id。
  不要假设「清单里的头部就是获奖作品」——两者无对应关系。

> 静态表与作者 intro 同属**快照型配置**：会过期、随种子发版更新。不要为了「实时」去爬活动页——活动页会改版/下线，
> 且 tagId 就是从它的 JS 里取的，稳定性差。

## 2. 形态一：赛事档案页（Contest Archive）

### 2.1 内容

一届赛事一页，展示：赛事名/届次、起止时间（有则显示，无则标「仅年份」）、赛道列表、参赛规模、
**按我们信号排序的代表作品**（每个 form 一组），以及获奖信息（若裁定做）。

### 2.2 数据源与请求

- **赛事列表**：从种子 `contest` 枚举（零请求）。这样新赛事只要进了种子就自动出现，无需维护赛事清单。
- **日期/赛程**：读内置静态表（§1.3）；表中没有就只显示从 `contest` 解析出的届次/年份，**不编造日期**。
- **参赛作品**：优先读本地聚合；要「完整清单」才按需调 API（§3 的清单能力复用）。
- **获奖**：若裁定做，读种子新增的 `contest_awards` 表（来源为活动页 JS 静态 JSON，见 `award-winners-as-seed-source.md`），
  按下述方式显示；否则整块隐藏，不做占位。

### 2.3「我们的形式」怎么体现

这是本页区别于官方活动页的核心，必须用上已有信号而非罗列：

- **先剔污染**：短/中篇组套用「征文名含『长篇』即假完结」裁定与 `form_user_verified.jsonl` 用户裁定
  （`docs/fake-complete-short-medium.md` §2.2/§2.3）。**否则档案页会把霸榜的假短/中篇当代表作展示**，
  与治理方向冲突。注意该裁定只作用 short/medium，不动 long/dialogue。
- **排序用同代分位**：累计 favs 混书龄/曝光分母，跨届横比会系统性偏向老赛事（报告 02/08）。
  按 `fav_pctl`（世代内分位）排代表作；跨届比较只比「各自在同代的水平」，不比累计绝对值。
- **form 分组**：按 `long/medium/short/dialogue` 分组展示，各组独立排序——长篇赛道流量本就是中短篇上百上千倍，
  混排会把后两者淹没。
- **双模式**：novly 模式只浏览/收藏入 watchlist；不做「征文推荐分」，不进 12 定义的推荐打分白名单。

## 3. 形态二：参赛清单浏览页（Contest Roster Browser）

### 3.1 内容

赛事 → 赛道 → 作品列表，分页浏览。列表项显示清单自带的标题/作者/简介/封面/赛道；
库内书额外叠加我们的 form 与信号徽标。

### 3.2 分页与 tagId

- 每个「赛事 × 赛道」对应一个 tagId，走对应年代的接口分页（旧 0 起 `pi`、新 1 起 `page`）。
- **赛事年代决定能否拿全清单**（降级依据）：

| 年代 | URL 形态 | 清单 API | 浏览页能力 |
| --- | --- | --- | --- |
| 早期（四征/五征，2016–17） | 静态页 | **无** | 只能用本地种子按 `contest` 聚合，标「不完整清单」 |
| H5（2018–22） | `pages.sfacg.com/{h5,pc}/act/...` | 旧接口，tag 表部分有 | 有 tagId 的赛道可调，其余降级本地 |
| SPA（2023 起） | `pages.sfacg.com/h5/act/zwYYYYMMDD/pc` | 新接口，十一/十二/十三征较全 | 完整清单可用 |

- tagId 地图不补全之前，浏览页对**未收录赛道**只能显示本地子集，并明示「仅显示库内作品」。

### 3.3 join 本地：库内 vs 库外

清单返回的 nid 与本地种子/用户库比对（`in_db` 语义见专题文档 §4）：

| 情况 | 显示 | 交互 |
| --- | --- | --- |
| **库内** | 清单字段 + 我们的 form / fav_pctl 徽标（覆盖层优先、种子兜底） | 走既有详情页 |
| **库外** | 只显示清单自带字段（标题/作者/简介/封面/赛道） | **无 form / fav_pctl 徽标**——这些是种子侧算的，库外书没有；点击是否触发 05 的详情抓取见 §6 待裁定 |

> 库外书不可能有我们的 form 判定与 universe 分位，不要伪造徽标或拿清单 `categoryID` 顶替 form（§1.2 规则 3）。

### 3.4 筛选排序（「我们的形式」）

- 可用筛选项**仅限已有维度**：form、赛道、世代/年份（来自定年）、库内/库外；不造「征文热度分」。
- 库内书可按 `fav_pctl` / favs 排序；**库外书无我们的成绩数据**，只能按清单返回顺序（官方排序）显示，并标注来源。
- 两套来源混排时必须标清「我们的排序」与「官方顺序」，避免读者误以为是同一口径。

## 4. 请求与限速契约

- **只取清单元数据**（nid/标题/作者/简介/封面/categoryID），**不取正文、不登录、不带用户 cookie**。
- **沿用引擎既有全局限速**（`app/docs/05-detail-fetch.md` §4：端点间隔 ≥1s、全局共享、队列硬上限），
  **不另起一套无节流的请求**；清单翻页按页串行，失败即跳过该页。
- 清单接口无契约、赛事结束可能改版/下线；**按页缓存 + 失败降级到本地子集**，不因清单不可用而阻塞页面。
- 状态：`status.errorCode`（新）/ `status`（旧）非 200 或结构缺失 → 视为接口失效，回落本地，不重试风暴。

## 5. 失败降级与边界

| 情形 | 处理 |
| --- | --- |
| 赛事无 tagId（早期/未摸到） | 只显示本地种子聚合，标「仅库内作品，清单不完整」 |
| 活动页改版 / 接口下线 | 清单不可用 → 回落本地子集；不显示空白、不清空已显示值 |
| 清单字段大小写变化 | 双格式解析；两者皆无 → 该条跳过，不猜字段 |
| 库外书无 form/分位 | 不显示徽标、不伪造；只显示清单自带字段 |
| 短/中篇头部含假完结 | 套用 §2.3 裁定剔除或标注；这是展示层必须守住的口径 |
| 赛事日期缺失 | 只显示届次/年份，不编造 |

**不做**：爬活动页取赛事元数据；用清单 `categoryID` 判 form；跨届横比累计 favs；
为征文造新指标或推荐分；把库外书写成种子；取正文/登录/带用户态；全库后台批量抓清单。
