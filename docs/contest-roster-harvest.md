# 征文页参赛清单：短/中篇补采通路（研究记录 2026-11-20）

> 用户判断：短/中篇在 db 里欠采（一次性完本、未上列表页的短篇可能根本没被单向游标扫描抓到），
> 而**征文页有参赛选手清单**，可用来补采。本记录验证该通路是否成立、怎么翻页、覆盖多大。
> 本轮只做研究与文档，**未改 `app/` 代码，未改数据集/种子**。
> 文中所有数字为快照现算值、仅供参考。

## 0. 结论先行

1. **通路成立**：征文页参赛清单由 REST 接口分页返回，含 `nid/标题/作者/intro/封面/categoryID`，
   可直接批量取，不需要逐本抓详情页。用户"rest api 支持翻页"的猜测**正确**。
2. **两套接口并存**（按征文页年代分）：
   - 旧 H5 页：`GET /ajax/ashx/Common.ashx?op=getNovelsByTag&tagId={t}&ps=200&pi={0-based}` → `{status,novels,totalPage}`
   - 新 SPA 页：`GET /api/essay/getNovels?tagIds={t}&page={1-based}&size={n}` → `{status,data:{totalPage,novels}}`
   - 两次翻页字段大小写不同（`NovelID` vs `novelID`），解析要兼容。
3. **tagId 是「某届比赛的某个赛项」的编号，每次新增、跨届不复用**（用户裁定 2026-11-21）：
   同一赛事的长/中/短各有独立 tagId，且**每办一届就新分配一批**——十三征 3 个赛项 = 3 个全新号
   （752/753/754），与十二征的 702/703/704 无复用关系；且 sandbox/test/pages 三套环境 tagId 还不同
   （如十二征短篇 535 vs 704）。**必须从每届页面 JS 里取，不能从届次/赛项名推导、不能猜**。
   这也是 tagId 地图永远追不齐的根因：它本就是一次性编号，不是稳定维度。
4. **补采价值**：本轮探到的 14 个 tag 合计 **31,092 本去重作品**，其中 **9,012 本（29%）不在 db**；
   短/中篇赛道漏采率最高（七征中篇 481/1359=35%、十二征短篇 171/321=53%）。
   用户举的 5 本"查不到的精确短篇"中，`血与梦`（709232）已在十二征短篇赛道清单内命中——**路径实证有效**。

### 2.2 「tagId 是否连续、能否试号补齐」实证（用户假设 2026-11-21，部分成立）

用户假设：「tagId 应该是连续的，每个比赛新增几个，不区分到底是什么比赛；数据可以靠用户观测补齐。」
**已按授权试号验证（一次性探针、size≤3 探活、串行限速、不落库、不取正文）。结论：方向对，但不能直接推算。**

**支持「连续分配」的数值规律**（§2 已知 tag 按值排序）：
- **同届赛项连号**：十一征 653/654/655、十二征 702/703/704、十三征 752/753/754，均严格连续。
- **年度间隔稳定**：655→702 = **+47**、702→752 = **+48**——每年大约新增 47–48 个 tag 号，
  其中仅 3 个是 X 征赛项，其余分配给同年其它征文/活动。早期间隔不均（418→454 +36、466→653 +187），年代久远/口径变化。
- **跨系列相邻号印证「全年首尾相接」**：2024 秋征 725 与八征冬征 726 **紧邻**（+1），
  对应秋征 9-30 截止与冬征 12-06 启动几乎无缝；说明同期的不同系列 tag 也会连号分配，
  「年度间隔 ~47」只是 X 征同系列的间距，不能拿来推其它系列。
- 即 tagId 确实是**全局递增分配的编号池**，每个赛事批几条——用户「连续、每比赛新增几个」的直觉**成立**。

**但「不区分什么比赛」不成立——空档里混着非征文 tag，试号必须逐个鉴别：**
- 探活结果：空档 704→752 内 **706–729 几乎连续全有数据**（totalPage 从 2 到 4000+ 不等），
  但抽查这些 tag 的书目，**categoryID 混杂（0/1/3/4）、书名题材各异、定年跨 2024–2026**——
  说明号池里同时存在**题材/活动标签页**，不是只有征文赛项。已知征文 tag 里 cat 也不统一（704=3、752=0），
  **靠 categoryID 无法区分**。
- **鉴别靠定年聚集度**：征文赛项的书创建时间集中在该届窗口（启动后 1–3 周，报告 06）。
  对 6 个候选 tag 拉全量清单（合计 **5,180 本**，导出 `analysis/out/contest_candidate_tags.csv`，不入库）
  后定年高度聚集，比 size=40 抽样证据强得多。**用户 2026-11-21 在 App 里按精确书名核对后，3 个 tag 已转正确认**（下表 ✓）：

  其中 725/774 后续又由用户给出的 UUID 活动页 `data-tagid` **二次实证转正**（724 对话线仍无活动页 URL）。

- **接口陷阱（本轮踩到，已验证）**：`getNovels` 的 `size` 对部分 tag 有边界——tag 724 用 `size=1/3/8` 正常返回，
  用 `size=500` 却返回空（`totalPage=1`）。**探活/导出不能只用大 size 判空**，遇疑似空 tag 降 size 重试；
  这也意味着 §2.2 早先「706–729 全 active」的探活结论只说明小 size 下有数据，个别 tag 可能是分页边界假象。

**所以补齐路径 = 「试号探活 → 定年聚集筛候选 → 用户观测确认」，而非「按间隔推算即得分」——本轮已完整跑通一遍：**
1. **探活**：新接口 `getNovels?tagIds=X&page=1&size=1`，看 `data.novels` 是否非空；空档 47 个号全探也就几十次请求，成本极低。
2. **筛候选**：对有数据的 tag 取 `size=40` 样本走 `eras.estimate`，定年月聚集在赛事窗口的才是征文赛项；题材标签跨年分散。
3. **用户确认**：候选 tag 的书目给用户看，确认是哪届哪条线——这是「用户观测补齐」的落点。

**边界**：tag 号池是站点全局的，**征文只是其中一类**，试号会捞到大量非征文标签；
定年窗口只能缩小范围、不能唯一定位（同届多个赛项 + 同期多赛事并行）；已探 active tag 的具体赛事归属**一律待用户裁定**，不写入正式 tag 台账。

## 3. 接口调用样例

```python
# 新 SPA（推荐，size 大、一页拿全）
GET https://pages.sfacg.com/api/essay/getNovels?tagIds=704&page=1&size=500
# → {"status":{"errorCode":200},"data":{"totalPage":2,"novels":[
#     {"novelID":713638,"categoryID":3,"novelName":"Re：如果成为神明",
#      "authorName":"某NoName","intro":"...","cover":"https://rs.sfacg.com/..."}]}}

# 旧 H5（pi 从 0 起；ps 可 200）
GET https://pages.sfacg.com/ajax/ashx/Common.ashx?op=getNovelsByTag&tagId=415&ps=200&pi=0
# → {"status":200,"novels":[{"NovelID":277050,"NovelName":"...","AuthorName":"...","Intro":"...","Cover":"..."}],"totalPage":...}
```

**限速**：沿用引擎既有抓取限速（分析侧现用 0.25–0.6s 串行 / 4 并发，无风控迹象）；
只取清单元数据，不取正文、不登录。清单里的 `intro` 是**作品简介**，不是作者 intro（§作者资料另行）。

## 7. 边界

- 清单只覆盖**参加征文**的书；未参赛的一次性完本短篇（如用户举例里部分）仍会漏——这条路不是全集。
- `categoryID` 在旧接口是 `0/1`，新接口是 `0/1/3`，与 `forms` 的 categoryId 判据同源但**不能当 form 真值**（E.28 只正向用 1/4）。
- 早期静态征文页（四征/五征）没有清单 API，需另寻来源（可能用户 App 可见）。
- 所有 tagId/页数是某一时刻快照，赛事结束后页面可能改版或下线；采集器需支持断点续跑与失效降级。
