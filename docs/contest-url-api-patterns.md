# 比赛 URL 与 API 规律研究：高质量书籍的高效入口

> **定位**：本文是征文/比赛数据通路的**统领研究文档**——把散落在端点档案、字段清单、补采记录、
> 获奖定案里的规律抽象成一套体系，并明确它们如何服务于「快速获取高质量书籍 → 提高种子质量」。
> 具体参数、字段、逐届对照**不在这里重复**，正文用路径指针指向权威文档。
>
> **口径**：文中计数/比例/误差均为快照现算值、仅供参考，随数据版本变化；禁止硬编码进代码。
> 本轮只写研究文档，**未改 `app/`、未改数据集/种子**。
>
> **用户洞察（立论根基）**：① 时代越新，进入官方榜单的参赛书比例越高（报告 15：库内征文占比
> 2016 约 20% → 2024 约 59.7%；月票榜上榜书 2024 达 97.8%，**头部口径，不可外推成"所有新书"**），
> 故「抓住比赛 ≈ 抓住新时代大部分热门书」；② 获奖 = 平台 + 读者双重认可，比单看收藏更干净的优质信号。
> 两者合起来：**比赛是种子质量的高效入口**——用远少于全库扫描的请求，换高密度的高质量书目。

## 0. 为什么研究「规律」而不只是「端点」

端点是点，规律是线。逐届爬端点永远追不齐（新赛事不断办、tagId 每届新增），
但**url 形态、tagId 分配、数据存放方式**这三类规律一旦摸清，就能把「逐本抓、逐届猜」
变成「按模式定位、批量取、自动鉴别」。研究目标有三条，按对种子质量的贡献排序：

| 目标 | 规律的作用 | 产出 | 状态 |
| --- | --- | --- | --- |
| **补优质** | 获奖名单的存放规律 → 批量拿到平台+读者双认证的书 | 优质子集 + 获奖标签 | 已验证（获奖定案） |
| **补书目** | 参赛清单 + tagId 规律 → 批量拿到参赛书全集 | 漏采书（尤其短/中篇） | 已验证（补采记录） |
| **提定年** | 官方赛程日期 → 高精度锚点 | 新书签定年更准 | 已验证（部分并入锚点表） |

**边界先行**：比赛只覆盖**参赛书**。未参赛的一次性完本短篇、更早的静态页时代作品仍会漏；
且比赛给的是**书目与认可信号**，成绩（收藏/点击）与实时状态仍要靠详情抓取。
本文研究的是「发现 + 优质增补」，不是「成绩实时」或「全量覆盖」的替代。

## 1. URL 规律

### 1.1 活动页 URL 的三代形态（按年代，实证）

| 世代 | URL 形态 | 数据存放 | 清单 API |
| --- | --- | --- | --- |
| 早期静态页（四/五征） | `book.sfacg.com/zwYYYY/` | 页面图片/少量链接 | **无**（只有规则页文本） |
| H5 活动页（2018–2022） | `pages.sfacg.com/{h5,pc}/act/zwYYYY/`、`/act/djzwYYYY/`（冬征） | 页面 `index.js` 顶部 `tagIds=[...]` | 旧 `Common.ashx?op=getNovelsByTag` |
| SPA 活动页（2023 起） | `pages.sfacg.com/h5/act/zwYYYYMMDD/pc` | 打包 JS 里 `longTagId/middleTagId/shortTagId`（X 征三轨）或单 `tagId`（冬征六 485 / 七 692 / **2024 春 699**） | 新 `/api/essay/getNovels` |

**规律**：年份段从 `zwYYYY`（启动年）演进到 `zwYYYYMMDD`（精确启动日，如 `zw20240504`=十二征 5-04）；
SPA 的日期 id 本身就是启动日，**可作赛事定年的页面自证**（见 `contest-editions.md`）。

**第四代（2024 秋起）：`zw/essayActivity_{UUID}.html`**。已实证六届（**2024 秋征** / 2025 春 / 2025 秋 / 2026 春 / 八征冬 / **九征冬**）都用它，
不再用日期式路径——**这正是春/秋征长期找不到 URL 的根因**，冬季征文从第八届起也换用它（旧一~五征是 `djzwYYYY`）。
**注意 UUID 页起点是 2024 秋征**：2024 春征（`zw20240301`，tag 699）仍是日期式 Vue SPA，
即 2024 年内春征（3 月）→ 秋征（9 月）之间换了模板，勿笼统写「2024 起都用 UUID 页」。
UUID 无法从届次推导，只能靠用户 App 提供入口；每届一套 UUID（4 个 tab：规则/作品/评论/获奖）。
六版同模板、只有 UUID 与 `template.js?v=` 版本号不同（2024 秋 `27868` / 2025 春 `42327` / 2025 秋 `83885` / 八征冬 `42945` / 2026 春 `62767` / 九征冬 `94362`），
版本大致随时间递增但非严格（2024 秋最早、九征冬最高、2026 春低于 2025 秋）。
且**用 jQuery + template.js、非 Vue**（与第三代 X 征 SPA 不同）。

**冬征 URL 演进补全（2026-11-21）**：第七届冬征（2023-12-04）用日期式 SPA `zw20231204`，
第六届（2022-12-05）用 `zw20221205`——两代都是日期式 SPA、都是**单轨**（tagId 485 / 692）。
即冬征经历 `djzwYYYY`（一~五征）→ `zwYYYYMMDD` SPA（六、七征）→ UUID 页（八征起）；
**至此冬征一~九届 URL 全部实证**（六/七征日期式 SPA、八/九征 UUID 页，九征 774 由 UUID 页 `data-tagid` 实证转正）。
两代 SPA 是同套模板早/晚期变体：六征 tagId 写死组件 data、获奖 `showBookDetail(数字)` + CSS 定位分组，
七征 tagId 分三环境、获奖 `openNovel("字符串")` + 标题图分组（§2.3 第四形态，详见 `contest-roster-fields.md` §8.6/§8.7）。

### 1.2 四条产品线的 URL 与节奏（全年首尾相接）

| 产品线 | URL 形态 | 启动节奏 | 掌握清单 API 到 |
| --- | --- | --- | --- |
| **X 征**（≈夏） | `zwYYYY` → `zwYYYYMMDD` | 早年 7 月、近年固定 5-04 | 十三征（2025） |
| **冬季征文** | 一~五征 `djzwYYYY` → 六/七征 `zwYYYYMMDD` SPA → **八征起 UUID 页** | 12 月上旬（12-04/05/06），1 月高峰 | 一~九征**全有且 URL 全实证**（六 485/七 692 SPA、八 726/九 774 UUID 页） |
| **春季征文** | **2024 春征 `zwYYYYMMDD` SPA → 2025/2026 `essayActivity_{UUID}.html`** | 3 月初（03-01） | **2024 春征(tag 699，日期式 SPA)、2025 春征(tag 746)、2026 春征(tag 789)** |
| **秋季征文** | **`essayActivity_{UUID}.html`（2024/2025 实证）** | 9-30 | **2024 秋征(725 UUID 页实证转正)、2025 秋征(772 页面实证)** |
| 对话线（点鸭等） | 点鸭系列 / 独立活动页 | 不定 | 724 点鸭秋色回忆等 |

**规律**：上一届截止与下一届启动仅差 0–1 天，四季构成**持续的新书供给泵**；
cohort bulk 下界定年一致晚于官方启动 9–20 天（投稿主体在启动后 1–3 周进入）——
**故 cohort 下界不可作启动日点锚，窗口约束才是正确用法**（`contest-editions.md`）。

### 1.3 获奖页 URL 的随机串规律（实操价值高）

获奖页末尾那串看似随机的路径（如 `zw20240504/Q3PrLponYiEwN`）是**活动页 JS 里写死的 Vue Router path**，
非 token/加密/动态生成。两类特性：
- **字符池固定**：来自同一混淆池反复重排（如十二征 `...QperQerQnWin` vs 十三征 `...QpersdQerQnWin` 只差 `sd`）；
- **语义会漂移**：几乎同串跨届可能从「长篇终审」变成「中短篇终审」。

**结论：不能硬编码 path→赛道**；每届从页面标题（组件 mounted 赋的 `document.title`）或 DevTools 确认。
详见 `contest-roster-fields.md` §8（两届完整路由表 + 陷阱实证）。

### 1.4 URL 缺口（研究重点）

春征 / 秋征 2024 起的 URL 已全部实证（2024 春 699 日期式 SPA、2024 秋 725 UUID 页、2025/2026 各届）；
**仅剩 2023 及更早的春/秋征 URL 未找到**、早期静态页（四/五征）无清单 API——这是「覆盖」的残余空白。
补齐优先靠**用户 App DevTools 现场取链接**，比猜 URL 快。

## 2. API / 数据通路规律

### 2.1 参赛清单：两套端点（按活动页世代）

| 世代 | 端点 | 翻页 | 返回 |
| --- | --- | --- | --- |
| 新 SPA（含 2026 UUID 页） | `/api/essay/getNovels?tagIds={t}&page={n}&size={n}` | **随版本变**：旧页 1 基、2026 春征页面代码传 `currentPage-1`（0 基），以页面实际传参为准 | `{status, data:{totalPage, novels[]}}` |
| 旧 H5 | `Common.ashx?op=getNovelsByTag&tagId={t}&ps=200&pi={0基}` | pi 0 基 | `{status:200, novels[], totalPage}` |

字段语义一一对应（大小写不同：`novelID` vs `NovelID`），每条 6 字段：nid/标题/作者/简介/封面/categoryID。
**不含成绩、定年、获奖、名次、赛道中文名**。参数与真实样例见 `sfacg-endpoints.md` §7.4、`contest-roster-fields.md` §1–§5。
**tagId 位置也随版本变**：旧 SPA 写在打包 JS 变量里、2026 UUID 页写在 HTML 的 `data-tagid` 属性（§2.2）。

### 2.2 tagId 分配规律（最重要的可推算规律）

1. **全局递增编号池**：同届赛项严格连号（653/654/655、702/703/704、752/753/754）；
   年度间隔稳定（655→702 = +47、702→752 = +48，每年新增约 47 个号，仅 3 个属 X 征）。
2. **每届新增、跨届不复用**：十三征三个号与十二征无复用关系——故不存在「掌握 4 个端点一劳永逸」。
3. **不区分赛事类型**：号池里混着题材/活动标签页，`categoryID` 无法区分（征文 tag 的 cat 也不统一）。
4. **环境异号**：sandbox/test/pages 三套不同（十二征短篇 533 vs 704），必须按 `location.host` 取 pages 值。

**可操作的补全路径**（已完整跑通一遍）：`size=1` 探活 → 定年聚集筛候选 → 用户 App 观测确认。
**陷阱**：size 对部分 tag 有边界（724 用 `size=500` 返回空、`size=1/3/8` 正常），判空须降 size 重试。
**已确认**：724=点鸭秋色回忆、789=2026 春征、746=2025 春征、772=2025 秋征、726=八征冬征（用户书名核对 / 页面 title）；**699=2024 春征**（本轮日期式 SPA 页面 JS `f121` 实证，sandbox 530 / pages 699）、**725=2024 秋征、774=九征冬征**（本轮 UUID 页实证转正，试号确认在先；`essayActivity_0a10b388-...html` / `essayActivity_373481c3-...html`）；页面实证名单再加 699、725、774；**692=七征冬征**（`zw20231204` 打包 JS `f121` 模块 `pages.tagId`，单轨，实测 200/totalPage=336）；**485=六征冬征**（`zw20221205` 组件 data 写死 `tagId:485`，无三环境配置，实测 200/totalPage=411）；详见 `contest-roster-harvest.md` §2.1–§2.2。

### 2.3 获奖名单：不在 API，存放形态随世代演进（四代）

获奖名单**不在任何接口**，但存放形态分四代，提取器必须都兼容：
1. 早期静态页：无获奖名单。
2. 十二/十三征：**JS 静态 JSON**（webpack 模块 `JSON.parse('[{"novelId","novelName"}]')`），
   一次 GET 一份 JS 得全量、无分页/鉴权。**两类陷阱**：① 初审/复审/入围模块（favs 中位 4–16）
   与获奖模块（1112–8372）混在一起，须按「奖项图标邻域 + favs 跃升」现场判定；② module id 是
   webpack hash、跨届会变，不能硬编码。
3. **UUID 页（2024 秋 + 2025 春/秋 + 2026 春 + 八征冬 + 九征冬，共 6 届实证）：HTML `<img data-nid data-categoryid alt>` 标签**——
   `data-nid` 给 nid（**唯一可靠字段**）、`alt` 给奖项名。**`alt` 命名法跨届变**：`02金奖.jpg` / `03金奖作品.png` /
   `02金奖-min.png`（2024 秋，奖项名完整可读）/ **八征冬退化成纯数字 `03-min.png`（奖项名丢失）**——后者要靠 HTML 结构恢复分组（偶数号 `<p>` 包裹无 nid 的是奖项标题图，
   奇数号有 nid 的是作品图），但中文奖项名写在标题图图片里、HTML 拿不到，不可臆造。
   获奖区还带 `data-firstpublictime`（2024 秋 2025-02-14、八征冬 2025-04-25、2025 春 2025-07-11、2025 秋 2026-02-13、九征冬 2026-05-15、2026 春 2026-07-10，均与官方公示日吻合）。
   档位每届不同：**2024 秋 11 本（金1/银1/铜3/推荐3/星火3，8.6k–33k，"星火奖"为新版奖项名）**、2025 春 10 本（金/银/铜×3/推荐×5，8.7k–27k）、八征冬 10 本（4 档 1/1/3/5，8.7k–80k，1 本不在库）、
   **九征冬 10 本（金1/银1/铜3/推荐5，6.2k–18.6k，alt 中文奖项名完整）**、2025 秋 7 本（金/银/铜×2/新人×3，6k–20k）、2026 春 6 本（金/银/铜/新人×3，金奖收藏仅 40）。
   这六版用 jQuery + template.js、非 Vue。详见 `contest-roster-fields.md` §8.5。
4. **日期式 Vue SPA（六/七征冬征、2024 春征）：Vue render 函数里硬编码 nid**——
   - 七征冬：`openNovel("677177")` 字符串参数 + `announce/N.png` 图（5 张标题图 + 16 张作品图），
     奖项名靠规则区名额 1/2/3/6/4 对齐；
   - 六征冬（早期变体）：`showBookDetail(619932)` **数字直接传参**，16 个可点击 div，
     **无标题图节点**，分组靠 CSS `top` 坐标跳变恢复（>8rem 为分界），同样 1/2/3/6/4 但名次仅布局推断、不臆造；
   - **2024 春征（第三变体）：`goNovel(692762)` 数字传参**，16 本按 `reward-box1/2/3/4` 分 3/3/5/5，
     另 6 张无 nid 标题图（奖项名在图里、JS 拿不到），公示 `2024-07-07 12:00`。
   公示切换点写死在 JS（六征 `2023/04/21`、七征 `2024-04-19 12:00`、春征 `2024/7/7 12:00`）。
   **三种调用写法（`openNovel("nid")` / `showBookDetail(nid)` / `goNovel(nid)`）提取正则都要兼容**，
   `data-nid`/函数参数始终是可靠 nid，奖项名只能尽力解析、不臆造。
   详见 `contest-roster-fields.md` §8.6/§8.7/§8.8。
详见 `award-winners-as-seed-source.md`、`contest-roster-fields.md` §8.4–§8.8。

### 2.4 官方赛程日期 → 定年锚点

活动页/官方通稿的精确日期是高置信锚点来源，但**用法有限制**：
四征的「窗口内最小 nid + 官方启动日」成立且已并入锚点表；
2024-09 后各届的 cohort bulk 下界定年一致晚 9–20 天，**点锚不成立，只作窗口约束与验证档案**。
详见 `contest-editions.md` §锚点候选、`anchor-density-strategy.md`。

## 3. 规律如何转化为种子质量（价值闭环）

| 通路 | 依赖规律 | 对种子的作用 | 质量提升机制 |
| --- | --- | --- | --- |
| **参赛清单补书目** | §1.1/1.2 URL + §2.1/2.2 API+tagId | 补 9,012 本（29%）不在 db 的参赛书，短/中篇漏采最重 | 扩大真实分母，让短/中篇评价公平（配合剔除假完结） |
| **获奖名单补优质** | §1.3 获奖页 + §2.3 静态 JSON | 新增优质子集 + `contest_awards` 表 | 平台+读者双认证，比单看收藏干净；同代分位中位 0.96–0.97 |
| **官方日期提定年** | §1.1 SPA 日期 id + §2.4 赛程 | 高精度锚点 | 新书签定年更准，支撑分位与榜单的时间可比性 |

**不造新指标**：排行榜仍用现有 `fav_pctl`；获奖只作筛选/徽标、不作打分项（避免「获奖 + 高收藏」双重计权）。
这与 app 主线（novly/classic 不引入新指标）一致。
