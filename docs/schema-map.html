667 本（全库 0.27%），666 张可下载，含 2013 年的书 → 图几乎永久可用。663/667 是 VIP。
不建 slot / start_at / end_at：官方只有一个 bgBanner 字段， 没有位置、没有上下架时间，不假装拿到。一行 = 一本书是唯一诚实的粒度。
轮播日轮换：(当天日期 ^ client_id) 做种子的加权随机，权重取 era_pct（不是 view_num）。 人气混了「当年用户规模」和「攒了多久」，直接加权会让 2015–2019 的老书永远赢。 同一天稳定（不闪图），一个月能看到 150 张不同，零后端。
不设 origin 字段去人工区分「成绩认可 / 引进推广」—— 30 本点击 < 50 万的角川系引进（文豪野犬 475）靠 era_pct 自然沉底，不隐藏不删除。
和 catalog.is_banner 的关系：「授予过」vs 「图还能下」，语义不同； 构建器断言两者行数相等，不等则失败。
nid_epoch2 列 / 85 行 seed.db ★ nid → 上架日。把「时间」变成免费字段
字段类型约束含义
nidINTEGERPK锚点书的官方 nid
dayINTEGERNOT NULL该 nid 的 addTime（unix 天）
85 个锚点，0 次逆序：nid 2,242 → 761,712 严格单调，分段线性插值误差 4 天 （nid=121065 估 2018-01-29 / 真 2018-02-02）。
为什么值得单独一张表：上游库没有 add_time，只有 last_update（活动时间）—— 而 banner 那批书长时间连载，last_update 全被拽到 2026 年。 这 85 行让 24.6 万本全部拿到上架日，零 API 请求，解锁了「年代轴」这一维。
首尾必须有真锚点：第一版最小锚点是 16870，nid=2242（真 2006-08-26）被外推成 2011-06-09，差 4.8 年。
维护：采集时遇到新书顺手 append 一条，锚点只增不改。

三条曲线同时往下：授予数 92 → 7（13 倍）、top1% 门槛 273 万 → 75 万（3.6 倍）、 banner 书人气 1,230 万 → 338 万（3.6 倍）。前一条是站方的钱，后两条是用户盘子。
用途：年代榜的语境（「2019 年 · 当年 24,347 本新书里 91 本获官方横幅」）、 年代总览页、以及给用户一个不下判断的解释——不同年份的成绩不能直接比。

F · 六条硬规则

1 · 数据可继承，判定不继承。上游的 A 后缀、warm/cold 分组、任何质量标签一律不取； stats_src + stats_at 是唯一表态。没有 quality、没有 stats_level。
2 · 字段名跟随 API key。viewTimes→view_num、markCount→mark_num、 expand.fav→fav_num。上游把「收藏」直译成 like、把「赞」直译成 praise，语义正好反了。
3 · 标签只有 name 一个身份。没有别名表、没有同义词表、没有 canonical。 「末世」8,813 本与「末日」465 本交集为 0，是两个独立标签。
4 · 写日志先于写数据。user_patch 是唯一能在种子替换后存活的东西。 先改 catalog 后补日志 = 中间崩溃就丢一个值，而且没有任何痕迹。
5 · 用户写入不改榜位。rank_snapshots 是构建期快照，本地重算会让 「看一次详情页」就能顶动榜，榜就不可解释了。自动收录的书没有榜位，UI 要能显示「有书、无排名」。
6 · 分期不改变库结构。v1 是纯静态架构（P0 bootstrap / P1 自产），没有任何服务端； 种子走 GitHub Release，观测全部留在设备上。P2 才加 FastAPI 收观测—— 届时这张图的 14 张表一行都不改，只多一个上报模块。
所以「用户可写」是第一版的能力，不是后端的能力；后端只决定观测会不会离开设备。
