## 0. 五条必须先读的结论

1. **官方搜索是 30 条截断，不是全库检索。** HTML 搜索返回条数上限 30，且页面上
   「共搜索到 N 个结果」的 N **本身就是截断后的数**——搜单字「之」声明 30 条，
   而库内标题含「之」的书有 28,100 本。**无法从接口得知真实命中总数。**
2. **但全库目录是可枚举的**：`op=novelbytype` 支持深翻页，九个分类合计 **42,568 页**
   = **255,408 个目录槽位**（≈ 目录能装多少书；PC 列表页页数同为 14,9xx，两端口径一致），
   实际返回 **221,354 条（±5,578）**——每页列 6 条、实测平均填充 5.20，
   **13% 的槽位被跳过**（条目移出目录但书仍可访问，悬疑整类普查实证）。
   末页停在 nid 2,689–3,355 的 2007 年老书（同人例外 54,067），
   **同页重复请求结果稳定、相邻页无重叠**。这是本次实测最重要的发现（§3、§5.1）。
3. **HTML 搜索有静默限流**：连续约 17–18 次请求后，返回 HTTP 200 + 页面标题变成
   「请输入关键字」+「共搜索到 0 个结果」，**不报错、不改状态码、不返回 429**。
   持续 3 分钟以上未恢复。同期 JSON 搜索、联想词、详情页、`novelbytype` 全部正常。
4. **状态码在本站零信息量**：不存在的 nid 同样返回 **HTTP 200**——PC 页 1,643 B 写着
   「小说不存在」，移动页 3,738 B 写着「出错啦」。**判存在/判活只能匹配文案**
   （§4.4）；同类陷阱还有 PC 列表页越界不报错而是粘住末页。
5. **判活要分三态，不细究下架原因**：① **死亡** = 「小说不存在」/「出错啦」页；
   ② **僵尸** = 有详情页但无阅读入口，或数字字段非法；③ **存活** = 有详情页 + 阅读入口 + 数字合法。
   僵尸页 13–15 KB、与存活页体积中位只差 35 B，按「>5KB 含书名」必判错。
   构建 CSV 已按 `status_missing` 剔除 **2,287 本僵尸**，**报告 10 把这批算作「存活」**，
   是 68.9% 口径的第三个缺陷（§5.2、§11.5）。

## 2. 搜索类：三个接口，三种能力

### 2.1 HTML 搜索（`s.sfacg.com`）

```
GET https://s.sfacg.com/?Key={关键词}&SS=0&S=1
```

| 参数 | 取值 | 语义 |
| --- | --- | --- |
| `Key` | 任意字符串 | 关键词。**必须 URL 编码**，否则中文可能被丢弃 |
| `S` | `1` | 查小说。`S=0` 返回漫画（实测小说条数为 0） |
| `SS` | `0`/`1`/`2` | **实测无效**。三种取值返回条数完全相同（29/29/29），可省略 |

**返回**：ASP.NET WebForms 页面（含 `__VIEWSTATE`），结果在 `<ul>` 列表里。
上游解析器 `_parse_html_results` 逐 `<ul>` 取 `<li>`。

| 字段 | 覆盖 | 说明 |
| --- | --- | --- |
| `NovelID` | 29/29 | 从链接 `book.sfacg.com/Novel/{nid}` 提取 |
| 书名 | 29/29 | `<a class="orange_link2">` 文本 |
| 作者 | 29/29 | 「综合信息： 作者/日期」斜杠前 |
| `last_update` | 29/29 | 同上斜杠后，格式 `YYYY/M/D H:MM:SS` |
| 封面 | 29/29 | `<img src>`，`//rs.sfacg.com/...` 协议相对 |
| **简介** | **27/29** | `li` 内的裸文本节点，长度 20–200 字。**这是三个接口里唯一提供简介的** |
| 评分 | ✗ | **没有** `Point` |

**条数上限（实测）**：

| 关键词 | 声明条数 | 实际返回 | 库内标题命中 |
| --- | --- | --- | --- |
| 英雄 | 29 | 29 | 1,289 |
| 重生 | 30 | 30 | 4,424 |
| 少女 | 29 | 29 | 11,168 |
| 之 | 30 | 30 | 28,100 |
| 的 | 28 | 28 | 98,793 |
| 魔法 | 28 | 28 | 4,405 |
| 转生 | 30 | 30 | 4,710 |

**上限 30，且「共搜索到 N 个结果」与返回条数恒等**——N 是被截断的数字，不是真实总量。
搜单字「的」时声明 28 条，而库内标题含「的」有近 10 万本。**不存在「翻到后面」这条路**。

**分页参数全部无效**（关键词「重生」，基准首条 `506050`）：

| 附加参数 | 返回条数 | 与基准是否同一结果集 |
| --- | --- | --- |
| （无） | 30 | — |
| `Page=2` | 30 | **是** |
| `page=2` | 30 | 是 |
| `pi=2` | 30 | 是 |
| `PageIndex=2` | 30 | 是 |
| `PageSize=50` | 30 | 是 |

### 2.2 JSON 搜索（`HTML5.ashx?op=search`）

```
GET https://m.sfacg.com/API/HTML5.ashx?op=search&keyword={kw}&_={毫秒时间戳}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `Status` | int | 200 正常 |
| `Novels[].NovelID` | int | nid |
| `Novels[].NovelName` | string | 书名 |
| `Novels[].AuthorName` | string | 作者 |
| `Novels[].TypeName` | string | 中文分类：科幻/魔幻/都市/玄幻 |
| `Novels[].Point` | float | **评分 0–10**，HTML 接口没有 |
| `Novels[].NovelCover` | string | 封面相对路径，需拼 `{COVER_BASE}/` |
| `Novels[].Tags` | null | **实测 240 条全为 `null`**，字段形同不存在 |

**条数**：实测 20 个关键词，6–15 条，**中位 12**（早期档案写的「固定 12 条」不准确，
是「多数 12，随关键词浮动」）。

| 条数 | 6 | 7 | 8 | 9 | 11 | 12 | 13 | 14 | 15 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 出现次数 | 1 | 1 | 1 | 1 | 1 | 5 | 3 | 5 | 2 |

**分页无效**：`pi=1/2/3` 返回完全相同的 12 条（`48704, 120384, 208296, …`）。

**与 HTML 搜索的关系（关键词「英雄」）**：

| 项 | 值 |
| --- | --- |
| HTML 29 条、JSON 12 条 | — |
| **JSON 独有** | **0 条** |
| HTML 独有 | 17 条 |
| JSON 在 HTML 中的位置 | `0,1,2,…,10,13`——**不是严格前缀** |

即：JSON 是 HTML 结果的子集，但少掉的第 12 条（索引 13 的 `124218`）说明两者
**排序规则不完全一致**，不能当成「HTML 的前 12 条」使用。

### 2.3 联想词（`Book.ashx?op=searchreffer`）

```
POST https://m.sfacg.com/API/Book.ashx?op=searchreffer
Content-Type: application/x-www-form-urlencoded; charset=UTF-8
Origin: https://m.sfacg.com
Referer: https://m.sfacg.com/search.html
X-Requested-With: XMLHttpRequest

keyword={关键词}
```

**返回**：`{"status": 200, "keywords": ["书名1", "书名2", ...]}`，**只有完整书名，无 nid**。

实测「英雄」15 条，**含重复**：

```
英雄我早就不当了
英雄再临(英雄？我早就不当了)
英雄再临（英雄？我早就不当了）      ← 全角括号，与前一条实为同一书
拜托请不要再找我当超级英雄了
拜托请不要再找我当超级英雄了          ← 完全重复
```

**必须去重**：规范化全/半角括号后按书名去重，15 条实测去重后剩 13 条。
联想词只用于「补全书名」，**不能直接当搜索结果**（没有 nid，无法 join）。

> 客户端用法见 `m.sfacg.com/search.html` 的内联 JS：`data: { keyword: encodeURIComponent($(this).val()) }`。
> 注意它做了 `encodeURIComponent`，而 jQuery 默认又会编码一次——**服务端实际收到的是双重编码**。
> 上游库 `predictive_novel` **不做编码**，实测同样返回 15 条，两种都能用。

### 2.4 三接口能力对照

| 能力 | HTML | JSON | 联想词 |
| --- | --- | --- | --- |
| 条数 | ≤30 | 6–15 | 15 |
| 分页 | ✗ | ✗ | ✗ |
| nid | ✓ | ✓ | **✗** |
| 简介 | **✓（27/29）** | ✗ | ✗ |
| 评分 `Point` | ✗ | **✓** | ✗ |
| 分类 `TypeName` | ✗ | ✓ | ✗ |
| 封面 | ✓ | ✓ | ✗ |
| `last_update` | ✓ | ✗ | ✗ |
| 受静默限流 | **是** | 否 | 否 |

**结论**：三者不可互相替代。HTML 提供简介与更新时间，JSON 提供评分与分类，
联想词提供「用户可能想搜什么」。**评分只存在于 JSON，简介只存在于 HTML。**

## 3. 分类枚举（`op=novelbytype`）——全库可枚举

这是本次实测最重要的发现：**官方目录存在一条可深翻页的枚举通路**，
此前所有档案（含 `archive/search.md`）都只记录了三个搜索接口，因而误判「官方只能搜不能列」。

```
POST https://m.sfacg.com/API/HTML5.ashx?op=novelbytype
Content-Type: application/x-www-form-urlencoded; charset=UTF-8
Referer: https://m.sfacg.com/search.html?type={tid}

tid={tid}&pi={页码}
```

| 项 | 实测 |
| --- | --- |
| 每页条数 | **6**（末页可少于 6） |
| 页码起止 | `pi` 从 **1** 开始；`pi=0` 返回空 |
| 返回字段 | 与 JSON 搜索**完全相同**（`NovelID/NovelName/AuthorName/TypeName/Point/NovelCover/Tags`），`Tags` 同样恒 null |
| 排序 | **不是按 nid**。首页混有 789090/773281/778683，第 5000 页混有 564324/572135/702115 |
| 稳定性 | **同页重复请求结果完全一致**；**相邻页无重叠**（5000∩5001 = ∅，5001∩5002 = ∅） |
| 体积 | 1.5 KB/页 |

**九个分类的目录容量**（`pi` 二分到最后一页，精度 ±1 页）：

| tid | 分类 | 末页 `pi` | 末页填充 | 目录槽位（×6） | 库内同分类 | 库内/槽位 |
| --- | --- | --- | --- | --- | --- | --- |
| 21 | 魔幻 | 14,908 | 5/6 | 89,448 | 85,696 | 95.8% |
| 22 | 玄幻 | 5,131 | 1/6 | 30,786 | 29,798 | 96.8% |
| 23 | 古风 | 1,430 | 4/6 | 8,580 | 8,258 | 96.2% |
| 24 | 科幻 | 2,994 | 1/6 | 17,964 | 17,366 | 96.7% |
| 25 | 校园 | 5,539 | 2/6 | 33,234 | 31,595 | 95.1% |
| 26 | 都市 | 4,154 | 4/6 | 24,924 | 23,450 | 94.1% |
| 27 | 游戏 | 2,180 | 1/6 | 13,080 | 12,782 | 97.7% |
| 28 | 同人 | 5,306 | 1/6 | 31,836 | 31,664 | 99.5% |
| 29 | 悬疑 | 926 | 2/6 | 5,556 | 5,170 | 93.1% |
| | **合计** | **42,568** | | **255,408** | **245,779** | **96.2%** |

> **本表已修正一次**：初版用 100 页窗口的粗略二分（误差可达 −100 页/类），把合计少记了 298 页
> （42,270 → 42,568）；当时的「游戏 100.3%、同人 100.7%」是这一精度缺陷造成的假象，
> 修正后九类全部 ≤100%。可复现于 `fetchers/probe_novelbytype.py`。

**四条必须注意的口径**：

1. **槽位 ≠ 返回条数**。「页 × 6」是**目录容量**（平台分页能铺出的位置数），
   实测平均填充 **5.20 条/页**（180 页随机抽样，SD 0.90，SE 0.067；分布 6→81、5→65、4→25、
   3→7、2→2），故实际返回 ≈ 42,568 × 5.20 = **221,354 ± 5,578（95% CI）**。
   **缺的 13% 不是「书不存在」，而是槽位被跳过**——悬疑 5,556 槽位返回 4,836，
   其中 523 本库内书查不到目录（§5.1）。
2. **分类内存在空洞页**。悬疑整类扫描中第 **915 页为空**、916–926 页仍有内容——
   二分法假定「空页之后全空」，因此末页值应读作「最后一个非空页」，与真实内容末端可差数页。
3. **「库内/枚举」比值不是覆盖率**。分母是上界、分子是库内 245,779 行（已剔正版日轻、含 2026 年）。
   九类比值 93.1–99.5% 是在「×6 上界」口径下算的，换成 ×5.20 会**全部超过 100%**——
   即库内书比分类目录里能列出的还多（§5.1）。
4. **排序不按 nid，且无「最新」参数**。首页混有 2026-10 的新书与 2022 年的书，
   **因此枚举不是「按时间增量同步」的工具**——要发现新书必须整类重扫，
   或靠首页（首页明显偏向新书，实测前三条 `786381/783690/778683` 均 ≥77 万）。

**限流表现（与 HTML 搜索相反）**：连打 30 次、间隔 0.5 秒，**30/30 全部成功、零空响应**；
0.3 秒间隔连扫 929 页（悬疑整类）同样零失败。单页 1.5 KB，42,568 页约 **62 MB 流量**，
按 0.5 s/页约 **5.9 小时**（实测约 1.4 s/页，整类九类全扫实际需 16 小时以上）。

### 3.5 更新窗口列表（`List/?ud={days}`）——最近 N 天被触碰的书（2026-11-18 实测）

`GET book.sfacg.com/List/?ud={days}&PageIndex={n}`，PC HTML，20 本/页，按最近更新降序。
页头「现在有`<span>N</span>`部小说」报窗口总数（ud=7 实测 1,943），但**站方在 ≈82 页
（≈1,640 本）截断**——与月榜 top20 右截断同性质，报的数翻不到。列表行自带标题/作者
（含 authorId）/评分/分类 tid/更新日期/字数，详情抓取失败仍有可用行。

与 novelbytype（#4）的分工：枚举全库但**无增量能力**（§3 陷阱）；ud 列表是唯一
「最近被更新」的高效增量发现源，ud=15/30 可扩窗（窗口上界未测）。
端点与截断上限发现自第三方 `jiweiyaya/sfacg-rank`（github.com/jiuweiyaya/sfacg-rank），
本项目实测复核：ud=7 PageIndex=1 → 28.7 KB / 20 条 / 总数 1,943。

### 5.1 目录容量、实际返回量与报告 10 的口径

**先分清三个数**，它们以前被混用：

| 量 | 数值 | 含义 |
| --- | --- | --- |
| **目录槽位容量** | 42,568 页 × 6 = **255,408** | 分页能铺出的位置总数。PC 列表页 `book.sfacg.com/List/?tid=21` 的页数同为 **14,9xx**（`pi=14900` 仍返回 20 条），与移动端吻合——**这是目录能装多少书** |
| **实际返回的唯一 nid** | **221,354 ± 5,578**（5.20 条/页） | 枚举真正给到的条目数 |
| 缺口 | **≈34,054（13.3%）** | 被跳过的槽位：条目被移出目录，但书本身可能仍可访问 |

> ⚠️ **255,408 是目录容量，不是全站活书上界**。我先前据此否定报告 10 的 356,696 本，
> 该推论已撤回：平台存在大量「页面可访问、但不在任何分类目录里」的书（下节实证），
> 这类书不占目录槽位。**目录装不下 ≠ 站上没有。**

**悬疑（tid=29）整类普查**（929 页全扫，可复现）：

| 指标 | 数值 |
| --- | --- |
| 目录槽位 | 926 页 × 6 = 5,556 |
| 返回条目（含重复） | 4,836 |
| 唯一 nid | **4,834**（2 条重复） |
| 槽位缺口 | **720**（13.0%，与全站 13.3% 一致） |
| 空页 | 915（类内空洞）、927–929（越过末页） |
| 与库内交集 | **4,647**（96.1%） |
| 库外合计 | **187** |
| ├ 快照后新建（nid > 774,850） | **165**（3.4%）——**不是漏抓，是时间差** |
| └ 同范围真遗漏 | **22**（占同范围 4,669 本的 **0.47%**） |
| 库内悬疑总数 | 5,170 → **523 本（10.1%）不在该分类目录里** |

**720 个槽位缺口与 523 本「库内有、目录无」是同量级的同一现象**：这 523 本几乎就是被目录跳过的那批书的一部分（差额 197 本是同类完全不存在的书）。抽 10 本核查，页面正常打开、分类标签仍写作「悬疑」，**不是改分类**。

由此得到四条结论：

1. **库外条目的主体是「新书」，不是「漏抓」**。165/187 的 nid 大于快照最大 nid（774,850），
   是 2026-05 扫描结束后上架的作品。**只有 22 本在快照范围内却未被收录（0.47%）**——
   按此外推全站真遗漏约 **1k 本**。（旧稿按 187/4,834 = 3.9% 外推得 8.6k，把时间差算成了漏抓。）
2. **「不在目录」是平台常态，不是异常**。约 **10% 的库内书查不到分类目录**（523/5,170），
   目录自身也有 **13% 的槽位被跳过**。因此**任何以目录为全集的口径都会系统性少算**。
3. **报告 10 的 21.1% 不能被目录口径直接否证，但也不能照用**。它测的是
   「`m.sfacg.com/b/{nid}/` 能否打开」——而「目录外仍可访问」的书确实大量存在，
   所以它推出的 11.1 万本遗漏**并非算术不可能**（我先前用目录容量下的「上界否决」是错的）。
   但它的判据有三个未验证的前提（见 §5.2）：① 未排除把非小说页算作存活；
   ② **状态码在本站完全不可信**（无效 nid 同样返回 200，见 §4.4）；
   ③ **未检查是否有阅读入口**——僵尸书有完整详情页，会被判「存活」。
4. **两个集合必须分开命名**：`目录内（可发现）` 与 `可访问（页面存在）`。
   库内书既有在目录里的，也有不在目录里的；目录里既有库内的，也有快照后新增的。

**处置**：报告 10 §4 的 68.9%（→ 356,696）在重算前**不可再被下游引用为覆盖率**；
任何引用须同时写明「页面存活口径」。重算需要「可访问 ∩ 在目录 ∩ 有阅读入口」的**联合抽样**
（同一批 nid 同时测三件事），而非单独补测一侧，也不是用目录容量做上界（§12 #7）。

### 5.2 三类「不存在」必须分开：死亡 / 僵尸 / 清洗剔除

用户 2026-11-17 指出报告 10 的根本缺陷：**它的「nid 缺失槽位 = 抓取遗漏」前提不成立**，
因为缺失槽位由三种互斥机制共同产生，而探针只区分了「页面能不能打开」。

| 类型 | 页面表现 | 状态码 | 有无阅读入口 | 在 CSV 中 | 报告 10 会判为 |
| --- | --- | --- | --- | --- | --- |
| **死亡** | PC 显示「小说不存在」；移动版「出错啦」 | **200** | — | 否 | 死槽（判对了） |
| **僵尸** | 有详情页（书名/字数/收藏/分类），但**无阅读入口**或**数字字段非法**；页面 13–15 KB | 200 | 无或数值非法 | 多数已剔除 | **存活（判错）** |
| **存活** | 有详情页 + `点击阅读`/`目录列表` + 数字合法 | 200 | 有且合法 | 是 | 正确 |

> 僵尸的成因很多——版权、违法违规、抄袭、搬运、AI 生成、作者主动、举报下架等，
> **不进判据**；多数页面简介**不会写**下架声明（§11.5）。低 id 段以盗版日轻为主，
> 只是僵尸的一个子集，不是全部。

**构建期的清洗已经处理掉一批**（`out/manifest.json` → `dropped`，共 **2,451 行**）：

| 剔除规则 | 行数 | 说明 |
| --- | ---: | --- |
| `status_missing` | **2,287** | status 为空 = 已下架但详情页仍保留 → **主要就是僵尸书** |
| `negative_favs` | 58 | 收藏下溢 |
| `title_without_text` | 56 | 无文字书名且无内容 |
| `licensed_light_novel` | **47** | 正版日轻（版权方账号），对应小 id 段 |
| `genre_unresolved` | 2 | 2010 改版前旧分类 |
| `all_zero` | 1 | 全零 |

剔除集 nid 中位 **9,272**，**2,342/2,451 < 10 万**——低 id 段密集，与「早期盗版日轻授权到期被强制下架」吻合。
`config.py` 的注释已写明：正版上架复用了同标题盗版条目的旧 id，授权到期使在册状态与内容失效。

**抽查实证**（随机 8 本剔除集 nid，2026-11-17）：

| nid | 标题 | 字节 | 状态 |
| --- | --- | ---: | --- |
| 21899 | 灌篮少年 | 13,802 | **僵尸**：页面完整、无阅读入口 |
| 44745 | 王者英雄战记 | 14,217 | 僵尸 |
| 24398 | 梦魔少年！ | 14,283 | 僵尸 |
| 21858 | 青之驱魔师 | 14,074 | 僵尸 |
| 29138 | 灰烬的深红·雷顿 | 14,182 | 僵尸 |
| 6359 | 罪恶天使 | 13,549 | 僵尸 |
| 6246 | 圣殿骑士的血 | 15,007 | 僵尸 |
| 307147 | `156879` | 13,837 | 有阅读入口（例外） |

**7/8 是僵尸**——`>5KB 且含书名` 会把它们全部计为「活书」。
对照：库内书与报告 10 的 63 本「遗漏存活书」抽查均有「点击阅读」「目录列表」，不是僵尸；
所以问题不在那 63 本的个体判定，而在**推断链把「缺失槽位中的死亡/僵尸/清洗剔除」整体当成了抓取遗漏**。

**三条硬结论**：

1. **判活按三态**：死亡看否定文案、僵尸看「无阅读入口 / 数字字段非法」、其余才算存活；
   不细究下架原因，不看体积与 HTTP 状态码（§11.5）。
2. **「nid 空洞」不是待解释的遗漏量**：其中一大块是构建期主动剔除（2,451 本，
   原始 jsonl 里都已抓到）与各类下架，不能反过来当作「数据集漏抓」的证据。
3. **低 id 段不能当作健康存量**：早期盗版日轻只是僵尸的一个子集，
   其他成因在下架时同样留下死亡页或僵尸页——这是**结构性缺失**，不是随机漏抓，
   因此遗漏并非「近均匀于世代」。

**复现**：

```bash
uv run --project analysis python -c "
import json, requests, re
ids = json.load(open('analysis/out/manifest.json', encoding='utf-8'))['dropped']['ids']
H = {'User-Agent': 'Mozilla/5.0 (Linux; Android 13) AppleWebKit/537.36 Chrome/131.0.0.0 Mobile Safari/537.36'}
for nid in ids[:8]:
    t = requests.get(f'https://m.sfacg.com/b/{nid}/', headers=H, timeout=20).text
    print(nid, len(t), '点击阅读' in t, '目录列表' in t, '出错啦' in t)
"
```
唯一可以确定的算术是：**目录容量 255,408 ≥ 任何时点的在目录书数**。

**「人气」带「万」单位且会被截断**（`11899.5万` = 118,995,000，数据集记 118,520,000，
差值来自时点不同）。**解析必须处理「万」后缀**，上游 `_row()` 的做法是
`float(x.replace("万","")) * 10000`，注意这会把 `11899.5万` 算成 118,995,000

### 4.3 两版取舍

| 需求 | 用哪个 |
| --- | --- |
| 收藏 / 赞 / 简介 / 体积小 | **移动版**（15 KB） |
| 点击数（人气） | **只能 PC 版**（73 KB） |
| 标签 | 只有 PC 版有结构化 `.tag-list`；移动版标签在 JS 里 |
| banner 位 | PC 版 `.d-banner` |

**移动版快 5 倍**。端上每次进详情页若只要收藏与赞，用移动版；
需要点击数时再补 PC 版——但**不要两版都抓**，5 倍体积差在端上不可忽视。

### 4.4 状态码不可信：判存在必须查文案

**本站对不存在的 nid 返回 HTTP 200**，与正常页同状态码、同 content-type。实测：

| 请求 | 状态码 | 体积 | 标题 | 页面文案 |
| --- | --- | --- | --- | --- |
| `book.sfacg.com/Novel/{无效 nid}/` | **200** | **1,643 B** | 出错了 | `漫 画 轻小说　小说不存在　很抱歉给您带来不便，如有需要您可以邮件联系我们　点击返回 轻小说频道首页` |
| `m.sfacg.com/b/{无效 nid}/` | **200** | **3,738 B** | 出错啦 | `出错啦`（无书名、无字数） |
| `m.sfacg.com/b/48704/`（有效） | 200 | 73,527 B（PC）/ 14.7 KB（移动） | 含书名 | 正常 |

**三条判据，按可靠性排序**：

1. **匹配否定文案**：PC 页查 `小说不存在`，移动页查 `出错啦`——这是唯一与实现无关的判据；
2. **无条件检查书名**：移动页正常时有 `.book_info span`，无效页没有；
3. ~~体积阈值~~（>5KB 判活）：只在「死页恰好 3.6 KB」时成立，**换版式即失效**，不可作为唯一依据；
4. ~~HTTP 状态码~~：**完全无效**，200 覆盖一切。

> 报告 10 的存活探针用的是「>5 KB 且含书名」，在移动版上恰好能分开；
> 但它同时**没有排除非小说页**（漫画与小说共享 nid 空间），也没有留下文案判据，
> 这是其 21.1% 至今无法复核的原因之一（§5.1）。

**另一个同类陷阱：PC 列表页越界不报错，而是粘住末页**。
`book.sfacg.com/List/?tid=21&pi=14920`（已越界）与 `pi=20000` 返回**完全相同的 34,181 B 页面**，
首批 id 一致（787963/787796/755372）——**不能用「返回为空」判断末页，只能比对内容是否与前一页相同**。
移动端 `op=novelbytype` 相反，越界返回空数组，可以正常判末页。

### 7.4 征文参赛清单（`getNovelsByTag` / `essay/getNovels`）——补采短/中篇（2026-11-20 实测）

征文活动页的「参赛作品区」是**分页 REST 接口**，无需登录、无认证，
返回 `nid/标题/作者/作品简介/封面/categoryID`，可用于补采单向游标扫描漏掉的短/中篇。
**两套接口按征文页年代分**（另见专题 `docs/contest-roster-harvest.md`）：

| | 旧 H5 页（2018–2022） | 新 SPA 页（2023 起） |
| --- | --- | --- |
| 地址 | `GET pages.sfacg.com/ajax/ashx/Common.ashx` | `GET pages.sfacg.com/api/essay/getNovels` |
| 参数 | `op=getNovelsByTag&tagId={t}&ps=200&pi={0起}` | `tagIds={t}&page={1起}&size={n}` |
| 返回 | `{status,novels[],totalPage}` | `{status:{errorCode},data:{totalPage,novels[]}}` |
| 条目字段 | `NovelID/NovelName/AuthorName/Intro/Cover/CategoryID` | `novelID/novelName/authorName/intro/cover/categoryID` |
| 单页上限 | `ps=200` 实测可用 | `size=500` 实测可用（更大值反被服务端截断） |

```text
GET https://pages.sfacg.com/ajax/ashx/Common.ashx?op=getNovelsByTag&tagId=415&ps=200&pi=0
GET https://pages.sfacg.com/api/essay/getNovels?tagIds=704&page=1&size=500
```

**关键陷阱**：

- **字段名大小写两套不同**（`NovelID` vs `novelID`、`Intro` vs `intro`），解析要兼容。
- **翻页起点随页面版本变**：旧 H5 用 `pi={0起}`；新 SPA 多数用 `page={1起}`，但 2025/2026 春征 UUID 页的
  `getNovelList` 传 `page: currentPage-1`（0 基）——**按页面 JS 实际传参为准，不要假设固定 1 基**。
- **`tagId` 是「某届比赛的某个赛项」的编号，每次新增、跨届不复用**（用户裁定 2026-11-21）：
  长/中/短各有独立 id，每办一届就新分配一批（十三征 752/753/754 与十二征 702/703/704 无复用关系，
  2024 春征 = 699、2025 春征 = 746、2025 秋征 = 772、2026 春征 = 789、2024 秋征 = 725、八征冬征 = 726、九征冬征 = 774、**七征冬征 = 692、六征冬征 = 485（均单轨）**），且同一赛事 sandbox 与生产环境 id 不同（十二征短篇 `533` vs `704`；2024 春征 sandbox `530` vs pages `699`）。
  **tagId 的位置也随版本变**：旧 SPA 写在打包 JS 变量里，UUID 页写在 HTML `data-tagid` 属性。
  必须按每届页面实际取生产值、按 `location.host` 前缀选环境，**不能从届次/赛项名推导、更不能猜**；
  这也是 tag 地图永远追不齐的根因。已实测的 tag 表见专题文档。
- **活动页 URL 形态演进**：`zwYYYY` → `zwYYYYMMDD` → 2025 起 `zw/essayActivity_{UUID}.html`
  （春/秋征用 UUID 页、冬征从第八届起也用 UUID 页、无法从届次推导，只能由用户 App 提供入口，
  已实证 2024 秋/2025 春/2025 秋/2026 春/八征冬/九征冬六版，详见 `contest-roster-fields.md` §8.5）。
  **例外**：冬征六/七届（2022-12 / 2023-12）是日期式 SPA `zw20221205` / `zw20231204`（单轨 tagId 写死在 JS），
  获奖写死在 Vue render 函数而非 HTML `data-tagid`（第四代形态，六征 `showBookDetail(数字)`、
  七征 `openNovel("字符串")`，详见 `contest-roster-fields.md` §8.6/§8.7）。
- `categoryID` 取值旧接口 `0/1`、新接口 `0/1/3`，与 `forms` 的 categoryId 判据同源，
  但**不能当 form 真值**（E.28 只正向用 `1/4`）。
- 清单里的 `intro` 是**作品简介**，不是作者 intro（作者资料见 `author-profile-on-demand.md`）。
- 只覆盖**参赛**作品；未参赛的一次性完本短篇仍会漏，非全库金标。

**请求样例**（2026-11-20 实测）：14 个 tag 去重 31,092 本，9,012 本（29%）不在 db，
短/中篇赛道漏采最重（十二征短篇 171/321）。实测用 0.25–0.6 s 串行 / 4 并发，无风控迹象；
沿用引擎既有抓取限速，只取清单元数据、不取正文、不登录。

## 8. 限流与失败模式

### 8.1 HTML 搜索的静默限流（最危险的一种失败）

| 项 | 实测 |
| --- | --- |
| 触发条件 | 连续约 **17–18** 次请求（间隔 0.5 s）后 |
| 表现 | **HTTP 200**，页面正常返回（5.8 KB），但标题变成「请输入关键字」，声明「共搜索到 0 个结果」 |
| 持续 | **> 3 分钟未恢复**（实测 20/45/90/180 秒均仍被限） |
| 影响范围 | **仅 `s.sfacg.com`**。同期 JSON 搜索、联想词、详情页、`novelbytype` 全部正常 |

**这是最危险的失败模式**：状态码 200、无异常、结构合法，只有一个中文短语说明被限。
任何「用条数是否为空判断成功」的逻辑都会把它当成「真的没搜到」，**静默地给出错误结论**。

**唯一可靠的检测方式**：检查响应里是否含「请输入关键字」。
上游库 `_parse_html_results` **不做此检查**，被限时返回空列表——这是必须自行补的。

### 8.2 其他端点的限流

| 端点 | 连打 30 次 @0.5 s | 结论 |
| --- | --- | --- |
| `op=novelbytype` | 30/30 成功 | 无可见限流 |
| `op=search`（JSON） | 未触发 | 网页实际调用就是它，正常量级安全 |

**建议节流**：单端点 ≥1 s 间隔；HTML 搜索是唯一需要严格计数的端点，
建议客户端硬上限（如 10 次/分钟）并在被限时降级到 JSON 搜索。

### 8.3 参数陷阱（本次实测纠正的四个误解）

| 误解 | 实测事实 |
| --- | --- |
| 「`SS=0` 会让搜索返回空」 | **假**。`SS` 三值无差异（29/29/29）。当时看到的空结果是限流，不是参数 |
| 「HTML 搜索返回全量」 | **假**。硬上限 30，且声明的 N 也是截断值 |
| 「JSON 搜索固定 12 条」 | **不准确**。6–15 条，中位 12 |
| 「`novelbytype` 需要特殊的 tid」 | **假**。tid 就是 PC 分类页的 21–29，九类齐全 |

## 11.5 页面状态判据：基于构建剔除 id 的对照实验（2026-11-17）

用户指出「处理构建脚本发现的区别，应该还有其他区别」——对，而且**区别比预想的大**：
`drop_mask` 的六类剔除里，**只有一类的页面真的不可读**，其余四类页面完全正常。

### 0. DOM 与目录页：两个更结构化的判据（2026-11-17 补充）

**详情页 DOM 几乎相同**（同一套 `book_*` class），差别集中在阅读容器：

| 选择器 | 僵尸（21899） | 存活（48704） |
| --- | --- | --- |
| `div.book_Catalog` | **空容器** `<div class="book_Catalog"></div>` | `<a href="/c/{nid}">点击阅读</a><a href="/i/{nid}">目录列表</a>` |
| `.book_info2` | `都市 已完结`（无 VIP） | `科幻 已完结 VIP` |
| `.book_Content_style` | 收藏/赞/打赏/月票都在，数值小 | 同结构，数值大 |
| 页面 `<a>` 总数 | 12 | 18（多 `/c/`、`/i/`、`/txt/`） |

**最优判据：检查 `div.book_Catalog` 下是否有 `<a>`**——比全文关键词匹配更稳定，
不依赖文案（下架原因多样、多数不写声明）。fallback 才是 `点击阅读`/`目录列表` 关键词。

**目录页 `/i/{nid}/` 仍存在，但空壳**：僵尸书 4–6 KB、章节字 <10；
存活书 48704 为 167 KB、章节字 1,078。`/c/{nid}/`（阅读页）对两者都返回
3,738 B「出错啦」，**不能用来区分**。目录页体积差 30 倍，可作二次确认，
但成本比详情页高 10 倍，不适合大规模判活。

**nid 区间分布（重要，直接影响补爬估算）**：

| 剔除原因 | n | nid 上限 | >10 万 | 页面状态 |
| --- | ---: | ---: | ---: | --- |
| `status_missing`（僵尸） | **2,287** | **83,624** | **0** | **全部无阅读入口** |
| `negative_favs` | 58 | 725,760 | 56 | 有阅读入口，数字非法 |
| `title_without_text` | 56 | 747,626 | 36 | 有阅读入口 |
| `licensed_light_novel` | 47 | 763,621 | 14 | 有阅读入口，VIP ~18 KB |
| `genre_unresolved` | 2 | 304,822 | 2 | 有阅读入口 |

**僵尸严格集中在 nid ≤ 83,624**——早期兴趣站搬运产物的低 id 段，作者名/书名有明显日系风格。
**高 nid 区间不存在僵尸**：独立验证两组样本——

- 报告 10 探针 `range_missing` 组按 nid 分 4 段各抽 10 本「旧判存活」：
  **40/40 都有阅读入口**（0–10万、10–25万、25–50万、50–80万）；
- 高 nid 30 本旧判存活 + 20 本旧判死亡：前者 30/30 有阅读入口，后者 20/20 是「出错啦」死亡页；
- 库内 nid >60 万 30 本：30/30 存活。

⇒ **僵尸不是均匀现象，而是低 id 段的结构性遗留**。报告 10 的「遗漏偏短、新、更新中」画像
若要保留，必须**剔除低 id 僵尸的干扰**后重新验证；补爬量估算也应按此分层，
不能对全 nid 范围套同一僵尸率。

### 实验设计

从 `out/manifest.json` 的 2,451 个剔除 id 出发，用 `pipeline.build_csv.load_jsonl` +
`clean_row` + `drop_mask` 重建逐条原因（manifest 只存汇总 id，需重跑判据）。
分组抽样 `m.sfacg.com/b/{nid}/` 移动版，76 次请求零失败，间隔 0.25 s：

| 组 | n | 体积中位 | 点击阅读 | 目录列表 | `应版权方要求` | 结论 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| **存活（CSV 内随机）** | 20 | 14,214 | **20/20** | 20/20 | 0/20 | 正常可读 |
| **`status_missing`（28 类）** | 20 | 14,179 | **0/20** | 0/20 | **20/20** | **版权下架僵尸** |
| `licensed_light_novel` | 20 | 18,034 | 20/20 | 20/20 | 0/20 | 正版日轻在读，剔除理由不是不可读 |
| `negative_favs` | 8 | 14,082 | 8/8 | 8/8 | 0/8 | 数值脏，页面可读 |
| `title_without_text` | 8 | 13,743 | 8/8 | 8/8 | 0/8 | 标题是符号，页面可读 |
| **死亡（无效 nid）** | 5 | **3,738** | 0/5 | 0/5 | 0/5 | 标题「出错啦」，`小说不存在` 在 PC 页 |

**关键量化**：僵尸页与存活页的体积中位只差 **35 字节（0.25%）**——`>5KB 且含书名`
完全无法区分；必须查**阅读入口**与**数字字段合法性**，
不细究下架原因（多数僵尸页不写声明，§11.5）。

### 三态判据（用户 2026-11-17 定案，不细分下架原因）

**只分三态，不追问为什么下架**——版权、违法违规、抄袭、搬运、AI 生成、作者主动、
举报下架等原因**不进判据**：多数页面的简介**不会写**「应版权方要求」之类的声明
（本实验抽到的 50 本僵尸恰好全带版权声明，是低 id 段有偏样本，不能外推）。

| 态 | 判据（满足其一即可） | 实测形态 |
| --- | --- | --- |
| **死亡** | 页面是「小说不存在」/「出错啦」——**匹配否定文案**，不看状态码 | PC 1,643 B、移动 3,738 B，HTTP 均 200 |
| **僵尸** | ① 有详情页（含书名/字数/收藏等字段）但**无阅读入口**；或 ② **详情页数字字段非法**（负数收藏、全零、字数与章节不符等） | 13–15 KB，与存活页体积中位只差 35 B；读入口 0/50 |
| **存活** | 有详情页 + 有 `点击阅读` / `目录列表` + 数字字段合法 | 14.2 KB，读入口 20/20 |

**方向性必须记牢**：

- 「应版权方要求,该小说已经下架」是**充分非必要**条件——出现它必是僵尸，
  **没出现不能判存活**；不能把它当主判据。
- 主判据是「**详情页 + 无阅读入口**」与「**数字字段非法**」，两者都是**缺陷检测**，
  与下架原因无关。
- `status_missing` 在 CSV 里对应 2,287 本僵尸（30 本分层抽样 30/30 无阅读入口），
  但它是**构建期借快照 status 做的间接判据**；站上判活仍应直接查页面，
  因为构建规则并未覆盖所有下架原因。

> **数字字段非法要单列**：`negative_favs`（58 本）在页面上有阅读入口，
> 但 `like_num < 0` 使收藏本身不可信——按用户判据归为僵尸，
> 不因「能点开阅读」就当正常供给。这正是「不只看阅读入口」的原因。

### 对 CSV 构建规则的直接后果

`status_missing`（2,287 本）= 真不可读；其余五类合计 **164 本页面全部可读**
（抽样 44/44 有阅读入口）。所以：

- **报告 10 的遗漏推断错在把「不在 CSV」等同于「不可读」且等同于「抓取遗漏」**：
  2,451 本被剔除的书在原始 jsonl 里**全部已被抓到**（只是构建时被判不可用），
  根本不是抓取阶段漏掉的。其中 2,287 本是僵尸、58 本数字非法（也归僵尸），
  其余 106 本页面可读、只是数据质量或口径问题。
- **真正需要重算的不是全站总量，而是「nid 空洞中三态的比例」**：
  现有探针的 21.1% 只测了「页面能否打开」，把僵尸与死亡都算成存活，
  须按本节三态判据重新判定。

### 对报告 10 重写与补爬估算的直接影响

报告 10 的旧链条是「缺失槽位 × 21.1% 存活率 → 遗漏活书 → 种子覆盖率」。
按本节实测，这条链要拆成三层，**只有最后一层才是补爬对象**：

> **为什么旧覆盖率 68.9% 偏低（用户 2026-11-17 定性）**：误判不在 C 组那 63 本的
> 个体判定——实测 63/63 有阅读入口、`book_Catalog` 均非空、19/25 能被官方 JSON
> 搜索命中自身、数字字段仅 2 本 `words=0`，**确实都是真活书**，21.1% 这个比率
> 没被僵尸污染。偏低出在**分母**：526,415 个「缺失槽位」把三类书混在一起——
> 构建时已剔除的 2,451 本（其中 2,287 本僵尸在原始 jsonl 里早就抓到）、
> 真死亡页、以及真遗漏活书——再统一乘 21.1% 外推。剔除集与死亡页**不是抓取遗漏**，
> 却被算进了「站上有、我们没有」的分母，于是 11.1 万本遗漏被高估、覆盖率被压低。
> 换句话说：**不是把死书判成了活书，而是把「已知在本地/已下架」的书算进了「漏抓」的分母**。

| 层 | 判定 | 处置 |
| --- | --- | --- |
| ① 已在原始 jsonl 但构建时剔除 | 2,451 本（其中 2,287 僵尸 + 58 数字非法 + 106 可读） | **不需要补爬**，数据已在本地，只需决定是否放宽构建规则 |
| ② 死亡页（200 + 否定文案） | 探针旧判「alive」中未覆盖，需重测 | **不可补爬**，页面不存在 |
| ③ 真「有阅读入口但不在库内」 | 高 nid 抽样 40/40 属此类，悬疑普查 22 本同范围真遗漏 | **这才是补爬对象** |

**补爬量的正确问法**：不是「全站有多少遗漏活书」，而是
「**在 `nid ≤ 774,850` 范围内、三态判据为存活、且不在 CSV 里的 nid 有多少**」。
按悬疑整类普查的同范围遗漏率 **0.47%** 和目录普查的 221,354 本估算，
量级约 1 千本（旧稿的 11.1 万、8.6k 均已撤回）。
**低 id 段要单独处理**：2,287 本僵尸集中在 nid ≤83,624，它们不是补爬对象，
而是构建规则的正确剔除——若报告 10 把它们算进「遗漏」，种子质量会被系统性拉低。

**重写 `report_survival.py` 时的硬要求**：

1. 判活必须用 `div.book_Catalog` 是否有 `<a>`（或关键词 fallback）+ 否定文案，**不用 HTTP 状态码、不用体积阈值**；
2. 先扣掉 manifest 的 2,451 个已剔除 nid，再谈「抓取遗漏」；
3. 三态分层报告，不要给单一覆盖率数字；
4. 高/低 nid 分层出数，僵尸率不可外推到全区间。
